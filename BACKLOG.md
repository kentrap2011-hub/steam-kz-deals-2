# BACKLOG

Постоянный список задач проекта, которые **нужно сделать, но не сейчас**.

Назначение:
- сюда переносить только подтверждённые проблемы и улучшения, которые сознательно отложены;
- `CURRENT_TASK.md` использовать для задачи, которая выполняется прямо сейчас;
- при выборе следующей работы просматривать этот файл и поднимать верхнюю подходящую задачу в активную работу;
- backlog не является историей завершённых работ.

## Жизненный цикл задачи — обязательный инвариант

- Как только пользователь выбирает задачу для выполнения, её нужно **сразу удалить из `BACKLOG.md`**. Активная задача не должна одновременно оставаться в backlog.
- После того как пользователь подтверждает фактическое завершение/production-результат задачи, в `BACKLOG.md` не должно оставаться записи со статусом `completed`, `needs_user_verification` или аналогичного хвоста. Если запись почему-либо ещё есть, удалить её **в том же шаге закрытия задачи**.
- Историю уже выполненных задач хранить в Git-коммитах и, только если это архитектурно важно, в `PROJECT_DECISIONS.md`; не использовать backlog как журнал истории.
- Если задача ждёт внешнего production/scheduled результата, она не считается завершённой. Не создавать для неё дубликат backlog-записи, если её состояние уже зафиксировано в `CURRENT_TASK.md` или другом каноническом handoff.
- Новый чат при выборе работы должен считать содержимое этого файла списком только реально оставшихся задач; не тратить время на повторную диагностику пунктов, которых здесь больше нет.

## Обязательные свойства каждой задачи

У каждой задачи в backlog должны быть три оценки по относительной шкале `1..5`.

1. **Локальное исправление (`L`)** — сколько работы нужно непосредственно для изменения кода/конфига/документации.
   - `L1` — тривиальная правка: одна строка, флаг, очевидный config/doc fix;
   - `L2` — маленький локальный патч в одном месте;
   - `L3` — заметная правка/диагностика в одном маршруте;
   - `L4` — несколько компонентов или новая интеграция;
   - `L5` — исследование/архитектурная работа/большая реализация.

2. **Полный цикл (`T`)** — сколько времени/этапов нужно от начала локального исправления до фактически обновлённой и проверенной системы.
   - `T1` — результат готов сразу после локальной правки;
   - `T2` — нужен обычный commit + короткий CI/test;
   - `T3` — нужен rebuild/несколько штатных стадий;
   - `T4` — есть внешний/scheduled этап или заметное ожидание;
   - `T5` — несколько циклов, внешний runtime/retry или длительность существенно зависит от внешней системы.

3. **Важность (`I`)** — насколько сильно незакрытая задача влияет на полезность/надёжность системы.
   - `I1` — косметика/малозаметное улучшение;
   - `I2` — низкая важность, основной сценарий уже работает;
   - `I3` — средняя, заметно улучшает качество/полноту;
   - `I4` — высокая, влияет на важный production-сценарий;
   - `I5` — критическая/блокирующая. Критический incident, секрет или production outage не должен лежать в backlog — его нужно разбирать сразу по правилам проекта.

Оценки относительные: они нужны для сравнения задач между собой, а не как обещание точного времени. Их можно уточнять, когда появляется новая фактическая информация.

### Порядок backlog

По умолчанию задачи хранятся и выбираются в таком порядке:
1. меньше `L` — выше;
2. при одинаковом `L` меньше `T` — выше;
3. при одинаковых `L` и `T` больше `I` — выше.

Явно отложенная пользователем задача может быть пропущена при выборе следующей работы, даже если формально имеет меньшее `L`.

### Бесплатные раздачи Steam / free-to-keep — отдельный видимый блок

**Статус:** `user_high_priority_next_slot`  
**L:** `L4`  
**T:** `T4`  
**I:** `I4`  
**Зафиксировано:** 2026-08-21  
**Актуализировано:** 2026-09-01  
**Приоритет пользователя:** выполнить в первый освободившийся worker-слот раньше обычных улучшений карточек/вторичных функций. Причина — бесплатные раздачи ограничены по времени, а пока отдельного видимого блока нет, пользователь может их фактически пропускать.

Пользовательское правило:
- регулярно проверять именно временные бесплатные раздачи / `free-to-keep`, а не смешивать их с обычными платными скидками;
- показывать такие игры отдельным самостоятельным блоком, чтобы они были заметны и не терялись в основном скидочном feed;
- не считать постоянный free-to-play автоматически такой раздачей;
- сохранить смысловой фильтр: отдельный блок предназначен для раздач, которые хотя бы потенциально релевантны пользователю, а не для безусловного вывода любого бесплатного мусора;
- сбор/полнота/повторная проверка должны принадлежать GitHub-owned production flow, а не памяти интерактивного чата.

Что сделать:
- сначала bounded RECON текущего production/source route: выяснить, видит ли система `free-to-keep` сейчас и на каком шаге такие предложения теряются;
- определить надёжный GitHub-доступный источник/сигнал для текущих Steam giveaway/free-to-keep предложений и точную семантику отличия от `free weekend`, демо и постоянного F2P;
- добавить отдельное production-представление/статус полноты для актуальных раздач, без ручного списка в ChatGPT;
- вывести отдельный видимый раздел/режим в read-only UI;
- обеспечить удаление/скрытие раздачи после окончания акции и не терять активную раздачу из-за обычного taste/ranking cutoff;
- добавить regressions на обнаружение, дедупликацию, срок действия и отдельную видимость;
- после rebuild проверить актуальные активные раздачи на реальном production state.

### Wishlist: хорошие скидки должны преодолевать слабое taste-попадание

**Статус:** ready_for_design  
**L:** `L4`  
**T:** `T3`  
**I:** `I4`  
**Зафиксировано:** 2026-08-30

Пользовательское правило:
- игра из Steam wishlist должна попадать в итоговый список при действительно хорошей текущей скидке, даже если автоматическое taste-попадание минимальное;
- wishlist остаётся явным сигналом личного интереса и в этом сценарии может преодолеть обычный taste eligibility/filter, а не быть только небольшим бонусом внутри уже прошедших фильтр игр.

Что сделать:
- пересмотреть eligibility/filter до ranking, а не только величину wishlist score bonus;
- определить `good discount` через канонический deal-quality/history контекст и зафиксировать порог/условие явно, не изобретая скрытую константу;
- сохранить защиту от плохой покупки: серьёзные подтверждённые риски и явно невыгодная цена не должны исчезать из объяснения только из-за wishlist;
- добавить regression: wishlist + хорошая скидка + слабый taste всё равно попадает в feed; слабая скидка не обязана пробивать фильтр;
- после rebuild проверить полноту wishlist относительно текущих скидок.
