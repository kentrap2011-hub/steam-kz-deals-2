# BACKLOG

Постоянный список задач проекта, которые **нужно сделать, но не сейчас**.

Назначение:
- сюда переносить подтверждённые проблемы и улучшения, которые сознательно откладываются ради более приоритетной работы;
- `CURRENT_TASK.md` использовать только для задачи, которая выполняется прямо сейчас;
- при выборе следующей работы просматривать этот файл и поднимать верхнюю подходящую задачу обратно в `CURRENT_TASK.md`;
- завершённые пункты удалять или переносить в историю/коммит, чтобы backlog оставался коротким.

## Обязательные свойства каждой задачи

У каждой задачи в backlog должны быть три оценки по относительной шкале `1..5`.

1. **Локальное исправление (`L`)** — сколько работы нужно непосредственно для изменения кода/конфига/документации.
   - `L1` — тривиальная правка: одна строка, флаг, очевидный config/doc fix;
   - `L2` — маленький локальный патч в одном месте;
   - `L3` — заметная правка/диагностика в одном маршруте;
   - `L4` — несколько компонентов или новая интеграция;
   - `L5` — исследование/архитектурная работа/большая реализация.

2. **Полный цикл (`T`)** — сколько времени/этапов нужно от начала локального исправления до фактически обновлённой и проверенной системы.
   - `T1` — результат готов сразу после локальной правки;
   - `T2` — нужен обычный commit + короткий CI/test;
   - `T3` — нужен rebuild/несколько штатных стадий;
   - `T4` — есть внешний/scheduled этап или заметное ожидание;
   - `T5` — несколько циклов, внешний runtime/retry или длительность существенно зависит от внешней системы.

3. **Важность (`I`)** — насколько сильно незакрытая задача влияет на полезность/надёжность системы.
   - `I1` — косметика/малозаметное улучшение;
   - `I2` — низкая важность, основной сценарий уже работает;
   - `I3` — средняя, заметно улучшает качество/полноту;
   - `I4` — высокая, влияет на важный production-сценарий;
   - `I5` — критическая/блокирующая. Критический incident, секрет или production outage не должен лежать в backlog — его нужно разбирать сразу по правилам проекта.

Оценки относительные: они нужны для сравнения задач между собой, а не как обещание точного времени. Их можно уточнять, когда появляется новая фактическая информация.

### Порядок backlog

По умолчанию задачи хранятся и выбираются в таком порядке:
1. меньше `L` — выше;
2. при одинаковом `L` меньше `T` — выше;
3. при одинаковых `L` и `T` больше `I` — выше.

Явно отложенная пользователем задача может быть пропущена при выборе следующей работы, даже если формально имеет меньшее `L`.

### Achievements: повысить ценность достижений для уже сыгранных игр

**Статус:** ready_for_design  
**L:** `L3`  
**T:** `T3`  
**I:** `I4`  
**Зафиксировано:** 2026-08-30

Пользовательское правило:
- для игры, в которую пользователь уже играл/которую прошёл, наличие хороших достижений намного важнее, чем для новой игры;
- если такая игра уже пройдена и достижений нет, её ценность для повторной покупки/возврата резко падает.

Что сделать:
- использовать confirmed played/completed state как контекст для achievement-компонента рейтинга;
- увеличить влияние achievement quality именно для уже сыгранных игр, не повышая его механически для всех игр;
- определить отдельный сильный отрицательный случай `played/completed + no meaningful achievements`;
- не придумывать точный новый вес молча: зафиксировать его в canonical ranking contract/decision до реализации;
- проверить regression-пары: новая игра без достижений не должна получать тот же штраф, что уже пройденная игра без причин возвращаться.

### Wishlist: хорошие скидки должны преодолевать слабое taste-попадание

**Статус:** ready_for_design  
**L:** `L4`  
**T:** `T3`  
**I:** `I4`  
**Зафиксировано:** 2026-08-30

Пользовательское правило:
- игра из Steam wishlist должна попадать в итоговый список при действительно хорошей текущей скидке, даже если автоматическое taste-попадание минимальное;
- wishlist остаётся явным сигналом личного интереса и в этом сценарии может преодолеть обычный taste eligibility/filter, а не быть только небольшим бонусом внутри уже прошедших фильтр игр.

Что сделать:
- пересмотреть eligibility/filter до ranking, а не только величину wishlist score bonus;
- определить `good discount` через канонический deal-quality/history контекст и зафиксировать порог/условие явно, не изобретая скрытую константу;
- сохранить защиту от плохой покупки: серьёзные подтверждённые риски и явно невыгодная цена не должны исчезать из объяснения только из-за wishlist;
- добавить regression: wishlist + хорошая скидка + слабый taste всё равно попадает в feed; слабая скидка не обязана пробивать фильтр;
- после rebuild проверить полноту wishlist относительно текущих скидок.

### Taste score: заменить грубый strong/moderate fallback детальными нормализованными факторами

**Статус:** ready_for_implementation  
**L:** `L4`  
**T:** `T4`  
**I:** `I4`  
**Зафиксировано:** 2026-08-30  
**Причина оценки:** прозрачный рейтинг 0–100 уже работает в production, но большинство старых taste-cache записей пока имеют только `strong/moderate`, поэтому компонент «Игра сама по себе» временно использует явный `legacy_coarse_fit` fallback (`42/50` или `34/50`). Для действительно тонкого сравнения интересности нужен один migration/enrichment cycle существующего semantic taste pipeline.

Что сделать:
- расширить taste result/cache contract полем `taste_factors` с нормализованными значениями `0..100` по пяти price-blind факторам V2;
- semantic worker должен оценивать сами нормализованные факторы, а не применять текущие веса;
- GitHub валидирует диапазоны и хранит vector в canonical taste cache;
- изменение `max_points` в `config/final_ranking_policy.json` после этого не должно требовать новой AI-оценки;
- мигрировать старые активные записи через существующую taste queue без новой recurring стадии;
- после миграции проверить распределение `taste_points` и несколько реальных пар игр;
- убрать `legacy_coarse_fit` только когда активный production scope имеет достаточное покрытие детальными факторами.

### Bundles/packages: учитывать более выгодный набор вместо покупки отдельных игр

**Статус:** ready_for_research  
**L:** `L5`  
**T:** `T4`  
**I:** `I4`  
**Зафиксировано:** 2026-08-30

Подтверждённый пример:
- сейчас по `BioShock` видна скидка на отдельные игры, но витрина не показывает, что покупка набора со всеми этими играми может быть выгоднее.

Что сделать:
- исследовать canonical Steam/SteamDB evidence для packages/bundles, их состава, текущих цен и скидок;
- для игры уметь находить релевантный набор, если он содержит эту игру и даёт пользователю объективно более выгодный вариант покупки;
- учитывать тип набора и персонализированную цену там, где Steam применяет complete-the-set/ownership pricing, не сравнивать несопоставимые цены как обычные fixed bundles;
- producer должен хранить выбранный purchase option и объяснение выгоды; UI только отображает его;
- на карточке явно показывать что выгоднее купить набор, какие релевантные игры он включает и сколько стоит вариант покупки;
- не допускать дублирования, при котором отдельные игры выглядят лучшей сделкой, если канонически доступен более выгодный набор;
- добавить regression на семейство `BioShock` и несколько наборов разных типов.
