# BACKLOG

Постоянный список задач проекта, которые **нужно сделать, но не сейчас**.

Назначение:
- сюда переносить подтверждённые проблемы и улучшения, которые сознательно откладываются ради более приоритетной работы;
- `CURRENT_TASK.md` использовать только для задачи, которая выполняется прямо сейчас;
- при выборе следующей работы просматривать этот файл и поднимать верхнюю подходящую задачу обратно в `CURRENT_TASK.md`;
- завершённые пункты удалять или переносить в историю/коммит, чтобы backlog оставался коротким.

## Обязательные свойства каждой задачи

У каждой задачи в backlog должны быть три оценки по относительной шкале `1..5`.

1. **Локальное исправление (`L`)** — сколько работы нужно непосредственно для изменения кода/конфига/документации.
   - `L1` — тривиальная правка: одна строка, флаг, очевидный config/doc fix;
   - `L2` — маленький локальный патч в одном месте;
   - `L3` — заметная правка/диагностика в одном маршруте;
   - `L4` — несколько компонентов или новая интеграция;
   - `L5` — исследование/архитектурная работа/большая реализация.

2. **Полный цикл (`T`)** — сколько времени/этапов нужно от начала локального исправления до фактически обновлённой и проверенной системы.
   - `T1` — результат готов сразу после локальной правки;
   - `T2` — нужен обычный commit + короткий CI/test;
   - `T3` — нужен rebuild/несколько штатных стадий;
   - `T4` — есть внешний/scheduled этап или заметное ожидание;
   - `T5` — несколько циклов, внешний runtime/retry или длительность существенно зависит от внешней системы.

3. **Важность (`I`)** — насколько сильно незакрытая задача влияет на полезность/надёжность системы.
   - `I1` — косметика/малозаметное улучшение;
   - `I2` — низкая важность, основной сценарий уже работает;
   - `I3` — средняя, заметно улучшает качество/полноту;
   - `I4` — высокая, влияет на важный production-сценарий;
   - `I5` — критическая/блокирующая. Критический incident, секрет или production outage не должен лежать в backlog — его нужно разбирать сразу по правилам проекта.

Оценки относительные: они нужны для сравнения задач между собой, а не как обещание точного времени. Их можно уточнять, когда появляется новая фактическая информация.

### Порядок backlog

По умолчанию задачи хранятся и выбираются в таком порядке:
1. меньше `L` — выше;
2. при одинаковом `L` меньше `T` — выше;
3. при одинаковых `L` и `T` больше `I` — выше.

То есть основной принцип пользователя: **сначала закрывать то, что можно исправить локально быстрее всего**, затем учитывать полный цикл, и только после этого важность как tie-breaker. Явно критические ситуации (`I5`, incident/security/outage) не ждут сортировки backlog.

### SteamDB history: закрыть оставшиеся retry и проверить штатный handoff

**Статус:** deferred_user_low_priority  
**L:** `L3`  
**T:** `T5`  
**I:** `I2`  
**Зафиксировано:** 2026-08-30  
**Причина оценки:** локально требуется диагностика/починка штатного handoff, но полный результат зависит от внешнего scheduled runtime, retry, ingestion, validation, checkpoint и downstream rebuild. Основной history-сценарий уже работает для 529 из 534 ключей; пользователь отдельно подтвердил, что оставшиеся 5 retry сейчас не важны.

Что осталось:
- GitHub-derived runtime work содержит 534 SteamDB history ключа: 529 resolved, 5 unresolved;
- оставшиеся ключи: `App_1282200`, `App_225320`, `App_399670`, `App_630060`, `App_901735`;
- последний известный failure для них: `runtime_web_internal_error`;
- нужно не обрабатывать их вручную в interactive chat, а довести до рабочего состояния штатный GitHub → scheduled runtime handoff;
- после получения evidence GitHub должен сам выполнить ingestion/validation/checkpoint, обновить canonical history cache и downstream artifacts;
- задача считается закрытой только после `unresolved_count == 0` и успешного end-to-end downstream rebuild.

При возврате к задаче сначала сверяться с `config/execution_ownership_contract.json`, `config/steamdb_lookup_contract.json` и актуальным `data/cache/steamdb_runtime_work.json`.

### Ranking: перейти на прозрачный числовой рейтинг 0–100 с разложением баллов

**Статус:** ready_for_design  
**L:** `L5`  
**T:** `T3`  
**I:** `I4`  
**Зафиксировано:** 2026-08-30  
**Причина оценки:** это высоковажное улучшение прозрачности и управляемости ranking. Независимый taste-review больше не является ожидаемой зависимостью, поэтому задачу можно проектировать на основе текущего production, известных пользовательских примеров и последующей проверки распределения по всему списку. Потребуется изменить саму каноническую модель, producer, regression-тесты и UI, затем выполнить полный production rebuild.

Цель:
- каждая игра имеет понятный итоговый балл, например `82/100`, который **реально определяет её автоматическую позицию**;
- карточка показывает вклад каждого критерия и позволяет быстро заметить неверный вес: например, если скидка или история цены дали слишком много баллов и вытянули менее интересную игру выше более подходящей;
- сохранить уже согласованный принцип примерно `60% вкус / 40% качество покупки`, но не придумывать точные веса отдельных подпунктов без отдельной проверки/согласования;
- срочность окончания скидки и жёсткие eligibility/budget gates не маскировать обычными баллами, если им логичнее остаться отдельными верхнеуровневыми правилами.

Что сделать:
- сначала разработать честный числовой `taste_score` без цены, скидки, wishlist и deal-quality; текущих `strong/moderate` недостаточно для правдоподобных значений вроде `51/60`;
- определить прозрачную шкалу `purchase_score` из скидки, текущей цены, качества относительно истории и других подтверждённых коммерческих факторов;
- отдельно определить видимые бонусы/штрафы wishlist, серьёзного риска, достижений и длительности без двойного учёта одного и того же сигнала;
- согласовать точные веса и диапазоны, обновить `config/final_ranking_policy.json`/новую версию canonical contract и rationale в `PROJECT_DECISIONS.md`;
- producer должен сохранять итоговый score и полное разложение баллов; UI только отображает готовые значения;
- сортировка должна использовать тот же producer-owned score, который видит пользователь; не создавать декоративный балл параллельно lexicographic ranking;
- добавить regression-набор на пары игр, где вкусовая разница должна перевешивать небольшую коммерческую выгоду, и наоборот;
- после внедрения пересобрать production и проверить распределение баллов по всему списку, а не только на нескольких примерах.
