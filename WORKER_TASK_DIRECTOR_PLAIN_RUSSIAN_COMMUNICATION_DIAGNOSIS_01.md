## Основная жалоба пользователя

Директорский чат постоянно объясняет простые решения техническими словами и английскими сокращениями, хотя текст должен быть понятен человеку без знания устройства GitHub. Пользователь вынужден уточнять даже базовые вопросы («что значит независимый QA PR», «что такое приёмка»). Причину нужно установить, а не просто добавить ещё одно неработающее правило.

## START

Прочитай актуальный CHAT_PROTOCOL.md и выполни START gate; bounded preflight только директорских правил коммуникации. Адресный task и Board top, без общего аудита репозитория.

## Что исследовать

1. Найди текущие предписания о ясности русского языка, англицизмах, терминологии, разделении внутренней служебной информации и объяснениях пользователю: `DIRECTOR_PROTOCOL.md`, `CHAT_PROTOCOL.md`, `CHAT_CONTEXT.md`, `DIRECTOR_HANDOFF_CURRENT.md` и только непосредственно связанные документы. Установи, **есть ли на самом деле** прямое правило не использовать ненужный жаргон. Не утверждай, что оно существует, если его нет.
2. На примерах известных диалогов из описанного пользовательского запроса и при необходимости тех небольших доступных источников, которые реально можно прочесть, сопоставь конкретные непонятные объяснения с нормами и реальной задачей директора. Пример: «независимый QA PR» вместо «другой чат проверяет предложенные изменения». Не заявляй доступа к скрытым инструкциям модели или ко всей истории чатов, если их нет в источниках.
3. Классифицируй доказанную причину: нормы отсутствуют; нормы есть, но противоречат друг другу; требования показывать SHA/PR/CI вытесняют простой ответ; нарушена уже действующая норма; либо не хватает доказательств. Раздели ошибку поведения директора и дефект репозиторного протокола.
4. Предложи одно **наименьшее практическое исправление**, которое может реально изменить ответы: например, правило «сначала ответ обычным русским, технические детали только по запросу или для нужной ссылки» либо указание директору соблюдать уже существующее, если оно достаточное. Представь 2–3 пары «плохо → понятно» на конкретных проектах.
5. Учти стоимость будущего чтения правил. Не предлагай новый длинный регламент, расширение обязательных START чтений, новый CI, Actions, автоматический языковой контроль, отдельный словарь, переустройство всей архитектуры или очередную цепочку аудитов.
