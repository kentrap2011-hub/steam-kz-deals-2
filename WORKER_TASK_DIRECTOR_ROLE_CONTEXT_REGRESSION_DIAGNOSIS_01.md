## Наблюдаемые эпизоды для расследования (свидетельства текущего диалога)

1. При первом принятии директорской роли первоначальное восстановление и регистрация задач в PR #242 заняли около 13 минут. Директор объяснил это широким чтением истории, несколькими GitHub gate и исправлением собственного сбоя CI. Нужно разделить разумный первоначальный bootstrap и необязательный избыточный сбор контекста.

На короткое поручение пользователя «Проверь чат 1» директор обнаружил draft PR #243, отчёт и три успешных CI — информации для краткого статуса достаточно, но продолжил открывать patch, полные протоколы, JSON-реестр и большую часть Board и пытался предвосхитить создание задания для ЧАТ 2, не запрошенное пользователем в этом сообщении. Пользователь: «Опять долго».
3. Директор признал, что повторно читает большие документы, смешивает статусную проверку с полным аудитом и переходит к следующей работе без запроса. Пользователь указал, что директор — долгоживущий управляющий чат для экономии контекста, а рабочие чаты предназначены для GitHub-исследований, технических проверок и правок.
4. Директор предложил опять «проверить и закрепить» правила, вместо того чтобы поручить независимое исследование. Пользователь требует найти конкретный источник этой поведенческой регрессии, а не очередную неопределённую перепись документов.

Эти факты — краткий изложенный пользователем сценарий и наблюдения, а не полная стенограмма или доступ к приватным инструкциям модели. Не выдавай предположения о hidden prompts, inference или модели за доказанные факты.

## Исследование — точные вопросы

A. Где и в каком **порядке** реальный новый директор получает определение роли? Дай точные файлы/короткие строки и возможные противоречащие обязательства (mandatory START, architecture preflight, глобальный governance gate, PR acceptance, inspect on every prompt, director bootstrap, handoff). Раздели «документ требует» и «модель сама решила».
B. Есть ли устойчивый **краткий director hot path** для типовых обращений («что делаем дальше», «проверь чат N», «принимай PR», «выдай prompt», «назначь новое задание»)? Если есть, почему его могли проигнорировать? Если нет, покажи точный пробел. Отдельно оцени важный случай: задачи ещё не зарегистрированы в main — что директор обязан сделать сам и что может делегировать, не нарушив gates.
C. На каждом эпизоде составь таблицу: запрос / минимально достаточные доказательства / фактическое лишнее действие / релевантная нормативная строка / тип проблемы / степень уверенности. Ищи причинно-следственную связь, а не общие пожелания «работать быстрее».
D. Раздели три уровня причин: (1) ошибки исполнения самого директора вопреки ясным правилам, (2) двусмысленность или конфликт документов, (3) техническая неоптимальность реестра/большого Board/CI. Поищи признаки, что новая оптимизация governance могла усилить формализм; **не заявляй причинность только по совпадению во времени**.
E. Предложи **один** минимальный, проверяемый план коррекции по приоритету, по возможности сначала без изменения кода/контрактов; если изменение текста действительно нужно — назови 1–2 точных места и формулировки для будущего отдельного IMPLEMENT task, но НЕ вноси их.
F. Приведи проверяемые acceptance scenarios и оценку ожидаемого изменения количества GitHub calls, чтений больших файлов, потребления директорского контекста. Главная метрика — директор не делает работу worker без основания, но обязательные safety/merge gates остаются.
