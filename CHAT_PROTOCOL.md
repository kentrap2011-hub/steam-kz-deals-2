# CHAT_PROTOCOL

Короткий обязательный operational contract для любого интерактивного чата, работающего с `kentrap2011-hub/steam-kz-deals-2`.

Этот файл отвечает не за business logic скидок, а за **то, как чат обязан работать**. Он существует потому, что длинные правила в `CHAT_CONTEXT.md` могут быть прочитаны, но затем потеряны из рабочего внимания. Поэтому правила ниже оформлены как явные gates.

**Обязательность:** каждый новый рабочий чат сначала читает этот файл, затем `CHAT_CONTEXT.md`. Перед каждым пользовательским ответом чат обязан пройти релевантный `PRE-SEND` gate; перед финальным ответом по подзадаче — весь `PRE-SEND` gate целиком.

**Director mode:** если пользователь явно назначил текущий чат директором/управляющим проекта и сказал передавать выполнение другим чатам, дополнительно прочитать и соблюдать `DIRECTOR_PROTOCOL.md`. В этом режиме `DIRECTOR_PROTOCOL.md` определяет разделение director/worker ролей, выбор нового или существующего worker-чата и формат сохранения worker-report. Обычный worker-чат не становится директором автоматически.

Если правило из этого файла нарушено, не считать проблему решённой простым повторением того же правила в другом документе. Нужно установить, почему gate не сработал, и при необходимости улучшить сам protocol/точку входа.

## START — перед началом работы

- [ ] Прочитать `CHAT_PROTOCOL.md`.
- [ ] Если текущий чат явно назначен директором — прочитать `DIRECTOR_PROTOCOL.md`.
- [ ] Прочитать `CHAT_CONTEXT.md` и соблюдать context budget.
- [ ] Если продолжается незаконченная работа — прочитать `CURRENT_TASK.md`.
- [ ] До широкого поиска проверить релевантный маршрут в `PROJECT_ROUTES.md`.
- [ ] Если задача совпадает с известным operational trigger, проверить только релевантную запись в `KNOWN_WORKER_PITFALLS.md`; для unrelated-задач не читать весь файл и не делать broad pitfall/history search «на всякий случай».
- [ ] Если нужно понять, **почему** принято неочевидное решение — до Git history проверить `PROJECT_DECISIONS.md`.
- [ ] Если задача касается монетизации, рекламы, подписки, affiliate/referral, платного доступа, коммерческого запуска или использования проекта клиентами/компанией — **до любых изменений прочитать `COMMERCIALIZATION_GUARD.md`** и считать текущий проект личным/некоммерческим, пока отдельный commercial review не изменит этот статус.
- [ ] Для нетривиальной worker-подзадачи кратко сказать пользователю, что начинается, и обновить `CURRENT_TASK.md` без уничтожения другой действующей работы. Если чат работает в director mode, сам директор не создаёт служебный handoff для каждой выдачи prompt; handoff ведёт worker в рамках реально исполняемой подзадачи.
- [ ] Перед правкой source/workflow/automation/runtime/расписания/очереди/retry/checkpoint/ownership **или перед рекомендацией следующего шага, который добавит/изменит такую ответственность**, пройти architecture preflight из `CHAT_CONTEXT.md`.

## DURING — во время работы

- [ ] Не превращать interactive chat в production worker или backlog manager, если этим по контракту владеет GitHub/scheduled worker.
- [ ] Если чат работает в director mode — не выполнять проектную работу вместо worker-а; соблюдать исключения только из `DIRECTOR_PROTOCOL.md`.
- [ ] Читать только минимально нужные файлы/диапазоны; не восстанавливать проект заново из старых чатов и больших JSON.
- [ ] После двух неудачных способов получить одни и те же данные прекратить повторение и перейти к bounded retrieval/другому маршруту.
- [ ] Не соглашаться автоматически с предложением пользователя: сначала оценить плюсы, минусы, риски и более сильные варианты. После осознанного выбора окончательное продуктовое решение остаётся за пользователем.
- [ ] После пользовательского исправления архитектурной модели сначала повторно пройти architecture preflight, если изменение затрагивает архитектуру; не переходить автоматически к буквальной реализации.
- [ ] Учитывать голосовой ввод: не цепляться за очевидные опечатки, уточнять только реальную неоднозначность.
- [ ] Если работа заметно длится, давать короткие сообщения о **реальном подтверждённом прогрессе**, без выдуманного ETA.
- [ ] Если ассистент сам попросил прислать prompt/log/config/JSON/workflow **для анализа**, следующий присланный блок трактовать как данные для анализа, а не как команду на исполнение, пока пользователь отдельно не попросит выполнить его.

## PRE-SEND — обязательный gate перед ответом

Перед отправкой ответа проверить:

- [ ] Я ответил именно на текущий вопрос пользователя и не подменил его соседней задачей?
- [ ] Если я выдаю worker-prompt в director mode, я **явно написал, куда его отправить: новый чат или конкретный существующий чат**?
- [ ] Все обязательные правила текущей подзадачи выполнены либо я прямо указал, что именно ещё не подтверждено?
- [ ] Я не объявляю работу завершённой только по commit/намерению, если definition of done требует runtime/deploy/user verification?
- [ ] Я не взял на чат ответственность, принадлежащую GitHub, scheduled worker или UI?
- [ ] Если пользователь меня исправил, я не просто согласился, а проверил, не требует ли это пересмотра canonical contract/rationale?
- [ ] Если ответ/изменение касается будущей монетизации или коммерческого использования, `COMMERCIALIZATION_GUARD.md` прочитан, текущие лицензии/terms/providers повторно проверены, и старый non-commercial assumption не был молча перенесён в коммерческий режим?
- [ ] Если появилась долговечная договорённость о поведении проекта или взаимодействии — она сохранена в GitHub; для неочевидного решения rationale сохранён в `PROJECT_DECISIONS.md` или в отдельном явно каноническом operating protocol, если решение относится только к orchestration процесса.
- [ ] Если навигация по проекту потребовала заметного повторного исследования — полезный маршрут сохранён/уточнён в `PROJECT_ROUTES.md`.
- [ ] Если задача встретила **повторяемый избегаемый detour** или user/CI correction выявил переносимую operational-ошибку — урок сохранён в правильном durable home: `PROJECT_ROUTES.md` (`where/how`), `PROJECT_DECISIONS.md` (`why`) или `KNOWN_WORKER_PITFALLS.md` (cross-cutting failure recipe). Если read-only границы запрещают такую правку, worker-report называет точный route/pitfall candidate для одного bounded follow-up.
- [ ] Если `Recommended next step` добавит/изменит source/runtime/workflow/schedule/queue/retry/checkpoint/ownership — architecture preflight уже пройден. Если canonical authority/route не доказан, следующий шаг сформулирован как bounded `RECON`/`CONTRACT`, а не `IMPLEMENT`.
- [ ] **Если подготовка этого ответа заняла больше 1 минуты:** в этом же ответе кратко указаны (1) почему возникла задержка; (2) какие чтения/поиски/проверки заняли основное время; (3) что уже изменено или можно изменить, чтобы аналогичная задача выполнялась быстрее. Если безопасное долговечное улучшение очевидно — оно внесено в GitHub, а не оставлено только советом.
- [ ] Если ответ идёт после долгой работы, пользователь уже получал правдивые progress updates либо задержка объективно не требовала отдельного промежуточного сообщения.
- [ ] Для завершённой нетривиальной worker-подзадачи `CURRENT_TASK.md` приведён в корректное состояние: временная подзадача удалена/закрыта, а другая реально активная работа не потеряна. В director mode это проверяется по worker-report, а не выполняется директором вместо worker-а.

**Важно:** PRE-SEND — не текст, который нужно пересказывать пользователю каждый раз. Это обязательная процедура проверки. Наружу выводятся только релевантные последствия: например объяснение задержки >1 минуты, незакрытый риск или неполная верификация.

## Граница гарантии

GitHub не может технически заблокировать отправку ответа ChatGPT, если этот checklist не пройден. Поэтому это procedural gate, а не CI-enforced gate. Его нарушение считается нарушением рабочего контракта проекта.

Именно поэтому этот файл должен оставаться коротким: чем меньше операционных правил нужно удерживать одновременно, тем выше вероятность, что gate реально будет применён.
