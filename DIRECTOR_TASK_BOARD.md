# DIRECTOR TASK BOARD

Компактная директорская карта задач проекта `kentrap2011-hub/steam-kz-deals-2`.

Назначение: быстро выбирать следующую пару worker-задач без повторного разбора длинного `CURRENT_TASK.md`.

`CURRENT_TASK.md` остаётся источником истины для технического статуса проекта. Этот файл хранит только директорские метаданные: приоритет, размер, область, конфликтность, необходимость пользовательской проверки и рекомендуемый порядок.

## Правила работы

1. Одновременно по умолчанию работают не больше **двух worker-чатов**.
2. Нормальная пара: **одна главная приоритетная задача + одна быстрая независимая задача**.
3. Перед запуском пары директор проверяет, что workers не будут менять одни и те же смысловые области/файлы или зависеть от незавершённого результата друг друга.
4. Если проблема понятна плохо или неизвестен размер исправления — сначала `READ-ONLY / RECON`, затем отдельный `IMPLEMENT` только по подтверждённой причине.
5. Большие задачи качества сначала допускается превращать в ограниченный аудит выборки, чтобы понять реальный масштаб до реализации.
6. UI-задачи, которые пользователь может оценить только на реальном телефоне, не считать окончательно закрытыми до короткой пользовательской проверки.
7. Worker-чат удаляется только по правилу `DIRECTOR_PROTOCOL.md`: после сохранения результата, решения директора и нужной пользовательской проверки.
8. После завершения/старта задач директор обновляет эту таблицу, не превращая её в технический журнал.
9. Приоритет ближайшего продуктового направления: сначала довести основную карточку рекомендации, затем расширять её дополнительными функциями.
10. Для каждой активной worker-задачи хранить ожидаемый report path. Если пользователь пишет просто `один чат закончил` / `чат закончил`, директор сначала проверяет ожидаемые report-файлы активных задач и сам определяет, какой worker завершился. Пользователю не нужно помнить название задачи или номер чата.
11. Если ожидаемый report не найден, но пользователь сообщил о завершении, директор дополнительно проверяет свежие commits после выдачи поручения: worker мог ошибочно сохранить report под другим именем. Если такой report однозначно найден по свежему commit/task содержанию, использовать фактический путь и зафиксировать расхождение; не заставлять пользователя вручную выяснять, какой чат закончил.
12. Подготовленная task-file не считается запущенной worker-задачей, пока директор не выдал пользователю команду для конкретного нового/существующего чата. Статусы `prepared` и `active` различать явно.
13. Пока worker-чат существует, ему назначается простой пользовательский слот `ЧАТ 1` или `ЧАТ 2`. Слот хранится в этой board рядом с задачей и не меняется при follow-up в том же чате. После подтверждённого удаления чата слот освобождается и может быть назначен новой задаче.
14. Перед каждым копируемым сообщением директор отдельной НЕкопируемой строкой пишет: `ЧАТ N — <короткое понятное имя> — НОВЫЙ ЧАТ` или `ЧАТ N — <короткое понятное имя> — СУЩЕСТВУЮЩИЙ ЧАТ`. Эта строка предназначена пользователю для ориентации и не включается в writing block.
15. При желании пользователь может переименовать сами ChatGPT worker-чаты теми же короткими именами; canonical идентификация всё равно хранится здесь по slot + task + report path.

## Как выбирать быструю вторую задачу

Предпочитать работу, которая:
- ограничена чтением/диагностикой или небольшой независимой областью;
- не меняет те же UI/producer/ranking части, что главная задача;
- имеет ясный критерий готовности;
- уменьшает неопределённость перед будущей большой задачей.

## Предпочтительный продуктовый порядок

1. Сделать способ покупки компактным и понятным. — завершено.
2. Упростить и привести в порядок подробную оценку на карточке. — завершено после phone follow-up.
3. Проверить качество причин `почему подходит / почему может не подойти` и исправить системные слабости.
4. Обеспечить нормальные русские описания и понятную информацию о русском языке. — `ЧАТ 1` аудитирует масштаб.
5. Устранить необоснованные `duration unknown` в видимых рекомендациях. — `ЧАТ 2` диагностирует причину и масштаб.
6. После стабилизации основной карточки добавлять вторичные функции, например YouTube-обзоры.

Порядок можно менять по новым пользовательским проблемам или новым blocker-ам; это директорская карта, а не жёсткий roadmap.
