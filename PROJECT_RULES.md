# Правила проекта рассылки скидок

Этот файл — постоянная точка входа для любого нового чата, который продолжает работу над рассылкой. Перед изменениями логики сначала прочитать этот файл. Новые подтверждённые пользователем правила добавлять сюда.

## Главная цель

Рассылка нужна не просто для показа скидок. Её главная практическая задача — помочь пользователю выбрать примерно одну платную игру в месяц, которую действительно стоит купить сейчас.

Бесплатные раздачи идут отдельно: если игру можно забрать навсегда бесплатно и она релевантна, её нужно показать независимо от месячного выбора платной игры.

## Как выбирать платные игры

Вкус — главный фильтр. Пользователю нужны игры, в которые он хотел бы играть сами по себе, а скидка должна делать покупку особенно удачной именно сейчас.

Большая скидка не может вытянуть игру, которая сама по себе не достигает хотя бы умеренного соответствия вкусу. Логика «взял бы только потому, что почти бесплатно» для платных рекомендаций не подходит.

После прохождения вкусового порога итоговый приоритет учитывает одновременно:

- насколько игра подходит пользователю по вкусу;
- насколько выгодно покупать её именно сейчас.

Базовый ориентир: примерно 60% веса — соответствие вкусу, 40% — выгодность текущего предложения. Это принцип ранжирования, а не разрешение скидке повышать вкусовую оценку.

Выгодность — это не только процент скидки. Нужно учитывать конечную цену, близость к лучшей исторической цене и то, насколько необычно выгодно текущее предложение.

Совсем символическую скидку можно отбрасывать до финального списка. Зафиксированный консервативный порог: скидка 5% и меньше считается недостаточной для смысла этой системы.

Бюджет ограничен. Нормальная целевая цена покупки — около 500 ₽. Небольшое превышение допустимо только при хорошем сочетании вкусового попадания и выгодности. Для сильного кандидата допускается более высокий бюджет, но 750 ₽ — абсолютный максимум для платной рекомендации. Цена выше 750 ₽ исключает предложение независимо от размера скидки и качества игры.

Зона ближе к верхнему пределу 750 ₽ предназначена только для действительно сильного вкусового совпадения и очень большой скидки относительно обычной цены. Операционный ориентир для «очень большой скидки» — 75% и выше. Скидка не повышает вкусовую оценку и не может спасти игру, которая сама по себе пользователю не подходит.

В стандартном диапазоне небольшого превышения бюджета слабая история цены сама по себе не удаляет подходящую игру: сильное вкусовое совпадение до 650 ₽ и умеренное до 550 ₽ могут оставаться в рассылке с решением «ЛУЧШЕ ЖДАТЬ». Зона 650–750 ₽ остаётся исключительной и требует сильного вкусового совпадения и скидки не меньше 75%; выше 750 ₽ предложение исключается.

Для ориентира 60/40 используется явная качественная матрица вместо скрытого числового балла: сильное попадание + «БРАТЬ СЕЙЧАС», сильное + «МОЖНО БРАТЬ», умеренное + «БРАТЬ СЕЙЧАС», сильное + «ЛУЧШЕ ЖДАТЬ», умеренное + «МОЖНО БРАТЬ», умеренное + «ЛУЧШЕ ЖДАТЬ». Wishlist применяется только как дополнительный приоритет внутри одной такой группы.

Итоговая выдача при этом должна быть не набором несортированных групп, а единым строгим порядком от наиболее важной игры к наименее важной. Позиция №1 означает игру, которую пользователь должен увидеть первой. Категории «БРАТЬ СЕЙЧАС / МОЖНО БРАТЬ / ЛУЧШЕ ЖДАТЬ» остаются объясняющими метками и важными признаками, но не заменяют итоговую сортировку. Все факторы финального приоритета — taste-fit, коммерческий verdict/выгодность, wishlist, практическая совместимость, наличие достижений и другие подтверждённые правила — должны приводить к единому месту каждой игры в очереди. Внутри пользовательского интерфейса не должно быть алфавитной или ценовой сортировки, которая маскируется под приоритетную.

Игры за несколько тысяч рублей не нужны в этой системе даже при огромном проценте скидки: задача рассылки — находить хорошие покупки в рамках ограниченного месячного бюджета.

Если точная числовая формула итогового ранжирования ещё не согласована, не придумывать скрытые числовые шкалы. Сохранять все необходимые признаки для последующей финальной логики.

## Wishlist Steam при финальной сортировке

Wishlist используется только после того, как игра уже прошла обычный отбор по вкусу и коммерческим правилам. Нахождение игры в wishlist само по себе не является доказательством вкусового соответствия, не добавляет игру в кандидаты и не позволяет обойти минимальный вкусовой порог, символическую скидку или бюджетный потолок.

Среди уже допустимых кандидатов wishlist даёт заметный бонус к приоритету, потому что пользователь заранее проявил интерес к этой игре. Этот бонус должен быть сильным, но ограниченным: игра из wishlist с явно слабее сочетанием вкуса и текущей выгоды не обязана стоять выше гораздо лучшей покупки вне wishlist. Особенно wishlist не должен автоматически поднимать игру с незначительной скидкой в самый верх.

Wishlist подключается только на этапе конечной сортировки/распределения. Точную числовую прибавку не придумывать без отдельного согласования с пользователем.

## Практическая пригодность покупки

После прохождения вкусового и коммерческого отбора учитывать практическую пригодность игры для пользователя как отдельный фактор финального приоритета.

Совместимость с современным Windows должна влиять на позицию игры. Нельзя автоматически считать игру проблемной только потому, что в старой карточке Steam до сих пор указана Windows XP/7: для старых игр эта строка может быть просто не обновлена. Нужно по возможности оценивать фактическую совместимость с актуальной Windows пользователя. Если игра требует патчей, compatibility mode, ручных исправлений или известна нестабильным запуском на современной Windows, понижать её относительно сопоставимых кандидатов. Если есть подтверждённая серьёзная несовместимость, это должно быть явно видно пользователю.

Наличие Steam-достижений также влияет на финальный приоритет. При прочих близких условиях игра со Steam Achievements предпочтительнее аналогичной игры без достижений. Отсутствие достижений само по себе не исключает хорошую игру, но должно понижать её в списке.

Совместимость и достижения не являются доказательством вкусового соответствия и не должны менять taste-fit. Это отдельные признаки практической ценности покупки после основного отбора.

Точный числовой вес штрафа за отсутствие достижений и за проблемы совместимости пока не придумывать без отдельного согласования с пользователем.

## Нельзя терять игры из-за неполных данных

Если не удалось получить дополнительную информацию, потенциально подходящую игру нельзя исключать только из-за этого.

Особенно это касается даты окончания скидки: её нужно стараться получить и показывать, но если получить не удалось, игра всё равно должна оставаться кандидатом и может попасть в итоговую рассылку.

Общий принцип: отсутствие второстепенной информации должно ухудшать полноту описания, но не приводить к потере потенциально хорошей покупки.

## Срок жизни скидки и кэша

Вкусовая оценка игры и текущее состояние скидки — разные данные. Вкусовую оценку можно хранить и переиспользовать после окончания акции, потому что она не содержит цену, процент скидки или срок акции.

Коммерческие данные обновляются один раз в сутки ночным GitHub-циклом. В течение дня не нужно повторно запрашивать Steam/цены/скидки/отзывы/историю только ради утренней выдачи.

Известный срок окончания скидки можно применять локально без нового сетевого запроса: если сохранённая акция уже закончилась к моменту выдачи, это предложение не показывается. Вкусовая оценка игры при этом сохраняется.

Если скидка появится снова, можно переиспользовать сохранённую вкусовую оценку, но цена, процент скидки и срок акции должны браться из нового суточного снимка.

Вкусовой кэш действителен только для той версии канонического профиля вкуса, на которой он был рассчитан. Если пользователь позже переоценивает игру, уточняет причину своей оценки или новый игровой опыт меняет профиль предпочтений, старые вкусовые verdicts, связанные с предыдущей версией профиля, должны считаться устаревшими и снова попадать на смысловую оценку.

На текущем этапе при любом содержательном изменении канонического профиля безопаснее инвалидировать весь старый вкусовой кэш, а не пытаться угадать, какие конкретно рекомендации затронуты. Это дороже один раз, зато не сохраняет устаревшие выводы о вкусе. В будущем выборочное обновление допустимо только если каждая вкусовая оценка будет надёжно связана с конкретными использованными профильными признаками.

Изменение цены, размера скидки, исторической цены, срока акции или бюджетных правил само по себе не должно инвалидировать вкусовой кэш: это коммерческая логика, а не изменение вкуса пользователя.

## Разделение ночной подготовки и утренней выдачи

Тяжёлая работа выполняется заранее ночью. GitHub собирает один свежий суточный снимок, затем ночная задача ChatGPT завершает нужные смысловые оценки и готовит данные/результат для утра.

Утренняя задача в 08:00 не должна повторно анализировать игры или ходить за новыми коммерческими данными. Она использует уже подготовленный результат.

## Владение production-артефактами

Разные этапы пайплайна не должны удалять или перезаписывать артефакты друг друга. Основной Steam-сборщик владеет только `data/production/manifest.json`, `data/production/shortlist/`, `data/production/freebies.tsv` и `data/production/freebies_index.json`. Он не должен удалять или коммитить `mailing/`, `pre_ai/`, `daily_ready/` и другие downstream-артефакты.

Workflow Steam-сборщика должен коммитить только принадлежащие ему production-пути и падать с ошибкой, если сборщик неожиданно изменил чужой production-артефакт. Это постоянный инвариант надёжности, защищающий ночную цепочку от modify/delete-конфликтов и временного исчезновения подготовленных данных.

## Роль ChatGPT

ChatGPT должен участвовать в смысловой оценке соответствия вкусу и в финальном выборе на основе уже подготовленных технических данных. Технические расчёты, которые можно надёжно подготовить заранее, должны выполняться автоматически, чтобы ускорить работу.

Автоматизация может заранее исключать явно согласованные случаи: не подходящие по вкусу игры, неигровой контент, символическую скидку 5% или меньше и предложения выше абсолютного бюджета 750 ₽. Остальные предложения оцениваются с учётом вкуса и выгодности в пределах бюджетных правил.

## Визуальное представление

Этап оптимизации данных завершён настолько, чтобы визуальную часть развивать непосредственно в рабочей реализации, а не через отдельные одноразовые макеты. Создать постоянную mobile-first веб-страницу, предпочтительно на GitHub Pages или другом постоянном static URL внутри существующего проекта. Дальнейшие визуальные изменения вносить сразу туда: если вариант подходит — он уже остаётся рабочим; если не подходит — править тот же интерфейс, а не переносить затем изменения из отдельного прототипа.

Основное устройство пользователя — телефон. Интерфейс проектировать прежде всего для мобильного Chrome и управления пальцем.

Весь пользовательский текст визуальной витрины должен быть на русском языке. Исключение — собственные названия игр, изданий, наборов и брендов, которые можно оставлять в оригинальном написании. Если источник не даёт русского описания, не показывать пользователю английский текст как замену.

Для каждой платной игры в пользовательском интерфейсе должны быть видны:

- текущая цена в рублях;
- обычная цена без скидки в рублях;
- процент текущей скидки;
- исторический платный минимум в рублях, если он известен; исторический минимум не заменять процентной дельтой;
- срок окончания скидки, если он известен;
- несколько реальных игровых скриншотов, а не один постер;
- краткое понятное описание игрового опыта;
- 1–2 конкретные причины, чем именно механики, структура, сюжетная подача или другой подтверждённый аспект игры совпадает с конкретными предпочтениями пользователя; общая фраза вроде «сильное соответствие вкусу» не считается достаточным объяснением;
- обязательный непустой блок «Риск»: конкретный потенциальный минус именно для пользователя. Если в старом taste-cache нет `negative_evidence`, это не повод оставлять блок пустым — риск нужно отдельно и обоснованно определить по известной структуре игры и каноническому профилю, не выдумывая неподтверждённых свойств;
- ссылка/кнопка открытия страницы покупки в Steam с приоритетом на переход в установленное на телефоне приложение Steam, с веб-fallback при необходимости.

Внутри одной рекомендованной purchase family не скрывать от пользователя другие действительно выгодные варианты покупки. Если отдельно игра, более полное издание, bundle или набор с другими играми серии дают разные разумные варианты ценности, показывать их вместе в карточке и дать пользователю самому выбрать. Это не означает создание нескольких дублирующих рекомендаций одной и той же игры: одна карточка/семья может содержать несколько выгодных вариантов покупки. Не показывать явно бессмысленные или заведомо худшие варианты только ради полноты.

На странице должен быть поиск по названию, чтобы пользователь мог быстро проверить, присутствует ли конкретная игра в текущем активном списке.

Свайп по основной карточке используется только для навигации по уже отсортированной очереди: свайп влево показывает следующую игру, свайп вправо возвращает предыдущую. Сам по себе свайп не меняет статус игры, не помечает её как «Интересно», не отправляет в финал и не перемещает в конец очереди. Все действия, которые меняют состояние или порядок игры («Интересно», «В финал», «В конец очереди»), выполняются только явными отдельными кнопками. Свайп по галерее скриншотов меняет только фотографию и не должен конфликтовать со свайпом основной карточки.

Постоянный интерфейс должен читать подготовленные production-данные и не становиться вторым независимым анализатором рекомендаций. Визуальный слой не должен заново пересчитывать taste-fit, цену, историю или коммерческий verdict.

## Поведение запланированной рассылки

На текущем этапе push- и email-уведомления для задачи рассылки намеренно не нужны и могут оставаться выключенными.

Успешный запланированный запуск должен давать видимый пользовательский результат в связанном с задачей чате/разделе ChatGPT. Нельзя завершать запуск молча: даже если часть данных временно недоступна, нужно показать полезный результат по доступным данным либо коротко сообщить о проблеме, которая не позволила сформировать нормальную подборку.

Формат отображения рассылки в будущем будет дорабатываться отдельно, поэтому текущую логику не привязывать к push-уведомлениям как к обязательному каналу доставки.

## Правила общения с пользователем

Пользователю не нужна техническая внутренняя информация без необходимости. Не перегружать ответы названиями внутренних файлов, форматов, этапов обработки и техническими терминами. Объяснять прежде всего простыми словами: что меняется, зачем это нужно и что это даст.

Чаты быстро достигают лимита контекста, поэтому дополнительно экономить объём общения. Не показывать промежуточные технические результаты, длинные пересказы уже известных правил, диагностические детали и варианты, которые не требуют решения пользователя. Сообщать только то, что реально важно для результата, выявленную проблему/риск или вопрос, который требует согласования. Если действие можно безопасно выполнить в рамках уже подтверждённых правил, выполнить его без лишнего обсуждения.

Если пользователь предлагает решение, не нужно автоматически соглашаться. Сначала оценить его сильные и слабые стороны. Если есть более удачный вариант, прямо предложить его и объяснить почему. Если после этого пользователь всё равно выбирает свой вариант — зафиксировать его как правило.

Спорные логические решения, влияющие на поведение рассылки, не принимать за пользователя без его явного поручения.

Пользователь часто вводит текст голосом. Если смысл сообщения можно уверенно восстановить, не цепляться к ошибкам распознавания. Если из-за голосового ввода возникает реально важная неоднозначность, переспросить.

- цели рассылки;
- правилах отбора;
- приоритетах покупки;
- составе рассылки;
- поведении при нехватке данных;
