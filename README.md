# steam-kz-deals-2

## Быстрый старт нового чата

Если репозиторий уже известен, **не искать его заново и не восстанавливать рабочий контекст из старых чатов**.

### Обязательный порядок

1. **Сначала прочитать `CHAT_PROTOCOL.md`** — короткий обязательный operational contract с gates `START / DURING / PRE-SEND`.
2. Затем прочитать `CHAT_CONTEXT.md` — карту источников истины, ownership, context budget и маршрутов работы.
3. Если пользователь просит продолжить незавершённую работу — прочитать `CURRENT_TASK.md`.
4. До любого широкого поиска по репозиторию проверить релевантный маршрут в `PROJECT_ROUTES.md`.
5. После этого открыть только 1–3 конкретных файла/контракта, которые нужны для текущего шага.
6. `PROJECT_DECISIONS.md` читать только когда нужно понять, почему принято неочевидное решение. Git history читать только если `PROJECT_ROUTES.md` и `PROJECT_DECISIONS.md` не дали ответа.
7. `PROJECT_RULES.md` не читать целиком по умолчанию; открывать только релевантный раздел, когда меняются или проверяются правила отбора, приоритеты, формат рассылки либо архитектурные договорённости.

`CHAT_PROTOCOL.md` является единой точкой для процедурных правил чата. Не полагаться на то, что обязательное правило удастся вспомнить из длинного контекста: перед ответом нужно пройти его `PRE-SEND` gate. В частности, объяснение задержки ответа больше одной минуты и правило интерпретации присланного по просьбе ассистента prompt/log/config теперь живут там как обязательные проверки, а не как независимые копии в README.

Цель такого старта — получить достаточный рабочий контекст за несколько точечных чтений, а не реконструировать проект заново. Repository-wide search, полный просмотр истории коммитов, больших JSON, логов и каталогов до проверки `PROJECT_ROUTES.md` считаются неоптимальным путём по умолчанию.

### Быстрая проверка после изменения canonical contract

Если меняется `version` или структура любого canonical contract/policy, в той же подзадаче сразу найти связанные validation-скрипты/workflow и проверить, нет ли в них явной привязки к предыдущей версии. Не считать изменение завершённым, пока соответствующий validator/CI не прошёл на новом commit. Это особенно важно для `config/steamdb_lookup_contract.json` ↔ `scripts/validate_execution_ownership.py` ↔ `Validate execution ownership`.

### Anti-stall для GitHub Actions и внешних/scheduled workers

Interactive chat не должен тратить минуты на синхронное ожидание внешнего worker-а или повторный polling одного и того же состояния.

- Для одного ожидаемого внешнего события сделать один state check и максимум один повторный check после появления конкретного нового сигнала (новый run/job/commit/submission/state artifact).
- Не вызывать один и тот же `peek`/status endpoint циклом только ради ожидания. После двух безрезультатных попыток остановить polling и сменить метод либо зафиксировать handoff в `CURRENT_TASK.md`.
- Для GitHub Actions вместо постоянного опроса предпочитать точный run → jobs/check/log или уже записанный state artifact.
- Если scheduled ChatGPT/external runtime ещё не дал нового observable result, зафиксировать, что следующий шаг принадлежит owning worker, и не превращать interactive chat в ожидатель или второй production worker.
- Возвращаться к проверке только когда есть новое событие или пользователь снова продолжает работу.

Если подготовка одного ответа всё же заняла больше одной минуты, обязательная процедура находится в `CHAT_PROTOCOL.md -> PRE-SEND`: в этом же ответе разобрать причину задержки и, если ускорение требует безопасного долговечного изменения, сразу улучшить маршрут, индекс, правило или другую точку входа в GitHub. Повтор аналогичной задачи должен требовать существенно меньше навигации.

### Fast path для маленьких web/UI правок

Для пользовательских UI-задач уровня `L1/L2` в `web/*` использовать короткий путь и не строить временный CI-маршрут без необходимости.

- Работать строго с одной выбранной пользователем задачей. Следующую не начинать до его подтверждения результата на опубликованной странице.
- Сначала перечитать только изменяемый `web/*` файл и его текущий blob SHA, затем делать прямой `GitHub.update_file`/`create_file` commit. One-shot workflow для простой правки HTML/CSS/JS запрещён по умолчанию.
- Временный workflow допустим только когда правку нельзя безопасно выполнить прямым file update и действительно нужен shell/runtime validator или многофайловая генерация. Само желание запустить `node --check` не является достаточной причиной усложнять маленькую UI-задачу временным workflow.
- После прямого commit в `web/**` использовать существующий `Deploy visual mailing`. Не создавать второй helper только ради запуска deploy.
- Если `app.js` или `styles.css` изменены, обновить cache-busting query в `web/index.html`, чтобы пользователь не видел старый asset из браузерного кэша.
- Проверять максимум один конкретный deploy run. Не считать задачу закрытой по наличию commit в `main`: финальный критерий — пользователь увидел изменение на реально опубликованной странице и подтвердил его.
- Если работа над одной маленькой задачей пересекла одну минуту, **сразу в этот момент**, не только в финальном ответе, сообщить пользователю: что именно заняло время, была ли ошибка/ожидание и какой более короткий маршрут применяется дальше.

Этот fast path добавлен после повторного случая, когда маленькая UI-правка была неоправданно проведена через временный GitHub Actions workflow, из-за чего YAML-ошибка до создания job и последующий повторный запуск растянули простое изменение больше чем на минуту.

`CHAT_CONTEXT.md` — каноническая компактная карта проекта: источники истины, минимальный набор файлов для разных типов задач, правила контекстной гигиены и архитектурные границы. `CHAT_PROTOCOL.md` — канонический procedural gate для поведения рабочего чата.

Если новая договорённость пользователя меняет поведение рассылки или взаимодействие с ним, сохранить долговечный результат в соответствующем каноническом файле GitHub, а не полагаться на историю чата.
