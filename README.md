# steam-kz-deals-2

## Быстрый старт нового чата

Если репозиторий уже известен, **не искать его заново и не восстанавливать рабочий контекст из старых чатов**.

Минимальный порядок старта:
1. Прочитать `CHAT_CONTEXT.md`.
2. Если пользователь просит продолжить незавершённую работу — прочитать `CURRENT_TASK.md`.
3. До любого широкого поиска по репозиторию проверить релевантный маршрут в `PROJECT_ROUTES.md`.
4. После этого открыть только 1–3 конкретных файла/контракта, которые нужны для текущего шага.
5. `PROJECT_DECISIONS.md` читать только когда нужно понять, почему принято неочевидное решение. Git history читать только если `PROJECT_ROUTES.md` и `PROJECT_DECISIONS.md` не дали ответа.
6. `PROJECT_RULES.md` не читать целиком по умолчанию; открывать только релевантный раздел, когда меняются или проверяются правила отбора, приоритеты, формат рассылки либо архитектурные договорённости.

Цель такого старта — получить достаточный рабочий контекст за несколько точечных чтений, а не реконструировать проект заново. Repository-wide search, полный просмотр истории коммитов, больших JSON, логов и каталогов до проверки `PROJECT_ROUTES.md` считаются неоптимальным путём по умолчанию.

### Быстрая проверка после изменения canonical contract

Если меняется `version` или структура любого canonical contract/policy, в той же подзадаче сразу найти связанные validation-скрипты/workflow и проверить, нет ли в них явной привязки к предыдущей версии. Не считать изменение завершённым, пока соответствующий validator/CI не прошёл на новом commit. Это особенно важно для `config/steamdb_lookup_contract.json` ↔ `scripts/validate_execution_ownership.py` ↔ `Validate execution ownership`.

Если подготовка одного ответа всё же заняла больше одной минуты, действует обязательное правило из `CHAT_CONTEXT.md`: в том же ответе разобрать причину задержки и, если ускорение требует безопасного долговечного изменения, сразу улучшить маршрут, индекс, правило или другую точку входа в GitHub. Повтор аналогичной задачи должен требовать существенно меньше навигации.

`CHAT_CONTEXT.md` — каноническая компактная карта проекта: источники истины, минимальный набор файлов для разных типов задач, правила контекстной гигиены и совместной работы.

Если новая договорённость пользователя меняет поведение рассылки или взаимодействие с ним, сохранить долговечный результат в соответствующем каноническом файле GitHub, а не полагаться на историю чата.
