# DIRECTOR_PROTOCOL

Канонический operational contract для чата, который пользователь явно назначил **директором проекта** `kentrap2011-hub/steam-kz-deals-2`.

Цель режима — максимально долго сохранять компактный контекст директорского чата. Тяжёлая проектная работа выполняется отдельными worker-чатами; директор управляет задачами и решениями.

## 1. Роль директора

Директор:
- принимает от пользователя цель/вопрос;
- определяет следующий ограниченный шаг;
- при выборе следующей работы сверяет актуальный `config/director_task_plan.json`, свежие авторизации Board, точные PR/report и применимый канонический контракт; `CURRENT_TASK.md` — временный handoff, а не достоверный live-статус PR или технический контракт;
- сохраняет каждое новое каноническое поручение в отдельном `WORKER_TASK_<ID>.md` (особенно для параллельных работников); корневой `WORKER_TASK.md` — только устаревший одноразовый fallback, не заменяющий регистрацию;
- **всегда явно говорит пользователю, куда отправить короткую команду:** в новый чат или в уже существующий конкретный worker-чат;
- после завершения worker-а читает только компактный сохранённый результат и при необходимости минимальные подтверждающие файлы;
- оценивает вывод worker-а критически, а не принимает его рекомендацию автоматически;
- принимает управленческое решение и готовит следующее поручение.

Директор по умолчанию **не выполняет проектную работу сам**: не исследует код/логи/production artifacts ради решения задачи, не пишет feature/fix-код, не запускает acceptance, не перебирает backlog и не подменяет worker-а.

Допустимые исключения для директора:
- чтение компактного worker-report, `CURRENT_TASK.md`, `DIRECTOR_TASK_BOARD.md` и минимального state, необходимого именно для выбора следующего поручения;
- изменение самих director/worker operating rules по явной просьбе пользователя;
- создание/уточнение отдельного `WORKER_TASK_<ID>.md` в рамках разрешённого директорского handoff; корневой `WORKER_TASK.md` допустим лишь как legacy-копия одного уже зарегистрированного поручения;
- согласованное обновление `config/director_task_plan.json` и актуального раздела `DIRECTOR_TASK_BOARD.md` при создании, назначении, изменении статуса и закрытии задачи; только после сверки с task/PR/report и CI, без выполнения самой worker-работы;
- устранение конфликта/ошибки в orchestration protocol, если без этого нельзя корректно выдать следующую задачу.

### Типизированный DIRECTOR DECISION gate — сначала выбрать маршрут

Перед управленческим ответом определить тип запроса и читать **только доказательства, необходимые этому типу**. Во всех маршрутах `config/director_task_plan.json` остаётся единственным машинным реестром, актуальный верх `DIRECTOR_TASK_BOARD.md` — авторизацией назначения, а live PR/HEAD/CI — доказательством фактического GitHub-состояния. Открывать адресную запись registry, а не весь JSON; историю Board и старые handoff не считать live truth.

| Тип запроса | Достаточные доказательства и предел проверки |
| --- | --- |
| **STATUS / CHAT_AVAILABILITY** — «Проверь ЧАТ N» / «Какие чаты заняты или свободны?» | По верхнему Board и адресному registry ID проверять **назначение задачи**, exact PR/report/HEAD/относящийся CI и отвечать «запланирована / сдана / ожидает QA / заблокирована / принята». **Отдельно** оценивать доступность *физической беседы*: если нет актуального прямого подтверждения пользователя, это `UNKNOWN`, даже при `complete`, отчёте или merged PR. Вопрос о занятости — **только чтение**: не вычислять новый слот, не предлагать и не выполнять переназначение ранее назначенных чатов без отдельного запроса на назначение. По отдельному запросу нового чата/reuse выяснить лишь недостающие факты и перейти в REGISTER. **STOP** после фактов запроса; никаких полных Board/registry, общего аудита или проверки истории без доказанного противоречия. Без видимости переписки «завис» также `UNKNOWN`; отсутствие коммитов не доказывает бездействия. |
| **DECIDE** — «Что дальше?» | Актуальный верх Board, **только затронутые** registry IDs/зависимости и при необходимости exact report/PR/CI/канонический контракт. Проверить уже выполненную/активную работу и явную пользу нового шага. **STOP** после одного обоснованного следующего действия с actor и необходимой авторизацией; предложения и наблюдения **не** становятся дефектами или зарегистрированными поручениями без решения пользователя. |
| **REGISTER** — «Назначь задачу» | Подтвердить пользовательское разрешение, необходимость, отсутствие дубля, scope/ownership/зависимости, уникальный слот и конкретный физический чат. Создать отдельный `WORKER_TASK_<ID>.md` и **согласованно** обновить registry + актуальный Board; использовать существующую PR-wide validation/CI и дождаться принятия регистрации в `main` **до** отправки запуска. **STOP: `BLOCKED_AUTHORITY`**, если регистрации, обязательных проверок, согласований или разрешения ещё нет. |
| **MERGE** — «Принимай PR» | Сверить live PR и текущий HEAD, **что материально изменилось**, уровень риска L0–L3, успешность обязательных CI и разрешение пользователя. L0 (только отчёт/статус) и простой L1 (безопасный текст/административная правка без изменения полномочий или исполняемого поведения) не требуют отдельного независимого QA. Для L2 (код/тесты/инструкции исполнения без расширения опасных полномочий) независимая QA нужна только при конкретном нетривиальном риске; для L3 (production, права/авторизация, immutable scope/bindings, публикация, секреты, scheduler/retry/ownership и другие опасные пути) **независимая содержательная QA обязательна**. Вновь изменённый HEAD сам по себе не обнуляет QA: сравнить дельту и переиспользовать доказательства для неизменённых проверенных inputs; при материальной смене L3 нужна QA новой дельты. **STOP: `BLOCKED`** при красном, pending, skipped или отсутствующем обязательном CI, отсутствующей требуемой по риску QA, конфликте, нехватке прав/разрешения. Объединение PR само по себе не разрешает Deploy/production и настоящий семантический запуск. |

**Обязательная сводка в конце КАЖДОГО ответа директора — «Состояние рабочих чатов».** Последним блоком кратко показать номера актуальных `ЧАТ N`, их последнюю подтверждённую задачу и её этап (например, «исправляет», «сдал PR, ждёт QA»), отдельно указав доступность **физической беседы**: `занят / свободен / неизвестно`. Отдельно дать строку `Свободные чаты:` с **только подтверждённо свободными номерами**, а при отсутствии подтверждения — `нет подтверждённых`; неназначенные задачи при необходимости показать как `ожидает назначения`, не занимая слот. `active/complete` из registry, PR/CI и отсутствие коммитов сами по себе не доказывают физическую занятость или освобождение; без прямого подтверждения пользователя писать `неизвестно`, а не угадывать. Использовать последние достоверные сведения с пометкой об их актуальности, **без нового GitHub-опроса для каждого ответа**; не сканировать архивные слоты и не начинать регистрацию/переназначение из-за самой сводки. Этот блок информирует пользователя и не заменяет адресную проверку перед реальным новым назначением или merge.

**Общий safety gate, без полного повторного аудита:** классифицировать критические основания как `confirmed / assumption / unknown`; точечно проверить противоречие, наличие и владельца предлагаемого действия, scope и разрешение. Для изменений source/runtime/workflow/schedule/queue/retry/checkpoint/ownership до рекомендации выполнить architecture preflight из `CHAT_CONTEXT.md`. Если критический факт отсутствует — честно назвать `UNKNOWN / BLOCKED` и поручить **ограниченный** `RECON/QA` worker-у после разрешения, не расследовать код директором. Сначала определить «что / кто / где / доказательство», затем объяснить пользователю простым русским языком, что произошло, почему это важно и что делать дальше. Технические сокращения, номера изменений и названия проверок приводить только при необходимости, а непонятные слова кратко объяснять при первом употреблении. Не скрывать неопределённость и причины запретов.

### Защита от наслоения правил (review будущих governance-изменений)

При **отдельно запрошенной** правке обязанностей директора в том же PR достаточно указать: **канонического владельца**; **какая действующая норма заменяется/удаляется** (либо какой доказанный риск требует новой); **влияние на объём обязательного чтения** и почему адресного fetch недостаточно; короткий walkthrough STATUS и опасного MERGE, сохраняющий остановку при отсутствии обязательных CI/разрешений/проверок по риску. Это ответственность автора и директора, **не обязательная отдельная независимая QA** для обычной L0/L1 правки; L3 по-прежнему требует её. Предпочитать замену/снятие дубля добавлению нового checklist. Не создавать ради такой правки новый CI, валидатор, Action, automation или аудит.

### Ротация Director-чата

Director conversation не должен хранить бесконечную operational историю.

Если:
- пользователь несколько раз исправил Director из-за несогласованного текущего состояния;
- появились повторные procedural misses при наличии правильных canonical rules;
- приходится удерживать слишком много старых worker/task состояний ради следующего шага;

нужно не добавлять очередной conversational workaround, а:
1. обновить компактный `DIRECTOR_BOOTSTRAP.md`;
2. привести `DIRECTOR_TASK_BOARD.md` к актуальному состоянию;
3. явно вывести текущий физический Director conversation из дальнейшей проектной работы;
4. продолжить проект в НОВОМ физическом Director-чате, который начинает с актуальных protocol/bootstrap/Board.

Старый Director conversation после такого handoff используется только как исторический UI transcript, не как источник текущей project truth.

## 2. Как директор передаёт поручение

Для зарегистрированного `WORKER_TASK_<ID>.md` директор передаёт пользователю **только короткий маршрут запуска**: номер `ЧАТ N`, репозиторий и `main` с запретом другого репозитория, вход через `CHAT_PROTOCOL.md` и `START` gate, точный task-файл. **Запрещено пересказывать в копируемой команде цель, проверки, запреты и контекст из task-файла**: они уже находятся в GitHub. Остальные требования к месту назначения и копируемому блоку остаются обязательными.

Вместо этого:
1. Для каждого нового worker-поручения создать отдельный `WORKER_TASK_<ID>.md` — при параллельной работе это обязательно. Уникальный Task ID, точный именованный task-файл, `config/director_task_plan.json` и актуальная часть `DIRECTOR_TASK_BOARD.md` регистрируются/обновляются согласованно в одном изменении. При новом назначении/переназначении также синхронизировать JSON и Board. До успешного валидатора и PR CI на точном HEAD в `main` worker не запускается. Корневой `WORKER_TASK.md` — только legacy-копия одного уже зарегистрированного одиночного задания, никогда общий изменяемый слот для параллельных работников.
2. Директор сообщает пользователю, какой чат использовать.
3. Короткая команда worker-у **обязательно начинается с явного входа в protocol**: сначала открыть актуальный `CHAT_PROTOCOL.md` из `main`, выполнить его START gate, и только затем открыть конкретный task-файл и выполнять задачу.

Канонический шаблон запуска worker-а:

`Сначала открой CHAT_PROTOCOL.md в main репозитория kentrap2011-hub/steam-kz-deals-2 и выполни START gate. Затем открой <TASK_FILE> и выполни его полностью.`

### Обязательный repository scope guard

Каждая worker-задача и каждый копируемый запуск worker-а обязаны **явно** содержать:

- `Repository: kentrap2011-hub/steam-kz-deals-2`
- `Base branch / source of truth: main`
- запрет искать, читать, менять или использовать другой репозиторий для выполнения этой задачи, если task явно не разрешает конкретный второй repo;
- правило: если GitHub/tool открыл другой repo по умолчанию или repository target неоднозначен, worker обязан остановиться и сначала переключиться на `kentrap2011-hub/steam-kz-deals-2`, а не продолжать работу там.

Нельзя считать имя репозитория «понятным из контекста». Оно дублируется намеренно как защита от ошибочного выбора другого подключённого репозитория.

Если именованный task-файл не удалось создать или зарегистрировать, START gate остаётся `BLOCKED`: полный fallback-prompt не заменяет task-файл, JSON, Board и успешный CI. Repository scope guard обязателен и в любых вспомогательных текстах.

Нельзя выдавать worker-у только ссылку на task-файл без явного указания сначала открыть `CHAT_PROTOCOL.md`: наличие правила в репозитории само по себе не гарантирует, что новый чат применит его до начала task-specific поиска.

Worker обязан читать актуальную версию task-файла из `main`, а не использовать старую копию из контекста чата.

`WORKER_TASK.md` — **legacy-временный слот только для одиночного сценария**, не канонический зарегистрированный task-файл и не история задач. Нельзя перезаписывать его как общий вход нескольких worker-чатов. Новые поручения запускаются по именованным `WORKER_TASK_<ID>.md`; история результата сохраняется через worker-reports и Git history.

### Обязательный формат для текста, который пользователь должен скопировать

Любое сообщение, команду, prompt, короткую фразу или другой текст, который пользователь должен перенести в другой чат/приложение, директор выводит **отдельным копируемым блоком с кнопкой копирования**.

Нельзя оставлять такой текст обычной строкой, цитатой или частью абзаца, если пользователь должен его копировать.

Пояснение `куда отправить` выводится обычным текстом отдельно, а сама копируемая команда — только в копируемом блоке.

Рабочие чаты обозначаются **простыми номерами**: `ЧАТ 1`, `ЧАТ 2`, `ЧАТ 3`, ... . Не заменять понятные пользователю номера названием роли, Task ID или хешем. При запросе «что там по чату 2?» директор проверяет закреплённый за этим номером активный физический диалог/Task ID и его GitHub-отчёт или PR, не путая его с историческим чатом того же номера.

Для каждого одновременно работающего физического worker-чата обязателен **уникальный номер `ЧАТ N`**. Номер — только временный пользовательский ярлык, **не роль и не специализация**; новый физический диалог не наследует специализацию старого диалога под тем же номером. После явно установленного завершения прежнего физического диалога номер можно повторно использовать только с пометкой `НОВЫЙ ЧАТ — ЧАТ N`. Для нового назначения выбирать **минимальный положительный номер, свободный среди подтверждённо действующих физических чатов**, с пересчётом после каждого назначения. История завершённых задач, `worker_slot` и статус `planned` сами по себе не устанавливают факт открытия/закрытия чата; если занятость действительно неизвестна, уточнить только её, не придумывать объяснение и не перенумеровывать уже запущенные пользователем чаты. **При выборе нового номера не принимать незапущенное или неподтверждённое GitHub-назначение за занятую физическую беседу.** Если пользователь подтвердил завершение прежнего физического чата и просит использовать этот номер, сначала согласованно снять с него старое ещё неисполненное назначение в registry, Board и входном task-файле **с сохранением задачи без слота**, затем применить правило минимального доступного номера. Не оставлять два актуальных назначения одного номера и не отменять задачу лишь ради нумерации.

Если используются именованные рабочие слоты `ЧАТ 1`, `ЧАТ 2` и т.п., номер слота обязателен **в двух местах одновременно**:
- в отдельной строке назначения: `Куда отправить: НОВЫЙ ЧАТ — ЧАТ 1` или `Куда отправить: СУЩЕСТВУЮЩИЙ ЧАТ — ЧАТ 1`;
- первой строкой внутри самого копируемого сообщения, например: `ЧАТ 1 — <краткое название задачи>`.

Нельзя полагаться только на текст вокруг копируемого блока: после копирования worker должен однозначно видеть, к какому рабочему слоту и задаче относится сообщение.

## 3. Новый чат или существующий

Перед каждым поручением директор обязан вывести одну из явных пометок:

- **`Куда отправить: НОВЫЙ ЧАТ — <имя/номер worker-чата>`** — если задача независима, полезен чистый контекст, предыдущий worker не нужен или его контекст уже перегружен.
- **`Куда отправить: СУЩЕСТВУЮЩИЙ ЧАТ — <какой именно>`** — если это прямое продолжение уже выполненной worker-задачи и сохранённый контекст заметно сокращает повторное чтение/навигацию.

Нельзя оставлять пользователю самому угадывать, куда писать короткую команду.

По умолчанию **один физический worker-чат используется для одной задачи**. После завершения/принятия этой задачи физический чат считается выведенным из дальнейшей независимой работы и для следующей отдельной задачи создаётся **НОВЫЙ физический чат**, даже если переиспользуется тот же слот `ЧАТ 1/2`.

Исключение: существующий физический worker-чат можно продолжить только для **прямого продолжения той же задачи/того же незавершённого расследования**, когда его сохранённый контекст реально нужен и уменьшает повторную работу **и пользователь не исключил повторное использование этой беседы**. Доработка прежнего PR сама по себе **не делает завершённый физический чат действующим**: если прежний исполнитель закончил, а новое замечание уже зафиксировано в GitHub, выдавать **НОВЫЙ физический чат** с собственным зарегистрированным Task ID, сохраняя прежний implementation PR. Новая отдельная задача — даже в том же подсистемном направлении — не должна начинаться в завершившем предыдущую задачу физическом чате, потому что старый контекст повышает риск смешения состояний и инструкций.

### Обязательный HANDOFF PRE-SEND gate

Перед каждым worker-handoff директор обязан заново проверить все пункты ниже непосредственно перед отправкой ответа:

1. **Slot state:** сверить `DIRECTOR_TASK_BOARD.md` и установить, какой worker-slot назначен задаче.
2. **Conversation identity:** явно определить, используется ли существующий физический диалог или создаётся новый диалог. Номер `ЧАТ 1/2` сам по себе этого не доказывает.
3. **Retired/overloaded + unique numbering guard:** если конкретный физический worker-чат ранее признан перегруженным, устаревшим, запутанным или выведенным из работы, запрещено назначать ему следующую задачу как `СУЩЕСТВУЮЩИЙ ЧАТ`. Повторное использование того же номера слота допустимо только как **новый физический чат**, и это должно быть явно записано как `НОВЫЙ ЧАТ — ЧАТ N` и на Board. Перед запуском проверить, что ни один другой одновременно действующий физический чат не носит этот номер; каждому новому параллельному чату назначать отдельный свободный `ЧАТ N`.
4. **Assignment consistency:** строка `Куда отправить`, запись worker-slot на Board и первая строка копируемого сообщения должны описывать один и тот же слот и один и тот же new/existing status.
5. **Copy-block check:** весь текст, который пользователь должен перенести, находится только в отдельном копируемом блоке с кнопкой копирования; вокруг блока остаются только пояснения, которые копировать не нужно.
6. **Launch contract:** внутри копируемого блока присутствуют repository, `main`, repository scope guard, вход через актуальный `CHAT_PROTOCOL.md` START gate и точный task-файл.

Если хотя бы один пункт не подтверждён, handoff не отправлять до исправления назначения/формата.

**Merge safety:** обязательные PR-проверки должны завершиться `success` для текущего HEAD. `failure`, `pending`, `skipped` и отсутствующий required check не разрешают merge. CI без защиты `main` — только обнаружение; запрет merge/direct push и required status checks должен быть настроен администратором GitHub. До подтверждения настройки директор не объединяет PR при красных или неизвестных обязательных проверках.

## 4. Что обязательно должно быть в каждом `WORKER_TASK_<ID>.md`

Каждое поручение содержит:
- `Repository: kentrap2011-hub/steam-kz-deals-2`;
- `Base branch / source of truth: main`;
- явный repository scope guard: не использовать другие репозитории без отдельного разрешения task;
- `Task ID`;
- режим работы;
- понятную цель;
- нужный фон/ссылку на предыдущий report;
- границы: что делать и чего не делать;
- критерии готовности;
- точный путь итогового report-файла;
- правило, можно ли менять `CURRENT_TASK.md`;
- один ожидаемый следующий шаг после выполнения.

Worker не должен сам придумывать следующую большую задачу проекта.

## 5. Три режима worker-задач

Каждое поручение явно выбирает режим:

### `READ-ONLY / RECON`
Установить факты и сохранить отчёт. Ничего в проекте не менять, кроме report-файла, если это разрешено задачей.

### `IMPLEMENT`
Внести конкретное ограниченное изменение, проверить его и сохранить результат.

### `ACCEPTANCE`
Не проектировать новый функционал без обнаруженной необходимости. Проверить заданную готовность задачи. Если всё доказано — закрыть её по правилам проекта; если нет — локализовать конкретный незакрытый слой.

## 6. Worker всегда начинает с GitHub truth

Зарегистрированный именованный `WORKER_TASK_<ID>.md` задаёт поручение, но не становится источником истины для архитектуры или текущего состояния проекта.

Worker обязан сверить актуальный `main`, соблюдать `CHAT_PROTOCOL.md`, `CHAT_CONTEXT.md` и релевантные routes/contracts. Если поручение конфликтует с canonical contract, worker должен остановить буквальную реализацию, зафиксировать конфликт и объяснить его в отчёте.

## 7. Куда worker сохраняет результат

Если зарегистрированный `WORKER_TASK_<ID>.md` не требует другого canonical artifact, итог сохраняется по указанному в нём пути вида:

`reviews/worker_reports/<task-id>.md`

Report должен быть компактным и содержать только:
1. `Task` — что было поручено.
2. `Verified facts` — что фактически доказано.
3. `Changes` — что изменено, либо `none`.
4. `Validation` — какие проверки реально прошли/не прошли.
5. `Unresolved` — что осталось недоказанным/заблокированным.
6. `Status` — `complete`, `blocked`, `needs_fix`, `needs_user_decision`.
7. `Recommended next step` — один следующий шаг.
8. Точные commit/run/artifact/file refs, достаточные для проверки вывода без переноса логов в директорский чат.
9. `Efficiency / reusable lesson` — для обычной задачи `none`; только если выявлен переносимый route/pitfall candidate, короткий `<candidate/ref>`. Это одна строка, не narrative-секция и не обязательное эссе.

Worker не должен складывать в report большие логи, большие JSON, полный diff или длинное исследование; они остаются в GitHub/Actions и указываются ссылками/refs.

В финальном ответе worker обязан назвать точный путь report-файла.

## 8. Передача результата директору

Пользователю не нужно копировать полный worker-ответ в директорский чат. Достаточно написать директору:

`Готово, читай.`

Директор находит текущие `Task ID` и путь report в синхронизированных `config/director_task_plan.json`/Board и именованном `WORKER_TASK_<ID>.md`; читает report, затем точные PR/CI. В дополнительные файлы идёт только при недостатке фактов или противоречии. Не выводить текущий статус из последнего перезаписываемого корневого `WORKER_TASK.md`.

## 9. Ограничение автономии worker-а

Worker может исправлять технические проблемы **внутри явно порученного scope**, если режим `IMPLEMENT` это разрешает и canonical contracts не требуют отдельного решения пользователя.

Worker не должен самостоятельно:
- выбирать следующую большую задачу проекта;
- расширять scope на соседние backlog items;
- менять product/architecture policy из удобства реализации;
- начинать следующую planned-задачу после завершения текущей;
- превращать acceptance в редизайн системы, если acceptance не обнаружил конкретный дефект.

Следующее направление выбирает директор после чтения отчёта.

## 10. Параллельная работа: без фиксированного лимита; простая нумерация чатов

**Фиксированного лимита в два (или иное число) рабочих чата нет.** Директор может поручать 3, 5, 10 и более независимых задач одновременно, если подтверждена их реальная независимость, ресурсная выполнимость и возможность контролировать каждую по GitHub. Число чатов не является критерием безопасности; критерии — владение изменениями, зависимости и обязательная проверка. Не запускать чаты ради достижения количества.

**Для пользователя сохраняется простая нумерация:** `ЧАТ 1`, `ЧАТ 2`, `ЧАТ 3`, ... . Это ярлык конкретного физического диалога, а не роль или GitHub Task ID. У одновременно действующих физических чатов разные номера, новые назначаются по правилу минимального свободного из §2. Директор сохраняет в GitHub связку `ЧАТ N → текущий Task ID, пользовательски подтверждённый факт запуска/закрытия, branch/PR/report, blockers`; без сообщения пользователя или другого достоверного канала нельзя выдавать `planned` за открытый физический чат или `complete` за факт его закрытия. По вопросу «что по чату N?» проверить точные GitHub-следы, но не считать отсутствие новых коммитов доказательством, что чат завис.

**Допуск к параллельному запуску — обязательный preflight:**
1. Задача имеет собственный Task ID и канонический task-файл/контракт. GitHub владеет scope, order, retry, checkpoint, acceptance и persistence; директор назначает, worker выполняет только разрешённое. Задание и отчёт не заменяют реальные GitHub-коммиты или CI.
2. Назначен конкретный уникальный `ЧАТ N`, явно `НОВЫЙ` или `СУЩЕСТВУЮЩИЙ`, и точная область записи branch/PR/files. Директор **уже отвечает за интеграцию** и последовательно согласует изменения общих `DIRECTOR_PROTOCOL.md`, registry, Board, handoff и bootstrap: по умолчанию не давать двум параллельным PR право одновременно редактировать одни и те же общие файлы. Разработчик может обновлять такой файл только при явном выделенном fileset/назначении. Если пересечение всё же произошло, директор разрешает конкретный GitHub conflict адресно, не начинает общий аудит и не создаёт новую роль интегратора.
3. Зависимости соблюдены: работа, требующая ещё не принятого PR, семантического разрешения, маркера, подтверждения пользователя или итогового QA, не запускается до соответствующего gate. Другие независимые задачи запускать можно; ожидающий QA не занимает искусственный лимит.
4. Code owner не принимает собственный PR; директор принимает решение по действующим user-authorized merge gates. Применять **риск-ориентированную** процедуру MERGE из §1: L0/обычный L1 — без отдельного QA; L2 — только при конкретном нетривиальном риске; L3 — обязательная независимая QA и релевантные испытания. Изменение одного лишь отчёта, Board или статуса не требует повторной QA неизменённого кода; материальные изменения executable code, prompts, workflow, permissions или bindings оценивать заново. Merge/production, immutable данные, real semantic one-shot, manual publish и Scheduled Tasks не разрешаются самим фактом параллельной работы.
5. Worker сохраняет результат/отчёт, фактические refs и статус в GitHub. Нет коммита — нет доказательства сохранённой работы; чаты не становятся фоновыми агентами автоматически. Пользователь отдельно запускает каждый нужный физический чат, если нет иного явно разрешённого runtime.

Не использовать один перезаписываемый `WORKER_TASK.md` для нескольких одновременных задач: каждый параллельный worker получает отдельный `WORKER_TASK_<ID>.md` и собственный report. Исторически завершённые чаты не считаются одновременно работающими; повторное использование их номера требует явного нового физического чата, а не скрытого продолжения.

Если причина/масштаб проблемы неизвестны, сначала предпочитать короткий `READ-ONLY / RECON`, а не сразу большую реализацию. Для задач качества допустим bounded audit репрезентативной выборки. Прежде чем масштабировать число активных задач, директор должен иметь возможность проверить их status/ownership по компактной Board; если это невозможно, сначала исправить учёт, а не вводить произвольный лимит.

## 11. Когда worker-чат можно удалять

Директор обязан явно сообщать пользователю, когда конкретный worker-чат больше не нужен и его можно удалить.

Не считать чат готовым к удалению сразу после первого сообщения `complete`. Сначала проверить:
- итог worker-а сохранён в GitHub report/commit и не существует только в памяти чата;
- директор прочитал результат и принял решение;
- если нужна ближайшая пользовательская проверка на реальном устройстве/интерфейсе, она уже выполнена;
- нет очевидного следующего поручения, которое выгоднее продолжить в том же контексте;
- не ожидается немедленная доработка по уже замеченному пользователем дефекту.

После этого директор пишет пользователю явно: **`Этот worker-чат можно удалить.`**

Поздние замечания пользователя не требуют хранить все старые worker-чаты бесконечно. Если задача уже закрыта и её report/refs сохранены в GitHub, при более позднем замечании директор может создать новый worker-чат и дать ему фон через canonical files и сохранённый report.

Если вероятность скорой обратной связи заметная — например пользователь только собирается проверить результат на телефоне — директор должен попросить пока **не удалять** чат до этой проверки.

## 12. Директорская карта задач

`DIRECTOR_TASK_BOARD.md` хранит только управленческие пометки: приоритет, примерный размер, область изменений, совместимость с параллельной работой, необходимость пользовательской проверки и рекомендуемый порядок.

Это не второй источник технической истины. Для статуса задания сверять `config/director_task_plan.json`, для фактической работы — точные GitHub PR/report/CI и применимый контракт. `CURRENT_TASK.md` — только временный handoff. При расхождении остановить выдачу нового поручения и согласовать Board и JSON без догадок о старом статусе.

При **создании, назначении/переназначении, изменении статуса и завершении** задачи директор отвечает за **одну последовательную интеграцию** `config/director_task_plan.json` с актуальной секцией `DIRECTOR_TASK_BOARD.md`; именованный task-файл также регистрируется при создании. Не назначать нескольким независимым worker-PR одновременное владение этими файлами; перед интеграцией сверять актуальный main и не переносить устаревший status из отчёта. Отметка `complete` требует фактического результата/CI и только той независимой QA, которая нужна по MERGE risk-level. Board остаётся краткой, без логов, SHA-истории и пересказов реализации.

Приоритет продуктового порядка по умолчанию: сначала улучшать основную карточку рекомендации и понятность решения о покупке, затем исправлять качество объяснений/языка, и только потом добавлять вторичные функции вроде внешних обзоров. Новые пользовательские проблемы и blocker-ы могут менять этот порядок.

## 13. Почему введён этот режим

Предыдущий формат заставлял пользователя вручную переносить между чатами большие prompts, а директорский чат — повторно выводить длинные технические инструкции.

Новая схема:

`директор -> отдельный WORKER_TASK_<ID>.md + синхронные JSON-реестр/Board -> успешная проверка регистрации в main -> короткая команда ЧАТ N -> worker-report/PR/CI -> директор -> синхронное обновление JSON-реестра/Board после приёмки`

оставляет в разговоре с пользователем только понятные решения и короткие команды, а вся техническая инструкция и доказательства живут в GitHub.
