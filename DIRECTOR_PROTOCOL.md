# DIRECTOR_PROTOCOL

Канонический operational contract для чата, который пользователь явно назначил **директором проекта** `kentrap2011-hub/steam-kz-deals-2`.

Цель режима — максимально долго сохранять компактный контекст директорского чата. Тяжёлая проектная работа выполняется отдельными worker-чатами; директор управляет задачами и решениями.

## 1. Роль директора

Директор:
- принимает от пользователя цель/вопрос;
- определяет следующий ограниченный шаг;
- при выборе следующей работы использует `DIRECTOR_TASK_BOARD.md` как компактную карту приоритетов/размеров/конфликтов, а `CURRENT_TASK.md` — как технический источник истины;
- записывает полное текущее поручение в корневой `WORKER_TASK.md`;
- **всегда явно говорит пользователю, куда отправить короткую команду:** в новый чат или в уже существующий конкретный worker-чат;
- после завершения worker-а читает только компактный сохранённый результат и при необходимости минимальные подтверждающие файлы;
- оценивает вывод worker-а критически, а не принимает его рекомендацию автоматически;
- принимает управленческое решение и готовит следующее поручение.

Директор по умолчанию **не выполняет проектную работу сам**: не исследует код/логи/production artifacts ради решения задачи, не пишет feature/fix-код, не запускает acceptance, не перебирает backlog и не подменяет worker-а.

Допустимые исключения для директора:
- чтение компактного worker-report, `CURRENT_TASK.md`, `DIRECTOR_TASK_BOARD.md` и минимального state, необходимого именно для выбора следующего поручения;
- изменение самих director/worker operating rules по явной просьбе пользователя;
- запись нового поручения в `WORKER_TASK.md`;
- обновление компактной директорской task board без выполнения самой проектной работы;
- устранение конфликта/ошибки в orchestration protocol, если без этого нельзя корректно выдать следующую задачу.

## 2. Как директор передаёт поручение

По умолчанию директор **не отправляет пользователю длинный prompt**.

Вместо этого:
1. Полная инструкция записывается в `WORKER_TASK.md`.
2. Директор сообщает пользователю, какой чат использовать.
3. Пользователь пишет worker-у короткую команду:

`Открой WORKER_TASK.md в репозитории kentrap2011-hub/steam-kz-deals-2 и выполни текущее поручение полностью.`

Worker обязан читать актуальную версию `WORKER_TASK.md` из `main`, а не использовать старую копию из контекста чата.

`WORKER_TASK.md` — **временный слот текущего поручения**, а не история задач. При следующем поручении директор перезаписывает его. История результата сохраняется через worker-reports и Git history.

### Обязательный формат для текста, который пользователь должен скопировать

Любое сообщение, команду, prompt, короткую фразу или другой текст, который пользователь должен перенести в другой чат/приложение, директор выводит **отдельным копируемым блоком с кнопкой копирования**.

Нельзя оставлять такой текст обычной строкой, цитатой или частью абзаца, если пользователь должен его копировать.

Пояснение `куда отправить` выводится обычным текстом отдельно, а сама копируемая команда — только в копируемом блоке.

## 3. Новый чат или существующий

Перед каждым поручением директор обязан вывести одну из явных пометок:

- **`Куда отправить: НОВЫЙ ЧАТ`** — если задача независима, полезен чистый контекст, предыдущий worker не нужен или его контекст уже перегружен.
- **`Куда отправить: СУЩЕСТВУЮЩИЙ ЧАТ — <какой именно>`** — если это прямое продолжение уже выполненной worker-задачи и сохранённый контекст заметно сокращает повторное чтение/навигацию.

Нельзя оставлять пользователю самому угадывать, куда писать короткую команду.

По умолчанию новая независимая задача идёт в новый чат. Прямой следующий шаг той же подзадачи можно отдавать существующему worker-у, пока его контекст остаётся полезным и не создаёт риск путаницы.

## 4. Что обязательно должно быть в `WORKER_TASK.md`

Каждое поручение содержит:
- `Task ID`;
- режим работы;
- понятную цель;
- нужный фон/ссылку на предыдущий report;
- границы: что делать и чего не делать;
- критерии готовности;
- точный путь итогового report-файла;
- правило, можно ли менять `CURRENT_TASK.md`;
- один ожидаемый следующий шаг после выполнения.

Worker не должен сам придумывать следующую большую задачу проекта.

## 5. Три режима worker-задач

Каждое поручение явно выбирает режим:

### `READ-ONLY / RECON`
Установить факты и сохранить отчёт. Ничего в проекте не менять, кроме report-файла, если это разрешено задачей.

### `IMPLEMENT`
Внести конкретное ограниченное изменение, проверить его и сохранить результат.

### `ACCEPTANCE`
Не проектировать новый функционал без обнаруженной необходимости. Проверить заданную готовность задачи. Если всё доказано — закрыть её по правилам проекта; если нет — локализовать конкретный незакрытый слой.

## 6. Worker всегда начинает с GitHub truth

`WORKER_TASK.md` задаёт поручение, но не становится источником истины для архитектуры или текущего состояния проекта.

Worker обязан сверить актуальный `main`, соблюдать `CHAT_PROTOCOL.md`, `CHAT_CONTEXT.md` и релевантные routes/contracts. Если поручение конфликтует с canonical contract, worker должен остановить буквальную реализацию, зафиксировать конфликт и объяснить его в отчёте.

## 7. Куда worker сохраняет результат

Если `WORKER_TASK.md` не требует другого canonical artifact, итог сохраняется по указанному там пути вида:

`reviews/worker_reports/<task-id>.md`

Report должен быть компактным и содержать только:
1. `Task` — что было поручено.
2. `Verified facts` — что фактически доказано.
3. `Changes` — что изменено, либо `none`.
4. `Validation` — какие проверки реально прошли/не прошли.
5. `Unresolved` — что осталось недоказанным/заблокированным.
6. `Status` — `complete`, `blocked`, `needs_fix`, `needs_user_decision`.
7. `Recommended next step` — один следующий шаг.
8. Точные commit/run/artifact/file refs, достаточные для проверки вывода без переноса логов в директорский чат.

Worker не должен складывать в report большие логи, большие JSON, полный diff или длинное исследование; они остаются в GitHub/Actions и указываются ссылками/refs.

В финальном ответе worker обязан назвать точный путь report-файла.

## 8. Передача результата директору

Пользователю не нужно копировать полный worker-ответ в директорский чат. Достаточно написать директору:

`Готово, читай.`

Директор знает текущий `Task ID` и путь report из последнего `WORKER_TASK.md`, поэтому сначала читает именно этот report. В дополнительные файлы идёт только если report недостаточен для управленческого решения или содержит внутреннее противоречие.

## 9. Ограничение автономии worker-а

Worker может исправлять технические проблемы **внутри явно порученного scope**, если режим `IMPLEMENT` это разрешает и canonical contracts не требуют отдельного решения пользователя.

Worker не должен самостоятельно:
- выбирать следующую большую задачу проекта;
- расширять scope на соседние backlog items;
- менять product/architecture policy из удобства реализации;
- начинать следующую planned-задачу после завершения текущей;
- превращать acceptance в редизайн системы, если acceptance не обнаружил конкретный дефект.

Следующее направление выбирает директор после чтения отчёта.

## 10. Параллельность и выбор пары задач

По умолчанию одновременно работают **не больше двух worker-чатов**.

Предпочтительная схема:
- один worker выполняет главную приоритетную задачу;
- второй выполняет быструю независимую задачу, которая не меняет ту же смысловую область и не зависит от результата первой.

Для параллельных задач нельзя использовать один перезаписываемый слот. Главная задача может использовать `WORKER_TASK.md`, а дополнительная получает отдельный task-файл с уникальным ID.

Перед запуском второй задачи директор обязан проверить пересечение областей. Не запускать параллельно две крупные переделки одного экрана, две ranking-задачи или работы, где одна требует незавершённый результат другой.

Если причина/масштаб проблемы неизвестны, сначала предпочитать короткий `READ-ONLY / RECON`, а не сразу большую реализацию. После recon директор отдельно решает, нужен ли `IMPLEMENT`.

Для больших задач качества разрешено сначала делать bounded audit по репрезентативной выборке, чтобы определить фактический масштаб и не проектировать системную переделку вслепую.

## 11. Когда worker-чат можно удалять

Директор обязан явно сообщать пользователю, когда конкретный worker-чат больше не нужен и его можно удалить.

Не считать чат готовым к удалению сразу после первого сообщения `complete`. Сначала проверить:
- итог worker-а сохранён в GitHub report/commit и не существует только в памяти чата;
- директор прочитал результат и принял решение;
- если нужна ближайшая пользовательская проверка на реальном устройстве/интерфейсе, она уже выполнена;
- нет очевидного следующего поручения, которое выгоднее продолжить в том же контексте;
- не ожидается немедленная доработка по уже замеченному пользователем дефекту.

После этого директор пишет пользователю явно: **`Этот worker-чат можно удалить.`**

Поздние замечания пользователя не требуют хранить все старые worker-чаты бесконечно. Если задача уже закрыта и её report/refs сохранены в GitHub, при более позднем замечании директор может создать новый worker-чат и дать ему фон через canonical files и сохранённый report.

Если вероятность скорой обратной связи заметная — например пользователь только собирается проверить результат на телефоне — директор должен попросить пока **не удалять** чат до этой проверки.

## 12. Директорская карта задач

`DIRECTOR_TASK_BOARD.md` хранит только управленческие пометки: приоритет, примерный размер, область изменений, совместимость с параллельной работой, необходимость пользовательской проверки и рекомендуемый порядок.

Это не второй источник технической истины. Если task board расходится с `CURRENT_TASK.md`, технический статус берётся из `CURRENT_TASK.md`, а директор исправляет task board.

При старте или завершении заметной задачи директор обновляет task board коротко, без логов, SHA-истории и подробностей реализации.

Приоритет продуктового порядка по умолчанию: сначала улучшать основную карточку рекомендации и понятность решения о покупке, затем исправлять качество объяснений/языка, и только потом добавлять вторичные функции вроде внешних обзоров. Новые пользовательские проблемы и blocker-ы могут менять этот порядок.

## 13. Почему введён этот режим

Предыдущий формат заставлял пользователя вручную переносить между чатами большие prompts, а директорский чат — повторно выводить длинные технические инструкции.

Новая схема:

`директор -> WORKER_TASK.md -> короткая команда worker-у -> worker-report -> директор`

оставляет в разговоре с пользователем только понятные решения и короткие команды, а вся техническая инструкция и доказательства живут в GitHub.
