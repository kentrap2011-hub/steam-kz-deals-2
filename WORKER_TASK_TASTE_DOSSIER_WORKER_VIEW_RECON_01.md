## Core question
What GitHub-owned compact read surface should be added so the Scheduled Task can reliably obtain the authoritative current immutable group descriptor(s) without reading the full manifest, while preserving GitHub as the control plane?

Evaluate at least these bounded options:

1. **Single compact current-worker-view file** generated by GitHub from canonical state, containing current snapshot identity, canonical expected sequence, and one or more exact predeclared immutable group descriptors.
2. **Per-group immutable descriptor files** generated by GitHub from the submission group plan, with a tiny separate pointer/index telling the worker which sequence is currently canonical expected.
3. Any existing repository artifact/path that already contains the required exact descriptor in a reliably small form and could be safely reused instead of adding a new artifact.

Do not assume option 1 is best; compare them.

## Required architectural properties
Any recommended design must preserve all of the following:
- GitHub alone owns scope, exact group identity/order, expected sequence, progress, retry/gap/replay state, persistence and completeness.
- ChatGPT/Scheduled Task must never reconstruct or guess group descriptors from partial manifest fields.
- The compact surface must be mechanically derived from canonical GitHub state, not hand-authored by ChatGPT.
- It must be small enough for reliable live-reader consumption.
- It must carry enough binding data to prevent stale/wrong-snapshot/wrong-sequence publication.
- It must support the buffered requirement that one invocation may publish group N, then N+1, N+2, etc. without waiting for canonical ingest of N.
- It must not accidentally turn the compact file into a ChatGPT-owned queue/backlog/retry manager.
- Daily snapshot preservation and same-snapshot group identity stability must remain intact.
- Existing state-based maximal-contiguous-prefix GitHub drain must remain authoritative.
- Taste Semantic Producer must remain untouched.

## Important same-invocation concern
The design must explicitly solve this issue:
If the compact surface contains only the single currently canonical expected group, then after publishing group N the Scheduled Task cannot wait for canonical progress to advance before learning N+1, because the buffered architecture intentionally allows N+1 publication before N is canonically ingested.

Therefore determine how the worker can safely know the next predeclared group(s) in the same invocation without reintroducing the oversized-manifest problem. Examples to assess include:
- a bounded window of multiple consecutive immutable groups;
- immutable per-group descriptor files addressable deterministically from a canonical plan/index;
- another bounded GitHub-owned scheme.

The solution must support at least the live acceptance criterion of 2 consecutive groups in one invocation, and ideally continued traversal for as long as the invocation remains healthy.
