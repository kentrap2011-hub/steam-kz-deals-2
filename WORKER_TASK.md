# WORKER TASK

## Goal

Сделать карточку покупки компактной на мобильном экране.

По умолчанию пользователь должен видеть один лучший/рекомендуемый способ покупки и короткое понятное объяснение, почему он лучший. Полный список остальных вариантов должен раскрываться только по явному нажатию пользователя.

Одновременно убрать из пользовательского текста внутренние технические формулировки вроде `одиночный вариант сейчас получает не меньший балл покупки` и заменить их человеческим объяснением практического смысла.

## Background

Основная fixed-package valuation уже завершена и подтверждена. Не пересчитывай package economics заново и не меняй ranking/math ради UI.

Плановая задача записана в `CURRENT_TASK.md` как:

`G. Compact purchase options — best option first, full list on demand`

Пользователь показал реальную мобильную карточку, где одновременно видны длинное описание набора и много отдельных вариантов покупки. Это занимает большую часть экрана и затрудняет использование.

Перед работой прочитай актуальные `CHAT_PROTOCOL.md`, `CHAT_CONTEXT.md`, `CURRENT_TASK.md`, relevant UI route/contracts и только нужные `web/**` файлы.

## What to do

1. Найди текущий UI-путь, который показывает package/standalone purchase options и объяснение их экономики.
2. Используй уже готовый producer-owned выбор/оценку лучшего варианта. UI не должен придумывать собственный ranking, цены или новую формулу выгоды.
3. В свернутом состоянии показывай:
   - один лучший/рекомендуемый вариант покупки;
   - его цену;
   - короткое понятное объяснение `почему`;
   - заметную кнопку/строку вроде `Показать все варианты` с количеством остальных вариантов, если они есть.
4. По нажатию раскрывай полный список всех подтверждённых вариантов, который сейчас уже доступен пользователю.
5. После раскрытия ничего не теряй: состав набора, отдельные варианты, цены и ссылки Steam остаются доступны.
6. Заменить технические фразы про внутренний `балл покупки` на пользовательский язык. Текст должен отвечать на вопрос `что выгоднее купить и почему`.
7. В мобильном свернутом состоянии длинный список не должен занимать большую часть экрана.
8. Состояние раскрытия — client-only UI state. Оно не должно менять production data или запускать вычисления.

Запусти релевантные UI checks.
