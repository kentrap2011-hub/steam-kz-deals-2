## Ключевой вывод и граница измерения

Пользователь наблюдает ~3 минуты на короткий prompt, также ~4 минуты и ранее ~5 минут. Это **человеческие наблюдения**, не таймеры GitHub. GitHub не показывает начало мыслительной подготовки, последовательность/длительность отдельных `functions.exec` вызовов, паузы между вызовами, время генерации или появления копируемого блока в клиенте ChatGPT. Нельзя приписывать серверным GitHub Actions полную задержку или публиковать якобы измеренный p50/p90 end-to-end.

**Два разных сценария:**
1. **Task уже зарегистрирован и подтверждён в `main`:** это выдача стандартной короткой команды, **не REGISTER**. `DIRECTOR_PROTOCOL.md` §2 уже запрещает дублировать scope/task-текст в launcher. Не нужны новая запись registry/Board, новый PR, CI или повторный full status scan, если факт подтверждён; целевой пользовательский путь — `<=60 s` при доступном GitHub.
2. **Новая задача / REGISTER:** нужны пользовательские полномочия, уникальный физический слот, task-файл, согласованные registry+Board, typed prewrite, один registration PR, существующие обязательные CI, head-bound merge и подтверждение появления task в `main` до выдачи launcher. `<=60 s` — **целевой**, но не обещанный путь **при быстрых CI и своевременном authorized merge**; никакая optimизация текста не отменяет внешний CI/merge gate.

## Реалистичное SLO и план измерений (без ложного p50/p90)

- **READY / task уже в main:** целевая выдача копируемого launcher **≤60 s** от пользовательского запроса при доступном GitHub; 0 регистрационных PR, 0 лишних CI, 0 перепубликаций, 0 незарегистрированных launchers.
- **REGISTER / новая задача:** целевые **≤60 s** лишь в благоприятном пути fast CI + authorised head-bound merge; **hard external bound отсутствует** (очередь Actions/необходимое разрешение/merge). При превышении честно назвать конкретный незавершённый gate, а не обходить его. 0 ненужных CI retries, 0 несвязанных writes, 0 обходов required checks.
- **Минимальная наблюдаемость:** для следующих ≥30 событий **раздельно для READY и REGISTER** записывать human `request_at` и `copy_visible_at` (если пользователь/клиент реально фиксирует), внутри одного `functions.exec` `stage_started_at`, `stage_ended_at` по DECIDE, prewrite, writes и checks; отдельно GitHub PR/commit/workflow/merge UTC, число amendments/failed CI, final reason (blocked/success). Только на такой выборке рассчитывать end-to-end p50/p90. GitHub timestamps сами по себе недостаточны. Не выводить fabricated averages из 4 selected PR.
- **Эффект следующего implement:** проверять реальные `publish` remote fetch count / critical path before-vs-after на deterministic latency mocks и в нескольких последующих REGISTER; независимые probes не должны ждать одна другую. Не обещать конкретного численного выигрыша до этих измерений. Для READY контролировать отсутствие лишних обращений, а не обещать ускорение этим helper.

## Ровно одно предлагаемое действие / владелец

**Предлагаемый один IMPLEMENT task:** `DIRECTOR_REGISTRATION_PREWRITE_PARALLEL_PROBES_MEASURE_01`. **Owner решения/постановки — директор; исполнитель — отдельный developer-worker после разрешения пользователя**, без назначения номера заранее и без самостоятельного запуска из этого QA. **Точный fileset:** только `scripts/director_registration_prewrite.js` и `scripts/test_director_registration_prewrite.js`; **не менять** `DIRECTOR_PROTOCOL.md`, `CHAT_PROTOCOL.md`, `DIRECTOR_TASK_BOARD.md`, registry, CI workflows, source-/production-/semantic-контракты.

**Обязательная реализация:** сохранить нынешние `prepare`/`publish`, строгие поля, `dryRun` и exact main rechecks; независимые task-existence probes и branch-existence probe выполнять параллельно с агрегированием 404/не-404, **не начинать tree/commit/ref при любой неоднозначности**; отдавать bounded `stage_timings_ms` и число remote reads/writes для этой операции без логирования секретов или task content; тестировать исход #338/неразрешённые transitions/exact-base race/dryRun=0 writes, конкурентность на deferred mocks и отказ при любом non-404. Проверять, что `functions.exec` вызывает существующий helper один раз и не делает обязательного `dryRun` + повторного `publish` для штатной регистрации. Использовать existing tests/CI, не создавать новый обязательный workflow. **Acceptance:** 0 лишних последовательных existence round trips, один atomic registration commit, 0 write при плохой проверке, exact-head CI/merge сохранены, объективные stage timings; пользовательский 60s SLO остаётся отдельной end-to-end оценкой, а не гарантией по одному тесту. Rollback — прежняя проверенная последовательность внутри helper, без понижения safeguards.

**Architecture preflight:** владелец registry/task/PR/CI/merge — существующий GitHub control plane и разрешённая developer/orchestration сессия, `config/execution_ownership_contract.json` не разрешает переносить производство в chat. Изменяются только проверки интерфейса GitHub в существующем helper, canonical `DIRECTOR_PROTOCOL.md` §2 уже разрешает prewrite и существующие CI. Никакой новой очереди, retry-loop, scheduler, backlogger, auto-merge или новых полномочий ChatGPT. Параллельные ЧАТЫ 1 и 3 работают над continuity и consent: **не редактировать их fileset и не трактовать их work как разрешение на merge**.

## Durable parent closeout — отчёт не равен закрытому решению

1. Worker сдаёт этот **единственный report-only DRAFT PR** с вердиктом и ссылкой. DRAFT не мержится самим worker-ом.
2. Директор адресно читает report и live PR, проверяет обоснование, отмечает решение **accept / reject / defer** и единственного owner; без повторного аудита. При accept — **только с разрешения пользователя** создаёт один ограниченный IMPLEMENT task; при reject/defer фиксирует конкретную причину и ownership в существующем registry/Board по действующему REGISTER/DECIDE маршруту, не теряет следующее действие.
3. После implementation-report директор сверяет тесты/CI и измеренный эффект; **только после проверки и разрешения** принимает соответствующее изменение. Report PR, source implementation PR и его принятие — разные события. Ready launcher не выдаётся до успешной регистрации новой задачи в `main`. Никакого risk-neutral auto-merge, semantic production launch или параллельных governance-правок ЧАТОВ 1/3.

**Route/pitfall candidate (только сообщение, не изменение):** в `PROJECT_ROUTES.md` раздел «Site tasks page / canonical Director forward plan» проверен по старому состоянию 2026-10-08 и ещё не указывает актуальный `scripts/director_registration_prewrite.js` + тест + `DIRECTOR_PROTOCOL.md` §2. Повторный detour #338 уже покрыт тестами prewrite, новой записи в `KNOWN_WORKER_PITFALLS.md` не требуется.
