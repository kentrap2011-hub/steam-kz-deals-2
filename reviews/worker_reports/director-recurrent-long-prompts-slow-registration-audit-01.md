## 3. Причина повторения — где именно перестали помогать правила

**Confirmed:** текущий протокол уже содержит строгую короткую форму launcher; типизированный REGISTER; risk-tier для MERGE; PRE-SEND; актуальный Board+JSON registry. Тем не менее процесс допускает рукописный произвольный JSON/Board diff: добавляя одну запись, директор поменял две чужие. Existing tests защитили main от двух детектируемых дефектов, но показали их только после нескольких коммитов. `blocker` после возврата статусов остался фактически stale — не доказано, что существующий CI обязан ловить такую семантическую несвежесть.

**Причинная интерпретация (высокая уверенность в механизме, не во внутреннем состоянии модели):** инструкции ограничивают *желаемое поведение*, но не задают атомарный, технически ограниченный write-set, допустимые значения публичных полей и неизменяемые поля существующих items для **именно операции создания**. Статус `PR merged` был принят как `task fully complete` при отсутствии verified production; затем исправление по частям принесло из архива старые факты. Отдельные «прочитай меньше»/«проверь перед ответом» не делают эту операцию механически безопаснее.

**Гипотезы, не факт:** желание перестраховаться повторением задания; большая история Board/Bootstrap/входных файлов, влияющая на контекст; длинные прежние примеры как implicit template; отсутствие полнотекстового захвата после ротации. Не подтверждены complete Director transcript, токены, точный timing, скрытая причина вывода длинных промптов или повторная частота на множестве запусков. **Нельзя** объявлять LLM «не способной выполнять инструкции» на основании одной операции; но и утверждать, что очередная формулировка правила технически заблокирует такое поведение, нельзя.

## 4. Варианты (от разных точек вмешательства)

| Вариант | Как работал бы #317 | Скорость/издержки | Защита от повторения после ротации | Цена/риск |
| --- | --- | --- | --- | --- |
| **A — узкая ручная регистрация, без кода** | Director пишет task + добавляет только новый ID и одну current Board-строку; не меняет Steam/ITAD statuses, заменяет `PR #` на нейтральное название, launcher фиксированный | Сразу меньше лишних commits; 3 ручных записи остаются | **Procedural only**. Правила уже существовали и не были гарантией | Нулевой rollout, высокий остаточный риск того же срыва |
| **B — механическая typed регистрация + ограничение diff, рекомендовано** | Вход: task path/ID/slot/goal. Генератор/шаблон **создаёт только новый item** с валидным публичным текстом и одну запись current Board; существующие IDs остаются byte-for-byte неизменны. Existing site-tasks validation отклоняет неожиданные edits к старым items и `PR #` в публичных полях. Launcher берётся из жёсткого короткого шаблона | Меньше ручной синхронизации и исправляющих циклов; один registration PR | **Механическое для registry delta и CI**, при наличии исполняемого пути; **не автоматически** для ChatGPT ответа, если директор свободно его переписывает | Небольшой targeted tooling/change existing validator; нужно чётко разрешить отдельный STATUS transition, не сломать легитимные PR; не требовать нового CI/workflow |
| **C — один источник, Board только производный** | Director меняет один canonical task-state document/entry; Board/current view генерируется из него; история остаётся архивом; убрать ручное поддержание обоих | Меньше ручной работы, конфликтов и stale snapshots | Strong after migration, если сайт и протокол признают один authority | Средне-высокая миграция, влияет на site tasks/backlog parser и historical state; опасность ошибочного cutover |
| **D — Issue/PR-first для bounded fixes, без формальной task-регистрации** | Для двух post-merge failures создаётся одна GitHub Issue/новый worker PR с полным scope и коротким launcher на issue; **не** меняются Board/registry | Существенно меньше регистрационных writes/ожиданий для мелких исправлений | GitHub issue/template durable; меньше мест для ошибок | Нужна явная смена `DIRECTOR_PROTOCOL.md` и принятие потери/проекции этих задач на site tasks page; нельзя самовольно обойти текущий REGISTER |
| **E — без отдельного директора на простых работах** | User поручает непосредственно существующему ЧАТУ 1 по Issue, тот работает в отдельном PR; директор подключается только для L3/merge | Минимум orchestration; меньше копирования | Внешних директорских handoffs меньше вообще | Выше риск дублирования/неотмеченной ответственности, прежние production/authorization gates должны оставаться GitHub-enforced |

B отличается от очередной формулировки правил **объектом контроля**: контролируется *операция изменения фактов*, а не память директора о checklist. C/D/E меняют модель хранения/маршрутизации, а не подправляют стиль. A уже практически требуется действующим протоколом и **не** считается решением устойчивости. Не совмещать разом B+C+D+E.

### Минимальные требования к B, чтобы не создать новую бюрократию

1. Одно ограниченное, **отдельно пользовательски разрешаемое IMPLEMENT**, а не серия аудитов: переиспользовать `scripts/build_site_tasks.py`/`scripts/test_site_tasks.py` и нынешнюю `.github/workflows/validate-site-tasks-page.yml`. Никакого нового workflow, scheduled task, второй проверяющей роли или дополнительного QA-PR для L1. **Не добавлять ещё один обязательный блок в Director protocol.**
2. Дать процедуре `register-one` один структурированный input; при `create` допустимые writes: новая `WORKER_TASK_*.md`, новая `items[id]` и current Board annotation; **не** изменять и не завершать соседние items. При необходимости меняется отдельной явной `update-status` с verified evidence — это другой намеренный тип операции.
3. Санитизировать/отклонять публичные поля `goal/title/blocker` **до** создания PR, сохранить нынешнюю строгую проверку сайта как защиту второго рубежа. Генерировать один короткий launcher из `ЧАТ N + repo/main + CHAT_PROTOCOL START + task filename`. **GitHub CI не может контролировать длину свободно написанного ChatGPT-ответа**; гарантированное отсутствие пересказа возможно лишь при фактическом использовании заранее сформированного текста.
4. **Оговорка реализуемости:** директор сейчас работает через GitHub connector, а не гарантированный локальный checkout. Если нельзя реально запускать helper в используемом интерфейсе, не выдавать неисполняемый CLI за решение. Тогда первым механическим уровнем становится контролируемый minimal-diff update через доступный GitHub write API плюс fail-closed delta-check в **уже существующем** PR CI; она остановит нарушение на проверке, **но не до commit**. Реальный runnable generation path требует доказанного существующего executor; не изобретать новый workflow по умолчанию.
