## 1. Executive finding: distinguish permission, execution and completion

**It is not proven that the first answer was an unauthorized failure to merge.** The current [DIRECTOR_PROTOCOL.md](../../DIRECTOR_PROTOCOL.md), §1 typed gate, explicitly classifies “проверь чат N” as **read-only STATUS (STOP without writes)** and “принимай PR” as **MERGE with user permission**, L3 independent QA and all mandatory exact-HEAD checks. A green QA verdict is not itself user authorization. The supplied first request “Чат 2 запустил, проверь чат 1” can legitimately be processed as STATUS; the second “Кто должен принять пр?” names the responsible actor but, literally, is not an imperative to execute the merge.

**There is nonetheless a concrete orchestration gap.** At the QA-time snapshot [Board at d24e942…](https://github.com/kentrap2011-hub/steam-kz-deals-2/blob/d24e9427425538600f8b3fb560ea41459658aaa1/DIRECTOR_TASK_BOARD.md) (top, final Steam QA lane) already states: after Chat 1's PASS, Director checks source HEAD/CI and **accepts existing #346**. [The QA task](../../WORKER_TASK_STEAM_POSTMERGE_ACTIONS_L3_FINAL_DELTA_QA_01.md) says the same. These are verified *conditional operational intentions*, **not independently verifiable quotations of user approval**. Neither the typed gate nor the QA → Director handoff specifies how to reconcile a pre-existing, provably user-authorized conditional MERGE instruction with a later apparently STATUS-only turn; how to record whether authorization was found or missing; or when an already-authorized action must actually run instead of ending as another recommendation. The current director can correctly say “the Director owns merge” without supplying an authorization disposition or executing a previously authorized merge.

**Behavioral replacement to implement and prove:**

1. First distinguish **user request type** and a **pre-existing actionable grant**. A pure “проверь чат 1” with **no proven grant** remains read-only STATUS (no mutation). An existing standing “после PASS принимай PR №X” counts only when explicitly sourced to the **user** (conversation/accepted user-approved instruction), scoped to that exact PR and condition, and not withdrawn. A Board author/worker task containing “Director merges” is a **plan**, not by itself an authorization record.
2. If a specific user-authorized *conditional merge* is already due, use the MERGE route on the current response, recheck actual source PR/HEAD, required CI, risk-specific independent QA, mergeability, permission and absence of material delta; **execute merge in the same turn** when all pass, not merely describe “next action”. This prior grant must be explicitly mentioned as the reason the otherwise STATUS-looking turn also has a MERGE action. If any premise is unknown, do not mutate; mark **BLOCKED_PERMISSION** or **BLOCKED_SAFETY** and name the exact missing evidence. Never silently manufacture prior approval.
3. A new explicit “Прими PR №X” invokes MERGE and should execute after gates, without another redundant user confirmation. “Кто должен принять?” is DECIDE/ownership, not a new merge grant; answer who and, if no prior grant, state “нужно явное разрешение” instead of admitting an unproven execution omission. A report-only PR and source PR are separate: do not act on the wrong PR or repeat full QA solely because a report HEAD changed.
4. The action disposition must be externally truthful in the same answer: **MERGED (commit/PR)** or **BLOCKED (specific authority/CI/QA/conflict/HEAD reason)**, never **“следующее действие”** masquerading as completed closeout. No automatic production dispatch, semantic worker, retries or site-publication claims from source merge.
