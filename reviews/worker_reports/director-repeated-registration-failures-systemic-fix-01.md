## Вердикт пользователю и один следующий IMPLEMENT

**Повтор произошёл потому, что директору запретили ошибаться словами, но оставили свободную ручную операцию, в которой нужно согласованно изменить task-файл, большой JSON и Board.** Указание «короткий запуск», риск-ориентированная QA и строгие GitHub CI уже работают в своих пределах; они **не проверяют сформированный регистрационный пакет до публикации первого коммита**. После [аудита #319](https://github.com/kentrap2011-hub/steam-kz-deals-2/pull/319) с точно таким же дефектом \`PR #\` не последовало принятого IMPLEMENT: #319 до сих пор report-only DRAFT. Поэтому в [регистрации #338](https://github.com/kentrap2011-hub/steam-kz-deals-2/pull/338) снова возник \`PR #\`, а также неверное enum \`effort="малая"\`. Это дефект **границы записи/валидации до записи**, а не основание для очередного длинного запрета в protocol.

**Предложить директору ровно один следующий task: \`IMPLEMENT_DIRECTOR_TYPED_REGISTRATION_PREWRITE_01\`** — небольшой *typed GitHub-connector-native REGISTER transaction* с локальной (в том же исполняемом вызове до любой записи) проверкой допустимых значений, публичных полей, ограниченного write-set и exact-head, плюс regression в **существующей** site-tasks CI на случай обхода инструмента. Сохранять единственный registration PR и нынешние risk/authority gates. Реализовать **только по отдельному решению пользователя/директора**. Не запускать ещё один RECON или новую независимую QA-цепочку.

## 3. Точный механизм повторения и предел знания

1. **Неправильная точка контроля:** PRE-SEND и director decision gate — процедурные, не технические; валидатор живёт **после** коммита. В #338 первые четыре write шли независимо; до PR отсутствовал один validated transaction. Два запрещённых формата были полностью проверяемыми без нового внешнего аудита.
2. **Свободная поверхность записи:** директор вручную сочиняет значения \`effort\` и публичные тексты; \`малая\` выглядит допустимым русским синонимом, но не входит в машинный enum; \`PR #\` естественно в приватном task и PR описании, но запрещено *в публичном реестре*. Нет единого prewrite source поля/формы для обоих контекстов. Простая инструкция «не забыть» не делает их типобезопасными.
3. **Избыточная координация:** смена статусов, new tasks и Board живут в нескольких файлах; обычный GitHub \`create_file/update_file\` делает последовательные commits, не атомарную тройку. #317 показал реальную опасность изменения чужих IDs. #338 нуждался в **явно разрешённых** двух completion transitions, поэтому blanket «никогда не трогай старые» тоже неправильный.
4. **Постфактум gate каскадирует:** один invalid enum остановил многие тесты до отдельного public assertion; после первой поправки проявился \`PR #\`. Точное устранение двух ошибок *перед первым push* возможно, если оба предиката применяются к whole candidate и failures агрегируются.
5. **Audit → owner implementation gap:** #319 уже сформулировал структурное решение, но остался DRAFT без owner-approved реализации. #299/#308/#333/#334/#337 действительно меняли разные проблемы, а не транзакционный REGISTER. Новый общий аудит без implement только воспроизведёт этот разрыв.
6. **Hypothesis, not GitHub fact:** объём Board (большой), старые шаблоны, самоповтор модели и контекст ротаций могут увеличивать затраты и путаницу. Нет trace промптов, hidden reasoning, поминутных tool calls и точного user-experienced 5-минутного span; нельзя присвоить им доказанную причинность.

## 5. Один IMPLEMENT: конкретные интерфейсы, владельцы и проверки

**Owner:** Director получает отдельное разрешение на scoped REGISTER-tooling implement, назначает одного developer-worker; он сдаёт **один** implementation PR. Director принимает по текущему risk-tier/required CI, без нового параллельного общего аудита. Пользователь разрешает governance-изменение; developer не выдаёт себе право merge/production/semantic start. QA L2 только при выявленном конкретном нетривиальном риске, L3 для опасных authority изменений остаётся обязательной.

**Scope/sources:** добавить компактный \`config/director_registration_contract.json\` как машинный prewrite schema (enums и запреты public field; обратная совместимость с existing JSON), \`scripts/director_register_transaction.js\` как *pure* candidate-builder/validator с тестируемыми независимыми функциями + адаптером вызовов доступных GitHub connector methods из \`functions.exec\`, \`scripts/test_director_register_transaction.js\` с fixtures старых ошибок. В \`scripts/build_site_tasks.py\` использовать те же schema-значения (либо автоматическую parity assertion на exact constants, но не две бесконтрольно расходящиеся копии); в \`scripts/test_site_tasks.py\` добавить regression для disallowed enum/public \`PR #\` и write-set. Изменить **только существующий** \`.github/workflows/validate-site-tasks-page.yml\` при необходимости base-diff guard, без нового workflow/job (fetch exact base commit точечно, не весь history); \`DIRECTOR_PROTOCOL.md\` лишь **заменить** описание ручного REGISTER на короткую ссылку на новый инструмент, не наслоить новый длинный gate. Board и registry business content/старые задачи не менять при реализации инструмента.

**Реальная доступность:** в текущей рабочей среде доступны \`functions.exec\` (исполняет JS) и GitHub \`fetch_file/create_blob/create_tree/create_commit/update_ref\`, \`create_branch\`, \`create_pull_request\` с exact ref/branch. Нет доказанного автоматического запуска repo Node/Python scripts **внутри GitHub connector**. Поэтому не выдавать \`python scripts/...\` за доступную директору кнопку. IMPLEMENT должен реально продемонстрировать *в этом class of ChatGPT connector session* вызов тех же чистых функций в исполняемом \`functions.exec\` JS (например, statically included adapter; никакого \`eval\`/dynamic import repo code) с проверкой версии schema/ref. Хранение \`.js\` в repo само по себе не делает его исполняемым у директора: если адаптер нельзя реально вызвать из этого интерфейса, **не заявлять prewrite protection**; остаётся честный CI-only fallback и \`BLOCKED_TOOLING\` для B. Нельзя вводить новый Action/scheduler лишь чтобы обойти этот предел.

**Предлагаемый контракт \`REGISTER_CREATE\` / \`REGISTER_BATCH\`:**
1. Вход: bounded список 1–2 \`{task_id, task_filename, task_body, title, goal, effort, urgency, reasons, dependency_ids, slot, blocker}\`; опциональные отдельные \`authorized_transitions\` (\`task_id, expected_status, new_status, expected_record_sha\`/verified snapshot, reason), разрешённые *явно* по owner evidence. Без transition список старых item ID immutable. Slot assignment обязано отражать подтверждение физической беседы; не выводить из \`active\`.
2. Считать **один exact main base SHA** и только нужные Board top/registry IDs + необходимые task/template/contract. Построить целиком candidate \`task file(s) + registry + current Board\` **в памяти**, не создавать branch/commit до validate.
