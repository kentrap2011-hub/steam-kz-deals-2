## 4. Единственный минимальный план коррекции (не выполнялся)

**P0 — behavior-only, без изменения файлов.** На ближайших 5 однородных запросах директор сохраняет mandatory gates, но ограничивает **доказательства типом действия**: сначала классифицирует `STATUS / DECIDE NEXT / HANDOFF / REGISTER / MERGE`; выбирает точную Board/registry запись и соответствующий PR/report/CI; прекращает fetch после достаточного evidence и даёт краткий статус/решение. Нет самостоятельного patch/source/log review в `STATUS`; сомнения → назначенный bounded worker RECON; чисто исторические bootstrap/handoff не используются для live-истины. Любой дополнительный fetch должен иметь обозначенный конкретный unresolved question. Это **применение существующих правил**, не послабление safety.

**P1 — только если P0 воспроизводимо провалится:** отдельный будущий IMPLEMENT с двумя текстовыми точками *в одном* `DIRECTOR_PROTOCOL.md`:
- **§1, после general gate L28–40:** «Для STATUS-request выполнить scoped current-truth gate: slot → 1 exact worker-report → PR HEAD/state → relevant exact-HEAD CI; сравнить с top Board/registry записью, не загружая их полностью. Переход к patch, code, history или новой задаче разрешён только при конкретном неразрешённом факте или отдельном запросе пользователя». Это не отменяет проверку authorizations и несогласованных статусов.
- **§2/§8 (L61–70 / L195–201):** явным образом развести `STATUS` и `REGISTER`: создание незарегистрированного нового task в main остаётся **личной governance-обязанностью директора** (именной task + registry + Board + PR exact-HEAD CI + merge) до запуска worker. Можно делегировать исследование технического содержания только уже авторизованному worker, но нельзя поручать незарегистрированную worker-задачу как будто её START gate выполнен; при блокировке регистрации сообщать `BLOCKED_AUTHORITY`, не подменять регистрацию длинным prompt.

**P2 — инструментальный только при измеренном эффекте:** индекс/точечные GitHub read helpers без новых state/queue/contract; не менять registry schema, CI и governance ради экономии единичного запроса. Директор не должен сам реализовывать P1/P2 по этому отчёту: решение остаётся за пользователем.

## 6. Верификация и пределы

- **Подтверждено чтением main:** `CHAT_PROTOCOL.md`, `CHAT_CONTEXT.md`, `DIRECTOR_PROTOCOL.md`, актуальный верхний Board, точная запись JSON, задача, ограниченный route/architecture preflight, исторические warnings, PR #241/#242/#243/#247 и exact-HEAD CI #243/#247.
- **Не выполнялось:** изменение протоколов, Board, реестра, кода/CI/scripts, production, semantic work, deploy, Scheduled Tasks, GitHub settings, PR merge. Только этот Markdown-файл в отдельном draft PR.
- **Доказательственный предел:** эпизоды директорского диалога предоставлены в task как вторичное свидетельство. Невозможно независимо подтвердить полную последовательность и латентность внутренних tool calls, точную token cost и намерения. Выводы о наблюдаемом отклонении имеют условие «если эпизод описан верно»; само наличие конкретных нормативных и технических факторов подтверждено напрямую.
