## 6. Steam external API verification, including disputed claims

**A. Existing Steam Search /results** is a storefront endpoint and parser, not the published GetAppList API. The repo's actual parameters are directly confirmed at steam_production.py lines 339–364 and runner lines 372–419: specials=1, category1=998, maxprice=4500, hidef2p=1, cc=kz, count=100, sort_by=Name_ASC. discount >=50 is local. The earlier bounded PR #148 Search tests reported particular attempted minimum-discount parameters were ignored; do **not** generalize that result to unrelated APIs. Steam category filters are not app.type; Sub_ package coverage must be separately diffed. Actual Search total is 8,986–9,286 for these dates, not the earlier ~63k before source reduction. Source: pinned project route and source linked above.

**B. Official Steamworks IStoreService/GetAppList/v1:** [Steamworks IStoreService GetAppList](https://partner.steamgames.com/doc/webapi/IStoreService). Official method URL: https://partner.steam-api.com/IStoreService/GetAppList/v1/ . The Service interface says to use input_json; **key is required, “Any web API key”**. Fields **if_modified_since**, **include_games**, **include_dlc**, **last_appid**, **max_results** (10,000 default, 50,000 maximum) are documented. Output **last_modified** means some information *or price* changed; **price_change_number** change means price *may* have changed, e.g. a discount starting **or** price adjustment. This is **not a guaranteed “sale began since previous scan” stream** and not a response of current KZT sale price/percent. AppID cursor does not prove Sub_ package coverage or fully reconstructed existing/expired offers. Authentication availability from this GitHub Actions repo and storage of the key were not checked or authorized for trial: **UNVERIFIED**.

**C. IStoreQueryService/Query/v1:** the publicly available **community-derived, not verified official Steamworks** interface listing [IStoreQueryService/Query](https://steamapi.xpaw.me/IStoreQueryService) describes query.filters.min_discount_percent and query.filters.discounted_dates_filter {start_date, end_date, allow_partial_overlap} and query/context type/country options. The existence of names in this community schema is **confirmed as a schema observation**; official permission/endpoint/version stability, whether a given account/key can call it from GitHub Actions, what the date filter means (promotion overlap vs start date vs price change), cap/currency consistency, exact App_/Sub_/DLC coverage, root links, stable pagination/sort, and identical >50% offers are **UNVERIFIED**. In particular discounted_dates_filter **cannot** be called “discount started after last run” based on its name alone. No live Query call was made.

**D. Storefront /api/appdetails batching:** the **nonofficial** reference [Get app details](https://github-wiki-see.page/m/revadike/internalsteamwebapi/wiki/get-app-details) and other independent explanations indicate **multiple appids do not return full metadata unless filters=price_overview**; full details normally require one AppID per GET. A KZ batch of price_overview, if supported in the current environment, would **not** itself carry fullgame, dlc lists, canonical identity, child ancestry or nested discovery, so treating it as a bulk replacement for all 1,800 requests is invalid. Historical SteamDB [Store Prices API](https://steamdb.info/blog/store-prices-api/) also reports inconsistent batched price returns. Exact response coverage, 100-ID behavior, failure modes and KZT accuracy are **UNVERIFIED without a separately authorized bounded live comparison**. Do not claim batch full-parent GETs work.

**E. “Only newly discounted since yesterday?”** None of the above official verified methods supplies a documented, complete KZ offer-event feed that alone captures starts, ends, changed percentages/KZT prices, removed/renamed/unavailable offers, new Sub_ packages, DLC parent changes, the review-based requalification of a base, skipped/failed days and out-of-order updates. Last_modified/price_change_number apply to metadata and possible price changes, not necessarily sale-start events and not the entire dynamic candidate eligibility. A discount that started before yesterday but remains active today is still an opportunity; a delta of only *new* offers would wrongly remove it unless last-known active offers were independently maintained and revalidated. Ignoring expiry could publish nonexistent discounts; a prior broken run must not advance the cursor. The only established current full-completeness authority is the live full snapshot + verified targeted relations.

Existing Search reuse/batch already removes most costly AppReviews traffic. | **Low payoff** relative to risk of false negatives and missing/reused reviews; keep existing guards. |

Source sorting, duplicate page signatures, local KZT gates and safety recheck cannot be labeled “wasted HTTP” merely because no error occurred in a three-day sample. **In particular all no-network checks should remain.** There is currently no verified source-side discount filter on the existing Search that justifies dropping the >=50 local predicate.

### Hybrid delta design, explicitly **NOT approved** for implementation

If a later contract revision were approved, a hybrid would need: immutable last-known App_/Sub_ offer map with exact KZT/discount/sale-expiry and parent-chain provenance; changed-since cursor with confirmed source semantics; refresh of **all still-active** offers even if their original discount started earlier; expiry/removal, root/DLC/package reconciliation, full fallback scan, and checkpoint commit only after a complete verified cycle. Failures, skipped days, changed review suitability, new DLC and cursor drift must reopen full reconciliation. Separate durable GitHub-owned state/retry/completeness contract would be required; current daily source policy does not authorize silently replacing the full snapshot. There is no proven start-sale-only API. As a speed option, this is **later research**, not the first trial.
