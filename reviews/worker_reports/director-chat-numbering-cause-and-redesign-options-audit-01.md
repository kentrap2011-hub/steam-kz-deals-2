# Independent audit — Director chat numbering failures and interaction redesign options

- Task ID: director-chat-numbering-cause-and-redesign-options-audit-01
- Date: 2026-10-26
- Repository / source: kentrap2011-hub/steam-kz-deals-2 / main
- Verified main at investigation start: 15e23985e21cf1962b849c355846001b301726e9 (registration #304)
- Mode: independent diagnosis, report only; no operating-policy change authorized.

## 1. Короткий вывод и решение, которое нужно принять

**Причина — не сложность арифметики.** Один ярлык «ЧАТ N» используется сразу как обращение пользователя к физическому диалогу, поле назначения GitHub-задачи, исторический label и иногда якобы роль/специализация. При этом у GitHub **нет проверяемого идентификатора или статуса физической беседы ChatGPT**. Реестр задач не является реестром живых бесед. Сверка четырёх частично дублирующих документов происходит вручную в длинном, постоянно сменяющемся контексте директора. Поэтому даже точный checklist может быть формально прочитан и практически не применён при следующей выдаче задания.

**Подтверждено:** поле worker_slot есть у задач, но нет поля physical_conversation_id / instance / lifetime; среди старых blocked-заданий есть прежние номера, не означающие текущий открытый физический чат; актуальная шапка Board и реестр отдельно фиксируют новые 1/2/4; протокол употребляет «следующий свободный», но не задаёт формальный алгоритм занятости/минимального свободного; старые снимки Board/handoff/bootstrap сохраняют конкурирующие назначения; регистрации пересекаются по одним файлам. PR #302 документировал конфликт #300/#301, впоследствии #300 был reconciled/merged. Эти факты доказывают архитектурную неоднозначность учёта, но **не доказывают внутренний механизм конкретной ошибочной реплики модели**.

**Со слов пользователя и записанного task (#304):** 26 октября директор выбрал новые 2 и 4, хотя ранее закрытые 1 и 3 были доступны, и сначала выдумал их «специализацию», затем назвал номера случайными. Невидимая переписка не находится в GitHub: достоверен пользовательский отчёт об эпизоде, но ни GitHub, ни этот аудит не могут независимо воспроизвести буквальный ответ директора или доказать психологическую причину. Фальшивое объяснение — не подтверждение реальной роли чатов.

**Предлагаемый короткий путь:** немедленно считать номер только временным UI-ярлыком, не приписывать ему роль, перед каждым новым назначением брать _текущий_ список фактически занятых номеров из краткой сводки пользователя/Director, выбирать заранее согласованным алгоритмом (например, минимальный свободный), явно говорить НОВЫЙ/СУЩЕСТВУЮЩИЙ; не сохранять фиктивную «специализацию». Без дополнительной QA-цепочки, CI или регистрационного документа ради одного номера.

**Предпочтительный долгосрочный путь, если важно сохранять ЧАТ 1/2/3:** отделить в **одном** компактном реестре экземпляр физического диалога от task ID: номер — переиспользуемый display slot; assignment / instance — отдельная запись с одноразовым generation ID, фактом launch/retire, текущим task ID и ссылкой на report/PR. Board должен быть производным _видом_ из реестра, а не вторым полуручным владельцем статусов. Слова пользователя «запустил/завершил» остаются источником факта о UI; GitHub может гарантировать только согласованность **заявленных записей**. Такой вариант меньше меняет привычный интерфейс, но всё ещё требует дисциплины ручного запуска. Ниже есть более радикальные альтернативы — от отказа от номеров до отмены роли директора.

**Важно сейчас:** пользователем уже открыты новые ЧАТ 2 и ЧАТ 4, а текущая новая задача закреплена за новым ЧАТ 1; на этой выборке ЧАТ 3 отмечен свободным. Не перенумеровывать 2/4 и не считать их завершёнными на основании registry status=planned. Ни одна предлагаемая схема не является условием завершения этих задач.

## 2. Фактическая модель и предел доказательств

### 2.1. Где какие идентификаторы

| Сущность | Фактическое место | Что реально доказывает | Что не доказывает |
| --- | --- | --- | --- |
| Физический диалог ChatGPT | UI пользователя, его история, сообщения | Пользователь знает, какой диалог открыл и куда вставил команду | Сам по себе GitHub не знает URL/ID, открыт ли он, активен ли, прочитан ли prompt, можно ли удалять |
| Номер ЧАТ N | текст поручения, Board, поле worker_slot во множестве записей task registry | Намерение директора связать задачу с человекочитаемым ярлыком | Уникальный физический экземпляр, текущее присутствие, прежнюю «специализацию» |
| Task ID / WORKER_TASK_*.md | отдельный именованный task-файл и JSON registry | scope, критерии, запреты, назначение, плановая запись | Факт начала работы, рабочую беседу, фактическое исполнение |
| Branch / PR / report | GitHub refs и reviews/worker_reports | Код/отчёт действительно сохранён, HEAD/CI/статус PR | Что чат закончил или пользователь проверил результат; что беседа жива |
| Роль developer / QA / director | конкретное поручение, DIRECTOR_PROTOCOL.md | Допустимую роль для **текущей задачи** | Постоянную специализацию номера/чистого диалога |
| Board / handoff / bootstrap | Markdown snapshots | Наиболее свежее **заявленное** распределение при правильной интерпретации верхних разделов | Live ChatGPT-occupancy, если пользователь открыл чат, но registry ещё planned |

Численные признаки на проверенном main:
- registry config/director_task_plan.json: 125 task items, из них 29 не имеют status=complete (включая legacy blocked), каждый item имеет worker_slot, но нет отдельной коллекции физических chat instances;
- текущие новые Chat 2 и Chat 4 в JSON: status=planned, хотя пользователь по task/Board уже сообщил об их запуске; это демонстрирует различие между task status и фактом физического запуска, а не ошибку worker-ов;
- Board ~3 668 строк, handoff ~85 KB, bootstrap хранит датированные исторические инструкции; верх Board на строках 8–17 фиксирует обновлённые назначения, но ниже сохранились исторические назначения 1–7;
- DIRECTOR_PROTOCOL.md §2/3/10 требует уникальный свободный номер и проверку физической идентичности, но слово «следующий свободный» **не является** ни определением минимального числа, ни вычислимой моделью активного множества.

### 2.2. Воспроизводимый эпизод 26 октября

Входное условие из пользовательского сообщения: предыдущие физические 1 и 3 завершены, директор должен запустить две новые независимые задачи. Ошибочное действие: назначены новые 2 и 4, а затем для этих новых физических диалогов выдано объяснение якобы старой специализацией. Новые чаты не наследуют ни принадлежности старого номера, ни его знания; действительная специализация находится в TASK, а не в ярлыке.

Контрольный алгоритм, если пользователь **подтвердил** множество активных физических слотов: сохранить занятые номера, выбрать самый маленький из доступных (для второго назначения пересчитать занятость после первого). Например, если 2 и 4 действительно были заняты, а 1 и 3 свободны, результат 1 и 3; если 2 тоже был свободен, строгий «минимальный свободный» дал бы 1 и 2. Поэтому прежде чем спорить о конкретной паре цифр, нужно зафиксировать входное множество занятых слотов. **Ни реестр задач, ни устаревший блок Board сами по себе такого множества не доказывают.**

Постфактум текущая верхняя секция Board корректно закрепляет новые ЧАТ 2 и ЧАТ 4 как уже запущенные, новый ЧАТ 1 как отдельное поручение, ЧАТ 3 как свободный. Нельзя исправлять историческую ошибку переименованием уже открытых 2 и 4.

### 2.3. Почему прошлые gates не предотвратили её

1. **Смешаны идентичности.** Один task item имеет worker_slot, но реестр не знает конкретный generation физического чата и момент его retirement. Разные task items могут иметь одинаковый worker_slot законно в разные эпохи; простая уникальность поля не решит задачу.
2. **Неверифицируемый ввод.** GitHub видит plan/status, а пользователь — ChatGPT UI. Даже правильная автоматическая сверка GitHub не покажет «пользователь уже создал новый физический чат» без сообщения/интеграции.
3. **Распределённая запись.** Registry, верх Board, handoff и bootstrap частично повторяют статусы. Протокол требует same-commit updates, но это дорого при параллельных изменениях: PR #302 подтвердил merge conflict #300 при #301, а PR #290 был заменён более узким #299 из-за пересечения с регистрацией и handoff. После reconciliation #300 merged — не заявлять старый конфликт как текущий.
4. **Неоднозначный выбор номера.** «Следующий свободный» не равен формуле «минимальный не занятый», и нет authoritative live occupancy set. Gate проверяет совпадение уже **выбранных** Board/prompt/registry, а не качество исходного выбора.
5. **Проверка выполняется самим ошибающимся агентом.** PRE-SEND — procedural, не UI-enforced; внутреннее самообъяснение может подменять неизвестный статус «специализацией». Это рабочая гипотеза об эпизоде, не доказанная трассировка модели.
6. **Длинный контекст и история старых ролей.** Десятки исторических одноимённых ЧАТ N повышают вероятность неверного связывания свежего слота с историей. Это правдоподобный фактор, а не установленная единственная причина.
7. **Нет причин считать каждый defect поводом к новому gate.** Ещё один checklist без новой наблюдаемости может увеличить те же издержки и не устранить ошибку.

## 3. Что пользователю действительно требуется

Необходимые способности: быстро сказать «отправь в новый ЧАТ 1», отличить новый диалог от старого; знать, какое _текущее_ задание связано с обозначением; параллельно не дать двум активным работникам редактировать одну ветку; по сообщению «проверь ЧАТ 2» открыть точный task/PR/report; без угадываний сообщить, что чат можно удалить. Историческая «специализация» номера, постоянный цифровой ярлык, подробная кадровая история в Board, отдельный повторный QA выбора цифры и запись всех промежуточных реплик в GitHub — не необходимы.

Повторное использование номера безопасно **только как нового физического экземпляра** после явного retirement предыдущего. Один **физический** worker обычно = одна задача; продолжение прежнего issue по тому же report может использовать тот же instance без reassign, но новая независимая работа — новый instance. Одну задачу могут последовательно делать несколько физических работников (implementation → QA), каждый с собственным instance; один worker может иметь несколько последовательных задач, но для настоящей независимой задачи старый контекст является риском. Не подменять физическую тождественность совпадением Task ID или PR.

## 4. Реальные альтернативы и цена

Оценки времени ниже — **порядок величины для организационных изменений**, не измеренные затраты и не обещание сроков. Любой изменяющий протокол вариант требует отдельного решения пользователя. Соседний аудит ЧАТА 4 оценивает общий QA/verification overhead; здесь оценивается только то, как номер и диалог вписываются в operating model.

### A. Нулевая миграция: дисциплина выдачи минимального свободного номера

**Механизм:** перед выдачей директор смотрит краткое подтверждённое пользователем множество _активных физических_ чатов; выбирает минимальный свободный номер; команду всегда маркирует «НОВЫЙ/СУЩЕСТВУЮЩИЙ», не выводит роль из номера. Если множество неизвестно, задаёт один точечный вопрос о занятости, а не придумывает ответ. При launch user confirms only when necessary; записи по ранее выданным чатам не перенумеровывать.

**Эпизод:** свободные 1/3 при занятых 2/4 → новые 1/3, «специализаций» нет.

**Плюсы:** нулевая разработка, привычные ЧАТ N, моментальный пилот. **Минусы:** зависимость от человеческого подтверждения и дисциплины директора; старые duplicate snapshots остаются. **Риски:** после ротации директора он опять примет registry planned за live; бесконечный checklist здесь бесполезен. **Цена:** минимальная, текстовое правило/разовая договорённость, без CI и QA.

### B. Один компактный реестр chat instances; Board как производное представление

**Механизм:** в единственной canonical director-записи отдельно хранить chat_instance_key (не утверждать настоящий внутренний ChatGPT ID), display_slot, generation, launch_status=[proposed,user_confirmed_open,retired], current_task_id, refs, updated_at и source_of_confirmation; статус task отдельно. На каждый новый физический чат новый generation; reuse номера допускается только после retired предыдущего. _Не_ создавать параллельно две ручные таблицы — убрать из handoff/bootstrap повторные live assignments, Board отображает актуальные слоты из одного реестра; старые mappings остаются историей по generation. Возможен маленький ручной snapshot до UI автоматизации. Не требовать от пользователя адреса/URL приватного чата.

**Эпизод:** authoritative заявленные active instances занимают 2/4; alloc(available) вернёт 1/3; старый физический «ЧАТ 1» другого поколения не маскируется под новый; назначение без user confirmation остаётся «proposed», а не «launched».

**Плюсы:** сохраняет номера, защищает от смены контекста, точно различает задачу и беседу, снижает дубли. **Минусы:** нужен перенос записей и простая смена привычек; GitHub не видит UI фактически. **Риски:** устаревшая ручная отметка still possible; двойное владение реестром/Board вернёт проблему; не вводить per-message verification. **Цена:** средняя (упрощённый 1-файловый прототип — малая; нормальная миграция и проекция — средняя).

### C. Небольшой атомарный GitHub allocator поверх B

**Механизм:** только если B покажет реальную потребность, маленькая GitHub-команда назначает минимальный free slot под generation key и CAS/expected HEAD, предотвращая два одновременных резерва; launch confirmed вручную. Никакой новой recurring automation. Технический allocator не определяет, какой ChatGPT-чат пользователь открыл: это независимая граница знания. При коллизии выдаётся одна понятная ошибка и требуется повторное назначение, а не новая серия QA.

**Эпизод:** atomic reservation выдаёт 1, затем 3, не позволит одновременно назначить их другой задаче, если active set верен.

**Плюсы:** точный алгоритм и защита от параллельных регистраций. **Минусы:** код, тесты, CI-интеграция и возможный конфликт commits; риск заменить простую проблему новым service. **Риски:** автоматизируется только «согласованность предположений», не реальный физический UI; больше ceremony. **Цена:** выше средней; оправдано только после подтверждения высокой частоты одновременных назначений.

### D. Непереиспользуемый последовательный номер или уникальный короткий launch-token

**Механизм:** вместо recycle ЧАТ 1 → новый ЧАТ 1, выдавать каждый раз следующий номер (ЧАТ 8, 9…) либо короткий уникальный token (например, W26-104), связываемый с task ID. Старые чаты никогда не получают прежний идентификатор. Слово «свободный» из алгоритма удаляется.

**Эпизод:** две новые задачи получили бы, например, ЧАТ 8 и 9, а не 2 и 4; ошибка именно «не выбрал 1/3» исчезает вместе с требованием повторно использовать старые номера.

**Плюсы:** простое отсутствие коллизий поколений, меньше условий. **Минусы:** длинные номера/токены и неприятная пользовательская навигация; текущая любовь пользователя к простым 1/2/3 не сохраняется. **Риски:** без истинного live identity директор всё ещё может отправить команду не туда или выдумать роль; счётчик должен быть единым при параллельной выдаче. **Цена:** небольшая, кроме переобучения интерфейса.

### E. Отказ от номера в пользу понятного имени *текущей задачи*

**Механизм:** маршрут «новый чат: Убрать freeze-gate №266», «новый чат: Анализ лишних QA», задача определяется точным WORKER_TASK; при необходимости пользователь переименовывает физический диалог в UI. Старую историю ищут по Task ID/PR, не по ЧАТ N. Допустить короткие неуникальные заголовки **только вместе с точным ID**, а не как identity.

**Эпизод:** директор не выбирает ни 2/4, ни 1/3; специализация номера вообще не используется. Два новых диалога названы по реальным поручениям.

**Плюсы:** пользователь сразу видит суть, меньше учёта свободных цифр и роль определена задачей. **Минусы:** длиннее обращения, неудобнее «проверь ЧАТ 2», UI-переименование вручную; задачи могут иметь похожие имена. **Риски:** Task ID также не доказывает открытый физический чат; нужна однозначная краткая текущая карта. **Цена:** малая/средняя, в основном переход интерфейса общения.

### F. Отдельный диспетчер назначений / интегратор

**Механизм:** директор решает _что и зачем_, а один координатор владеет очерёдностью, chat-instance ledger, пересечениями веток и launch messages. Worker берёт только конкретную задачу; QA остаётся независимым при реальной необходимости, а не создаётся ради цифр. Координатор может быть отдельным человеком/чатом или простой функцией GitHub, но не вторым равноправным реестром. Без доступа к пользовательскому UI также нуждается в подтверждении пользователя.

**Эпизод:** директор сообщает «две новые независимые задачи»; координатор выдаёт номера по единому live set, запрещает придумывать историческую специализацию.

**Плюсы:** разгружает директора, улучшает единый контроль параллельных задач/веток, совместим с частью предложений ЧАТА 4. **Минусы:** дополнительная роль, handoff и возможная очередь перед каждым запуском. **Риски:** очередной «проверяющий проверяющего», человеческая ошибка переносится другому агенту; если задачи редки, цена больше пользы. **Цена:** средняя/высокая, зависит от уровня автоматизации.

### G. Полный переход на GitHub issue/PR-first: чаты как одноразовые инструменты, без регистрации физических номеров

**Механизм:** один issue/task — одна authoritative карточка scope, owner, branch, progress и report; директорская Board заменяется проектным представлением GitHub issues, старые task files можно постепенно заменить issue body/шаблоном. Физические разговоры становятся временным способом выполнить ticket, не участвуют в state machine; пользователь запускает новый чат на нужный ticket и просит «проверь задачу #…». Координацию PR/HEAD/QA задаёт минимальная workflow-политика; status не выводится из переписки. Роль директора можно оставить только для приоритизации или убрать вовсе, если пользователь сам выбирает tickets.

**Эпизод:** два ticket получают исполнителей, без пары «2 и 4»; никакого реестра номеров. Задание и история доступны по одному ID.

**Плюсы:** существенно меньше дублирования task registry/Board/handoff, хорошо масштабируется, убирает категорию ошибок нумерации. **Минусы:** радикальная смена привычного интерфейса, перенос task history/website tasks page, работа по связям issue/PR, возможная чрезмерная сложность для личного проекта. **Риски:** часть фактов о реальных разговорах всё ещё не видна, просто становится несущественной; GitHub Issue labels не гарантируют успешную работу. **Цена:** высокая миграция, но потенциально низкая постоянная стоимость, если director/QA overhead тоже снижается.

### H. Отказ от нескольких director/worker бесед: единая рабочая сессия + GitHub state

**Механизм:** одна управленческая сессия ставит последовательно или в поддерживаемом workspace процессы, существенный код/данные/результаты немедленно сохраняются в GitHub; конкурирующие независимые задачи выполняются через native PR/issue actor, без ручного маршрута Chat 1/2/3. Существующая концепция Director/worker заменяется моделью «пользователь → queue/issue → уполномоченный исполнитель → GitHub». Реальные capabilities/доступность среды отдельно проверяются, не предполагать автоматический фоновый доступ к ChatGPT физическим чатам.

**Эпизод:** двух физических workers просто не требуется обозначать; задача определяется ticket и branch; проблема выбора «2 и 4» отсутствует.

**Плюсы:** минимум человеческой маршрутизации и промптов; потенциально сильнейший эффект вместе с сокращением повторных QA. **Минусы:** очень большая организационная перестройка, потеря удобства независимых чистых контекстов, риск лимита одной сессии, меньше полезной параллельности. **Риски:** перенос задач в единую сессию без GitHub state может ухудшить всё, от чего защищал текущий protocol; не подходит, если независимые параллельные review нужны действительно. **Цена:** высокая и неопределённая до пилота.

## 5. Сравнение и наиболее разумный маршрут выбора

| Вариант | Убирает неверный выбор цифры | Отличает поколения физического чата | Убирает дубли статусов | Операционная цена | Сохраняет «ЧАТ 1/2/3» |
| --- | --- | --- | --- | --- | --- |
| A. Минимальное правило | частично, при известной занятости | нет | нет | очень низкая | да |
| B. Единый ledger | да для заявленного active set | да | да при правильной миграции | средняя | да |
| C. GitHub allocator | да при корректном input | да, через B | как B | выше средней | да |
| D. Без повторного использования | устраняет сам reuse-выбор | да по уникальному номеру | нет | низкая | нет, номера растут |
| E. Task-name вместо цифры | не нужен выбор цифры | task ≠ physical instance; нужна карта | частично | низкая/средняя | нет |
| F. Координатор | при правильном исполнении | зависит от ledger | зависит от режима | средняя/высокая | да |
| G. Issue-first без слотов | категория ошибки исчезает | не требуется для task state | потенциально да | высокая миграция | нет |
| H. Без мультичата | категория ошибки исчезает | не требуется | потенциально да | высокая/неопределённая | нет |

**Быстрое исправление ≠ хорошая архитектура.** A подходит буквально к следующему назначению без QA, но ничего не делает с долгоживущей причиной: registry хранит 125 задач и не хранит физические instances; Board/handoff/bootstrap дублируют состояния. B убирает именно эту категорию неоднозначности, не ломая пользовательские короткие «ЧАТ N». C стоит откладывать: автоматический lock оправдан только при реальной гонке двух одновременных назначений, а не в ответ на единичный произвольный выбор. Если пользователю на самом деле не нужны цифры, E проще B; если одновременно раздражают director PR conflicts, чрезмерные проверки и ручная регистрация, G следует сравнить с идеями параллельного аудита ЧАТА 4. F может оказаться полезным интегратором, но вводить его только ради нумерации — вероятная новая бюрократия.

**Мой условный выбор:** A для ближайшего реального назначения; B для сохранения текущего пользовательского интерфейса в долгую, с устранением duplicate live Board/handoff; G как радикальный кандидат **если** пользователь хочет прежде всего избавиться от самой multi-chat orchestration. Это не разрешение внедрять B или G без отдельного решения.

**Что можно убрать:** live status из handoff и bootstrap, повторные активные worker-role labels в исторических Board-разделах, псевдороли привязанные к номеру, обязательный per-assignment multi-file sync (при B/G). **Что сохранить:** точный task/разрешение, branch/PR conflict ownership, различение user-confirmed launch и planned, конкретные merge/CI ограничения — но только в одном релевантном contract; не дублировать их как новые нумерационные gates.

## 6. Следующий пилот без дополнительной QA-цепочки

1. Оставить текущие физические ЧАТ 1/2/4 без смены номеров и без вмешательства в их отчёты/PR.
2. При **следующем** пользовательски разрешённом назначении директор единожды формирует компактную строку вида: «Заняты: ЧАТ 1, 2, 4 (подтверждено пользователем на дату X); свободен: ЧАТ 3; следующему НОВОМУ диалогу — ЧАТ 3». Если актуальное множество неизвестно, запрашивает один факт вместо вымысла; пользователь может подтвердить/исправить. Не требовать отдельного QA чата.
3. Если pilot очевидно работает и пользователь хочет оставить нумерацию, следующим **одним** изменением operating model выбрать B: убрать конкурирующие живые записи в пользу одного chat-instance ledger; провести миграцию только текущих известных активных назначений, архивные записи не переводить в ложные live instances. Не вводить allocator C до реальной необходимости.
4. Если пилот показывает, что пользователю нужны именно задачи, а не чат-номера, сразу предпочесть E или G, не строить ledger только потому, что он технически возможен.

**Acceptance пилота:** один короткий точный адрес запуска, user understands new/existing, нет коллизии с объявленными активными физическими чатами, задача ищется по task ID в GitHub; _никакой отдельной PR/CI/QA проверки цифры_. Если пользователь подтверждает другой реальный набор открытых чатов, выбор корректируется до запуска; старые созданные чаты не переименовывать.
