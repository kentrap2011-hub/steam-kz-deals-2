# Диагностика: почему директорские команды запуска удлиняются

**Task:** `director-launch-prompt-length-drift-diagnosis-01` · **ЧАТ 5** · 2026-10-25  
**Источник:** `kentrap2011-hub/steam-kz-deals-2`, `main`. **Режим:** независимый read-only RECON, report-only draft PR.

## 1. Подтверждённые факты

1. Действующая схема уже требует сохранять все подробности в отдельном `WORKER_TASK_<ID>.md`, а пользователю отправлять **короткую** команду. Прямой шаблон запуска есть в [DIRECTOR_PROTOCOL.md, §2, строки 62–74](https://github.com/kentrap2011-hub/steam-kz-deals-2/blob/main/DIRECTOR_PROTOCOL.md#L62-L74); то же повторяет [DIRECTOR_BOOTSTRAP.md, строки 30–42](https://github.com/kentrap2011-hub/steam-kz-deals-2/blob/main/DIRECTOR_BOOTSTRAP.md#L30-L42).
2. В копируемом сообщении обязательно сохранять точный репозиторий, `main`, запрет иных репозиториев, `CHAT_PROTOCOL.md` → START gate, именованный task-файл и номер `ЧАТ N`. Отдельно требуется сказать «НОВЫЙ/СУЩЕСТВУЮЩИЙ» и поместить копируемый текст в отдельный блок: [DIRECTOR_PROTOCOL.md, строки 75–110](https://github.com/kentrap2011-hub/steam-kz-deals-2/blob/main/DIRECTOR_PROTOCOL.md#L75-L110), [строки 125–136](https://github.com/kentrap2011-hub/steam-kz-deals-2/blob/main/DIRECTOR_PROTOCOL.md#L125-L136), [CHAT_PROTOCOL.md, строки 44–52](https://github.com/kentrap2011-hub/steam-kz-deals-2/blob/main/CHAT_PROTOCOL.md#L44-L52).
3. **Точка пробела:** §2 говорит «**по умолчанию** директор не отправляет ... длинный prompt» ([строка 64](https://github.com/kentrap2011-hub/steam-kz-deals-2/blob/main/DIRECTOR_PROTOCOL.md#L64)), а HANDOFF PRE-SEND проверяет наличие обязательных полей и согласованность назначения, **но не запрещает переписывать содержимое task-файла в копируемом блоке** ([строки 125–136](https://github.com/kentrap2011-hub/steam-kz-deals-2/blob/main/DIRECTOR_PROTOCOL.md#L125-L136)). Формально можно выполнить все шесть пунктов и всё равно вывести 20–40 строк пересказа. Сама схема правильная; место утечки — **проверка итогового текста ответа**, а не регистрация задач.
4. Актуальная [Board, строки 8–13](https://github.com/kentrap2011-hub/steam-kz-deals-2/blob/main/DIRECTOR_TASK_BOARD.md#L8-L13) уже регистрирует этот ЧАТ 5 и разделяет его с QA ЧАТ 2/4. [DIRECTOR_BOOTSTRAP.md, строки 5–9](https://github.com/kentrap2011-hub/steam-kz-deals-2/blob/main/DIRECTOR_BOOTSTRAP.md#L5-L9) и [DIRECTOR_HANDOFF_CURRENT.md, строки 6–8](https://github.com/kentrap2011-hub/steam-kz-deals-2/blob/main/DIRECTOR_HANDOFF_CURRENT.md#L6-L8) прямо помечают старые назначения/состояния как исторические; они не источник актуальных поручений. В [примере нынешней задачи ЧАТ 2](https://github.com/kentrap2011-hub/steam-kz-deals-2/blob/main/WORKER_TASK_DOSSIER_V2_PR274_ENABLED_FIX_FINAL_INDEPENDENT_QA_01.md#L20-L47) все критерии и запреты уже находятся в GitHub — повторять их при запуске не нужно.
5. [CHAT_CONTEXT.md](https://github.com/kentrap2011-hub/steam-kz-deals-2/blob/main/CHAT_CONTEXT.md) требует экономить контекст; [DIRECTOR_PROTOCOL.md, строки 263–271](https://github.com/kentrap2011-hub/steam-kz-deals-2/blob/main/DIRECTOR_PROTOCOL.md#L263-L271) объясняет: длинные переносимые prompts были причиной появления отдельного task-файла.

## 2. Почему возникает «дрейф»

**Доказанный дефект формулировки:** «по умолчанию» не определяет исключения; не указан прямой запрет на пересказ task-содержания внутри копируемого блока. **Доказанный дефект контроля:** проверка HANDOFF PRE-SEND подтверждает наличие полей, но не компактность. Это даёт возможность длинному ответу пройти существующие gates.

**Правдоподобные, но не доказанные механизмы:** директор может перестраховываться и повторять контекст, тесты и запреты, которые видит в Board/задании; длинные сообщения могут становиться примерами для следующих сообщений; после ротации чата исторические разделы bootstrap/handoff увеличивают объём видимого текста. Более длинный контекст способен повышать риск ошибки выбора формата. Эти объяснения нельзя объявить фактической причиной действий модели по одному репозиторию.

**Предел доказательств:** сообщения пользователя подтверждают жалобу, но у проверки нет полных стенограмм всех физических директорских чатов с датами и длинами запусков. Поэтому частоту, кривую роста и причинную связь **не измеряли**. ЧАТ 4 / PR #272 и предложенный #275 касаются другого дефекта — понятности языка; их решения не подменяют проверку длины запуска.

## 3. Сравнимые запуски одной и той же задачи

Оба образца предполагают, что директор отдельно пишет: **Куда отправить: НОВЫЙ ЧАТ — ЧАТ 5**; сообщение скопировано отдельным блоком. В обоих случаях реальный объём полномочий определяется **тем же task-файлом**, а не числом строк запуска.

**Раздутый (пример неверной практики; составлен для сравнения, не цитата реального запуска):**

```text
ЧАТ 5 — диагностика директорских промптов
Repository: kentrap2011-hub/steam-kz-deals-2
Source of truth: main
Не читай и не используй другие репозитории; если инструмент открыл другой, сначала переключись.
Сначала прочитай CHAT_PROTOCOL.md из main и выполни START gate.
Затем прочитай WORKER_TASK_DIRECTOR_LAUNCH_PROMPT_LENGTH_DRIFT_DIAGNOSIS_01.md.
Изучи правила директора, Bootstrap, Board и handoff.
Установи, почему промпты становятся длиннее, не выдумывая мотивов.
Сравни два варианта сообщения; укажи точный дефект gate.
Предложи одно минимальное решение без скриптов и CI.
Не меняй протокол, контракты, код, registry, Board, production.
Не запускай Research, Assembly, workflows или задачи по расписанию.

```

**Оптимальный — для нового директорского чата как образец выдачи ЧАТУ 5:**

```text

Repository: kentrap2011-hub/steam-kz-deals-2
Source of truth: main
Работай только в этом репозитории; если открыт другой, сначала переключись.
Сначала прочитай CHAT_PROTOCOL.md из main, выполни START gate. Затем полностью выполни WORKER_TASK_DIRECTOR_LAUNCH_PROMPT_LENGTH_DRIFT_DIAGNOSIS_01.md.
```

## 4. Одно минимальное исправление — на решение директора

**Файл и место:** `DIRECTOR_PROTOCOL.md`, §2, **заменить существующую строку 64**, не добавляя новый пункт checklist:

> **Для зарегистрированного WORKER_TASK директор передаёт пользователю только короткий маршрут запуска: номер ЧАТ N, repository/main и запрет другого репозитория, вход через CHAT_PROTOCOL.md/START и точный task-файл. Запрещено переписывать в копируемой команде цель, проверки, запреты, контекст и итог из task-файла; всё это остаётся в GitHub.**

Это конкретизирует уже существующее требование, действует после ротации, потому что новый директор читает действующий §2, и не плодит второй протокол. Простой признак соблюдения при **существующем** просмотре копируемого блока: в нём только адреса/вход/идентификация; если виден повтор проверок или запретов из task-файла — текст необходимо сократить. Никакого отдельного ритуала, теста, CI или нового документа не нужно.

**Архитектурная граница:** меняется лишь возможная будущая формулировка director handoff. GitHub по-прежнему владеет зарегистрированным task/Board/registry и production control plane; копируемый запуск ничего не исполняет автоматически. Настоящую правку сейчас **не вносили**.
