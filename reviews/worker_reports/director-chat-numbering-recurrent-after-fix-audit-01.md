## Executive summary

**Новая ошибка — не счёт 1, 2, 3 и не доказанная нехватка свободных номеров.** Директор ответил на вопрос о *занятости физических бесед ChatGPT* как будто GitHub-статусы задач позволяли определить, какие из этих бесед доступны. По переданному case он объявил 2–5 «свободными» и предложил переназначить только что зарегистрированные новые ЧАТЫ 6–8 на 2–4, хотя пользователь **не просил переназначения**. Завершение задачи, наличие worker-report или закрытие PR не являются свидетельством закрытого, удалённого, пригодного для повторного использования либо вообще открытого физического чата.

Предыдущий независимый [аудит #306](https://github.com/kentrap2011-hub/steam-kz-deals-2/pull/306) диагностировал именно отсутствие наблюдаемой physical-chat identity и путаницу labels. Принятый [PR #308](https://github.com/kentrap2011-hub/steam-kz-deals-2/pull/308) **действительно** уточнил минимальный подтверждённо свободный номер, отсутствие специализации номера и необходимость пользовательского подтверждения запуска/закрытия, но изменил **только текст DIRECTOR_PROTOCOL.md**. Не появился ни отдельный источник подтверждения физической беседы, ни проверяемый ответный маршрут для вопроса «эти чаты заняты?», ни ограничитель *самовольного предложения переназначить уже запущенные/зарегистрированные слоты*. Следовательно, ранее исправили **правило выбора при новом REGISTER**, но не **эпистемический маршрут read-only вопроса о доступности**. Наличие явной нормы и её нарушение подтверждаются; механизм, по которому модель её проигнорировала, из GitHub восстановить нельзя.

**Выбор одного ближайшего изменения:** в отдельном, пользовательски одобренном небольшом governance PR **заменить**, а не дополнить, текущую строку STATUS/чатового статуса в DIRECTOR_PROTOCOL.md на явный read-only **CHAT_AVAILABILITY response contract**: (1) возвращать отдельно только GitHub-назначение/состояние задачи; (2) доступность *физического* чата показывать как UNKNOWN, если нет прямого актуального подтверждения от пользователя; (3) не классифицировать «свободен» по PR/report/status, не вычислять новый слот и **не предлагать/не выполнять переназначение**, если пользователь спросил только о занятости; (4) лишь при отдельном желании пользователя освободить/назначить слот запросить недостающее подтверждение и перейти в REGISTER. Это изменение **не является повтором** старого алгоритма «минимальный свободный»: оно отделяет тип вопроса от операции назначения и убирает сам ошибочный переход к переименованию. Реализуется одной заменой в существующем protocol, без новых CI, ролей, JSON-реестров, worker-цепочек и автоматизаций. Текстовый gate не может технически гарантировать поведение ChatGPT: полная внешняя принудительность потребовала бы отдельной UI-интеграции, которая здесь несоразмерна.

Текущие назначения **1–8 сохраняются без изменений**. Этот отчёт не даёт разрешения перенумеровывать их.

### Конкретный case 28 октября

**Confirmed GitHub:** PR #320 зарегистрировал **НОВЫЕ физические ЧАТЫ 6, 7, 8** для трёх различных задач; эти имена сохранены в актуальном Board и registry. В main также есть нормы §2/§10 DIRECTOR_PROTOCOL.md: GitHub task status сам по себе не свидетельствует об открытии/закрытии, новый номер выбирается из **подтверждённо** свободных, переназначать уже запущенное по догадке нельзя.

**Supplied case от пользователя (не GitHub transcript):** после регистрации пользователь спросил «А чаты 1–5 заняты?». Директор посмотрел Board/PR, по завершённым старым задачам/отчётам объявил 2–5 «свободными» и предложил переместить только что назначенные 6–8 в 2–4. Пользователь отверг изменение номеров и запросил данный аудит. Прямой transcript директорской беседы недоступен из GitHub; слова и мотивы не выдаются за независимую запись.

**Что можно было сказать доказательно:** названия последних поручений, поля worker_slot и status, существование PR/отчётов, завершение отдельных *работ*, наличие регистрационных назначений 6–8. **Чего нельзя было узнать:** какие именно беседы ChatGPT 1–5 физически открыты, продолжаются, завершены пользователем, сохранены им, доступны для повторного использования или какому поколению одного номера принадлежат. Даже status=complete или merged PR это не доказывают.

**Дополнительная проверка против упрощения «2–5 все свободны»:** текущий registry содержит, например, active giveaway-itad для ЧАТА 2 и active audit-task для ЧАТА 5 (у #319 отчёт уже в draft, но registry и состояние физической беседы не тождественны); также есть старые blocked элементы с теми же номерами. Это демонстрирует неоднозначность даже вычисления «последнего relevant task» из всех элементов registry. Не превращать active в доказательство открытого UI чата, а complete/blocked — в доказательство свободного.

**Суть ошибки — две отдельные недопустимые операции:**
1. **Evidence/type error:** преобразование «у старой задачи есть отчёт / задача завершена» в «физический чат свободен». Это не арифметическая ошибка; множество подтверждённо занятых физических instances не задано.
2. **Intent/authority error:** преобразование вопроса «заняты ли?» (чтение) в предложение **изменить уже утверждённые номера** 6–8. Никакого запроса на их изменение не было. Даже если бы 2–5 были подтверждённо свободны, это само по себе не повод переносить регистрационные назначения 6–8.

**Вероятный, но недоказанный механизм:** директор применил STATUS/DECIDE lookup GitHub и использовал знакомые task completion signals как прокси для физической доступности; затем попытался ретроспективно «оптимизировать» номера уже оформленных assignments. Нет данных, позволяющих отличить с уверенностью context drift, невнимательное чтение §2/§10, эвристику заполнения пробелов и влияние старых Board/handoff snapshots.

### Предлагаемое конкретное implementable изменение (не выполнено этим аудитом)

В **отдельно авторизованном коротком L1 governance PR** заменить в DIRECTOR_PROTOCOL.md строку типа **STATUS — «Проверь ЧАТ N»** или её часть, относящуюся к состоянию physical conversation, одним специализированным правилом принятия решения **CHAT_AVAILABILITY**. Вместо обобщённого «проверь физический слот» определить точную ветку для запроса «заняты / свободны / можно ли повторно использовать ЧАТ 1–5?»:

> Ответ только на запрошенный статус. GitHub даёт сведения о задачах и назначениях, **не** о доступности физической беседы. На неподтверждённый physical state отвечать «неизвестно», не выводить «свободен» из status/PR/report. При вопросе о занятости не вычислять новое назначение, не предлагать и не делать переназначение уже выданных ЧАТ N. Если пользователь **отдельно попросил новый слот/reuse**, уточнить только неизвестные физические факты у пользователя, затем применять уже существующий REGISTER/минимальный свободный и синхронизировать Board/registry после явного решения.

Здесь ключевой механизм — **fail-closed выход для отдельного типа пользовательского запроса** плюс **read-only → mutation separation**. Он не заменяет старое правило minimal-free; оно остаётся корректным только при действительном новом назначении. Убрать из существующей STATUS-формулировки возможность предполагать, что Board «устанавливает точный физический слот» в смысле доступности UI; Board устанавливает **заявленное назначение Task ID**, не текущую открытость диалога. Для изменения достаточно одной согласованной текстовой замены, без нового task registry и CI. Никаких L3 полномочий, production, scheduler, queue или ownership не затрагивается. **Абсолютного технического enforcement ответа модели в текущем ChatGPT UI нет**; это наименьший целесообразный implementable шаг в существующей модели, а не обещание безошибочности каждого будущего ответа.

**Пример правильного ответа на тот же вопрос:**

> По GitHub я могу проверить, какие задачи числятся за ЧАТАМИ 1–5 и какие PR/отчёты уже готовы. Но из этого нельзя определить, какие физические беседы в ChatGPT сейчас заняты или свободны; это мне неизвестно без твоего подтверждения. ЧАТЫ 6–8 уже назначены, их номера не меняем. Если ты захочешь позже переиспользовать 1–5, уточним только нужные номера.
