## Что подключено

- В уже существующем `.github/workflows/ingest-taste-steam-review-dossier-checkpoint.yml` добавлен **только ручной, по умолчанию выключенный вход Notes V2**. Он передаёт GitHub-привязки (исходный marker, trial и пары исходных Research/Assembly Git-коммитов для игр) в уже написанный `drain_buffered_groups(notes_v2=...)`.
- Вход использует ту же общую блокировку `taste-steam-review-dossier-canonical-writer`, тот же механизм подготовки файлов, одну фиксацию Git и успешную отправку в `main` как границу подтверждённого сохранения. Новый writer, workflow, планировщик или автоматический повтор не создавались.
- Обычный V1 всё ещё запускается только по прежнему `push` и выполняет прежние шаги. Ручной запуск с неотмеченным разрешением **не запускает V1**. V2 не меняет старую проверку и приём трёх игр.
- V2-only `config/dossier_notes_v2_individual_writer_contract.json` теперь явно определяет приоритет **поштучной приёмки только для явно выбранного режима V2**, даже если старый исходный контракт ещё описывает приём тройкой. Изменяемый другим PR #266 `config/dossier_research_notes_v2_contract.json` не тронут.
- Для живого V2-вызова **одновременно** нужны отдельные разрешения в исходном Notes V2, в новом контракте writer, одобрение подключения и одобрение безопасности передачи в Deep. Сейчас все эти разрешения выключены; запрос запуска сам их не включает. Вход повторно проверяет исходные неизменяемые Git-данные и существующий строгий валидатор. Готовность игры из предварительного отчёта не считается приёмкой.
- Результат игры и её точное подтверждение готовятся в существующем `data/cache` + `data/control` и попадают в одну общую Git-транзакцию. При отказе записи этой транзакции нельзя сообщать успех. При конфликте с существующим V1-кэшем другая версия файла не перезаписывается; судьба таких конфликтов остаётся предметом отдельного решения перед включением.

## Проверка A / B / C

Сценарий на синтетическом исходном Git-маркере и неизменных исходных 18 назначениях:
- A — строгая проверка пройдена, подготовлен и записан результат с подтверждением.
- B — заведомо ошибочный финальный результат, отклонён, не записан.
- C — строгая проверка пройдена и сохранена независимо от B.
- Следующая пригодная игра из другой исходной тройки проходит, хотя B не исправлена.
- Повторная обработка A/C не создаёт другого результата; расходящиеся записи отвергаются отдельно. Ошибка записи подтверждения прерывает всю общую транзакцию.

**Дополнительный реальный Git-тест без GitHub-публикации:** тот же проверенный V2-код на одноразовых тестовых данных вызывает действующий `stage_taste_dossier_canonical_writer.sh`, создаёт **один** Git-коммит с результатами и подтверждениями A/C, затем успешно отправляет его в **локальное одноразовое bare-хранилище**; B в коммите нет. Тест выполнен в GitHub Actions: `Validate inactive Dossier final GitHub acceptance integration`, запуск [40172701850](https://github.com/kentrap2011-hub/steam-kz-deals-2/actions/runs/40172701850), сам новый тест `test_v2_github_writer_hookup_single_transaction` — **OK**. Все 16 тестов его основной V2/V1 final-acceptance группы прошли; у общего запуска были другие проверки, включая сначала устаревшее требование не иметь никакого ручного входа. Это требование в затронутых V1-тестах уточнено: по-прежнему нельзя запускать V1 вручную, а V2 допускается только выключенным отдельным входом.

**Граница подтверждения:** результаты и подтверждения A/C попали в Git-коммит и были проверены в тестовом **локальном** хранилище, на машине GitHub Actions. Это **не** подтверждение настоящей публикации V2 в удалённом `main`: живой вызов не выполнялся, флаги выключены, настоящих 18 игр мы не обрабатывали. Изменения кода PR #274 действительно сохранены на GitHub. Существующий V1 writer и production не запускались этим заданием.

## До реального испытания 18 игр

1. Независимо проверить точный итоговый HEAD PR #274 и применимые GitHub checks; решить обнаруженные независимые/нестабильные старые тесты по их владельцу. Убедиться в безопасном совместном состоянии PR #266 и #270 перед использованием настоящих входных Git-привязок.
2. Отдельно утвердить V2-only поштучную публикацию, политику конфликтов с ранее принятым V1-кэшем и то, когда Deep разрешается использовать новый результат. До этого никаких автоматических признаков Deep-ready не создавать.
3. После принятия кода и отдельного разрешения на запуск включить соответствующие контрактные разрешения и один раз передать действительные marker/trial/Research/Assembly пары в существующий заблокированный общий механизм GitHub. Только успешно сохранённые **в удалённом GitHub `main`** результат и подтверждение каждой игры будут означать настоящую приёмку; повторные попытки не подразумеваются.

**Architecture preflight:** владелец scope, проверки и записи — GitHub; исключительно его существующий сериализованный writer; новый ручной вызов не переносит эту ответственность в чат и не вводит очередь/планировщик/квоту или второй способ публикации. `main`, production, Scheduled Tasks, настоящий Research/Assembly, текущие принятые игры и PR #266/#270 не менялись.

**Почему проверка заняла дольше:** пришлось прочитать канонические границы записи и старые проверки, затем дождаться результатов GitHub Actions и уточнить два старых теста, запрещавших любой ручной вход. Это изменение сохранено в PR, чтобы тот же конфликт не повторился при следующей проверке.
