## 1. Decision-ready conclusion

**What is proven:** the live GitHub-owned collector repeatedly received actual HTTP **429** from `store.steampowered.com/api/appdetails` during full parent-targeted DLC discovery, including after a bounded-retry change. HTTP 429 itself means an upstream rate-limit/refusal signal. The request's app ID is **not** evidence of an invalid game. A green PR regression is **not** a live-collection acceptance result.

**Most likely causal class, confidence MEDIUM:** the required quantity/cadence of independent Storefront appdetails lookups exceeds an undocumented effective Store request budget or reaches its blocking state during the run. The program's ideal continuous 0.9-second inter-start pacing allows about **333 calls/5 minutes**. This is above older independent **200 appdetails calls/5 min** observations and even a separate unofficial **300 total Store calls/5 min** estimate. Those values are *not official, not validated for this environment or 2026*, and the actual rolling request counts in our failing run are missing. The aggregate 436 parents/616s cannot prove a five-minute burst; retries and other phase time are mixed in. **Do not declare an exact Valve quota, per-IP allocation, or required new pacing.**

**Competing explanations:** the dynamically shared GitHub Actions outbound egress IP may have pre-existing reputation/other users' traffic (plausible, not established); longer-lived security/CDN/WAF gating may outlast short retry cooldowns (plausible, not established). Exact per-IP vs per-session/client, country/language or cookie partitioning is **unknown**. No 429 response headers, precise first-429 ordinal, 403 sequence, IP identity or per-AppID attempt count are available from cited run logs.

**Single next action for Director to authorize separately:** a **bounded observability-only change** in the existing GitHub-owned appdetails collector, with no traffic-rate, retry, quota, completeness, stage or schedule changes. In the next ordinary production main run, record sanitized per-request status, monotonic timestamp/rolling 300-second count, stage (parent relation vs DLC price), retry ordinal, and presence/sanitized value of `Retry-After`, plus first-429 and 403 summary; correlate with total requests made by this process. Never log credentials/cookies/secret URLs or probe Steam independently. This can distinguish repeatable load/rolling-window correlation from early refusal, and whether short retry cooldowns can recover; egress-identity attribution may still need later separate evidence. No implementation is authorized by this report.

## 3. Ten external sources — dates, grades, limitations

Grades: **A** official documentation of what it actually covers; **B** independent direct developer observation/experiment, not a Valve guarantee; **C** community maintained estimates, limited or unverified methodology. Publication/last-update dates distinguished from access dates.

1. **[A] Valve Steamworks Web API Overview** — [official doc](https://partner.steamgames.com/doc/webapi_overview?language=english), accessed 2026-11-04 (undated page). Published public Web API host is `api.steampowered.com`, partner host is `partner.steam-api.com`; IP rate-limit warning about 403 explicitly concerns the **partner host** and cannot be copied to `store.steampowered.com/api/appdetails`. Short quote: “The public Steamworks Web API is accessed” via `api.steampowered.com`.
2. **[A] Valve Steam Web API Terms of Use** — [official terms](https://steamcommunity.com/dev/apiterms), **last updated July 2010**, checked 2026-11-04. Short quote: “one hundred thousand (100,000) calls ... per day.” This belongs to licensed Steam **Web API**, not a verified Storefront appdetails allowance or rolling per-IP limit.
3. **[B] SteamDB / xPaw direct engineering writeup** — [Store Prices](https://steamdb.info/blog/store-prices-api/), original **2013-02-05**, explicit **2015-07-20 update**. Short quote: “rate limited to 200 requests per 5 minutes”. It documents the *Storefront* `appdetails` change, including the disabling of unrestricted multi-AppID full details. Valuable firsthand but **11-year-old limit observation**, not a 2026 Valve rule.
4. **[C] Revadike InternalSteamWebAPI wiki, appdetails page** — [Get App Details](https://github-wiki-see.page/m/Revadike/InternalSteamWebAPI/wiki/Get-App-Details), last modified **2024-04-12**. Claims 200/5min, and for multiple AppIDs only `filters=price_overview` works; without filter/multiple filters it reports `400` + `null`. Community documentation, no dated test setup.
5. **[C] Revadike wiki homepage** — [Home](https://github-wiki-see.page/m/revadike/internalsteamwebapi/wiki), last modified **2026-10-26**. Short quote: “global limit to 300 store requests per 5 mins”; endpoint-specific limits listed separately. **300** is an alleged host-wide Store budget; **200** is an alleged appdetails-specific budget. They measure different scopes and are not proof of contradictory Valve policy or of our specific per-IP bucket.
6. **[B] gofurry/steam-go experiment** — [Storefront AppDetails Rate-Limit Experiment](https://github.com/gofurry/steam-go/blob/main/docs/experiments/store-rate-limit-20260607.md), **2026-06-07**. Two 360-request runs; 3 AppIDs × 3 cc × 2 languages × 20 repeats; 10 workers, no interval/retry/proxy, second after about five minutes. Both runs reported **228 OK / 132 failed**; 429 around request 220–233, later 403 around 263–267, plus first-run transport timeouts. Reproducible **within that aggressive traffic configuration**, not evidence that our 0.9s pacer or GitHub egress shares the same limit/window. Does not independently prove IP vs session vs other identity.
7. **[B/C] deivit24/python-steam-api community issue #55** — [July 21, 2025 comment](https://github.com/deivit24/python-steam-api/issues/55). User reports `appdetails` 200 calls/300 seconds and HTTP 429, with **no `Retry-After` on their observed error**. The issue does not attach raw response traces or controlled measurement; weight lower than the steam-go experiment. Its missing `Retry-After` observation **does not prove our response lacked it**.
8. **[B] syntaxerrors/Steam issue #69** — [2018-02-28](https://github.com/syntaxerrors/Steam/issues/69). Firsthand example: multi-ID `appdetails` without `filters=price_overview` gave 400; with that single price filter it worked. This undermines batch collection of **parent `dlc` / child `fullgame` / `type`**; working *price-only* batch is not a substitute for required verified parent membership.
9. **[B/C] nickxudotme/steam-cli** — [README section Cache and Rate Limits](https://github.com/nickxudotme/steam-cli), checked 2026-11-04, **README observation date not independently stated**. Reports normal 200 `appdetails` `Cache-Control: public,max-age=3600`, `Expires`, `Last-Modified`, no remaining-quota header; implements caching by `appid+cc+lang`. It does **not** document 429 headers for appdetails. `IStoreBrowseService/GetItems` provides purchasing data but their `dlc` command still uses **`appdetails.dlc` for parent membership**.
10. **[A] GitHub Actions egress documentation** — [About GitHub's IP addresses](https://docs.github.com/en/authentication/keeping-your-account-and-data-secure/about-githubs-ip-addresses), accessed 2026-11-04. Officially states dynamically allocated IP addresses from **shared infrastructure**, and other tenants can affect public IP reputation. This supports egress reputation/neighbor traffic as a real hypothesis, **not** a diagnosis of our runs or proof of a shared Steam rate counter.

**Official-numeric-result:** Across the accessed Valve terms/Steamworks reference, there is **no verified, Valve-published numeric 429 requests-per-IP/5-minute budget for `store.steampowered.com/api/appdetails`**. Neither the official 100,000/day Web API Terms nor the official partner 403 note transfers to it. 200 and 300 are distinct third-party estimates, not operational truth to encode in policy.

## 5. Remedies considered, without choosing or implementing them

- **Conservative shared global pacing + appropriate terminal cooldown:** technically consistent with old Storefront observations; unlike solely retrying it reduces the *initial* arrival rate. However `1.5s`, `1.8s`, `2s` and `200/5m` are **not guaranteed safe values**; 3 workers share a pacer already. A slower full base+child pass increases collection time; verify real workload and the existing 60-minute/01:00/freshness constraints before approving any runtime change.
- **Exact fresh cache reuse:** may reduce duplicate physical reads, only where valid authority already exists and the complete parent DLC membership, exact AppID, KZ currency, current price/discount and source timing remain provably current. Old parent relations are not automatically today's complete truth; partial/stale data cannot satisfy fail-closed paid scope. Designing persistent validity is separate contract work.
- **Bounded cooldown/checkpoint inside one GitHub-owned daily cycle:** may help long windows but does not itself lower total upstream workload. No new recurring runner, second queue, cross-day quota, forced 'success', or ChatGPT ownership; must account for elapsed budget, state durability and exact-cycle completeness.
- **Multi-AppID batch:** price-only with `filters=price_overview` has actual independent examples; required `dlc` parent list, child `type` and `fullgame` relation have **no trustworthy verified batch equivalence**, with documented 400/null for unrestricted multi-ID detail. Hence not an authorized general replacement; a later read-only bounded verification/contract proof would be required even for price-only substage.
- **HTTP conditional requests:** some 200 appdetails responses expose `Last-Modified`/cache headers, but no evidence that `If-Modified-Since`/ETag gives reliable 304, avoids Store throttling, or preserves KZ price freshness. Not justified as the immediate fix.
- **Alternative documented interfaces:** Steamworks public Web API and `IStoreBrowseService/GetItems` are not demonstrated to provide the same current **parent-to-DLC** verified relation and exact KZT paid-child fields with identical semantics. A separate compatibility/evidence task would be needed, not a silent endpoint swap.
- **Rejected:** skipping eligible parents, shrinking required scope/top-N, stale backfill, substituting SteamDB/global DLC search, switching cc to non-KZ, bypassing 429 with proxies/rotating IPs, adding scheduled stages, changing quota to make the run green, or treating a PR-only green test as live acceptance.
