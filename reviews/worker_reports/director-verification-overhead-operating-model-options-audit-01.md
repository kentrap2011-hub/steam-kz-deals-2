# ЧАТ 4 — почему растёт стоимость проверок и как перестроить работу

**Task ID:** director-verification-overhead-operating-model-options-audit-01  
**Режим:** независимый evidence-based audit / варианты operating model; никаких изменений работающих правил.  
**Срез GitHub:** main 995edffee2c69394272cd5713f946e7056b1b11c, 2026-10-26. Дальнейшие статусы надо сверять с live PR; этот отчёт не является менеджером задач.

## Короткая сводка для пользователя

**Почему возникли лишние проверки.** Проект объединил правильный принцип «не принимать потенциально опасные изменения без доказательств» с несоразмерной практикой «любой worker, PR и новый HEAD обязательно проходят независимую QA, а каждая задача имеет отдельный task, registry, Board, handoff и report». Из-за этого отчёт без изменений кода создаёт новый HEAD, новый HEAD формально обнуляет QA, новые назначения изменяют общие служебные файлы, конфликт этих файлов требует нового PR и ещё одной QA. Несколько актов проверки подтверждают лишь отсутствие доступа к исполняемой среде — а не дефект системы. Эти требования в основном наши Markdown-правила, не GitHub. При этом проверка действительно находила существенные ошибки: QA-266-01 в происхождении freeze, QA #274 в противоречивом enabled path, а GitHub честно фиксировал конфликт #300 после #301.

**Сравнили семь моделей:** минимальное устранение рекурсивной QA; один конечный результат вместо каскада; проверку пропорционально риску; интегратора с единым владельцем общих файлов; один реестр без дублирующей ручной синхронизации; GitHub-first release pipeline; отказ от постоянной директорской иерархии для простых задач. Модели совместимы не полностью и могут применяться поэтапно.

**Предпочтение:** быстрый ограниченный эксперимент — варианты 1 + 3 и облегчённая часть 4: перестать сбрасывать QA из-за отчётов/статусов, классифицировать реальные изменения по риску, серийно обновлять общие управляющие файлы у одного ответственного. **Долгосрочно:** варианты 3 + 4 + 5 (GitHub источник фактов, один интегратор, отдельный QA только когда есть опасное изменение). Для опасных операций не отказываться от явного разрешения пользователя, точных scope/bindings, CI, независимой проверки критичного кода и реального end-to-end доказательства. Не внедрять архитектуру до отдельного выбора пользователя.

Значит, QA нужна для новых authority/activation paths, но проверка должна выбирать исполняемый опасный путь, а не механически повторять общий checklist.

## 2. Корневые механизмы перепроверок

1. **Нет типизации изменения, только всеобщий merge-gate.** Одинаковая процедура ставится для поправки однофразового launcher, report-only PR, исправления вычислений production и выдачи внешних полномочий. Это снижает долю полезных проверок.
2. **QA привязана к любому HEAD, а не к реально проверенной дельте.** Добавление обычного отчёта меняет Git SHA; не меняет исполняемый код, семантические instructions или результаты уже прошедшего тестового workflow. «Новый commit ⇒ вся QA обнулена» — локальная организационная норма. Material-file fingerprint или короткий delta-review точнее.
3. **Зависимые согласования оформляются несколькими независимыми PR.** Task registration → QA report PR → director status PR → reconciliation PR → новая QA. Каждая ветка может честно конфликтовать с другой. Нет единого сериализованного владельца registry/Board/handoff.
4. **Слишком много ручных проекций одного факта.** Live PR/CI показывает merge, worker-report показывает результат исполнения в момент написания; Board/JSON/handoff содержат скопированные статусы и стареют после следующего merge. Затем директор проверяет собственные копии и «исправляет рассогласование».
5. **Неудавшаяся среда выдаётся за следующую работу по проверке, хотя нужен новый маршрут исполнения.** #282→#289→#295 повторяли отсутствие checkout; успех дала одна узкая правка существующего GitHub runner.
6. **Происходит эскалация гипотетических threats в обязательные authority gates.** В #266 реальный structural bug оправдал specific correction; попытка доказать недоступную внешнюю аттестацию создала другой, самостоятельный блокер. Threat model личного проекта, последствия ложного принятия и реальная способность получить доказательство не сопоставлялись.
7. **Самотестирование процедурной корректности.** Регистрация QA-работника изменяет статусные документы; это изменение снова нуждается в QA, как и переучёт QA. Система начинает оптимизировать проверяемость собственных реестров вместо получения работающего продукта.

Это не означает, что любая проверка искусственна. Реальны: несоответствие входных привязок, перезапись результатов, неверная активация, опасный workflow, реальная семантическая ошибка, коллизии commits и failure публикации. Проблема — безразличие между ними и служебным движением текста.

## 3. GitHub действительно требует vs собственные правила

| Вопрос | GitHub / механика данных | Текущая собственная процедура и её цена |
| --- | --- | --- |
| Разные ветки меняют одни строки | Конфликт нельзя автоматически безопасно объединить. Нужна фактическая интеграция; #300/#301 настоящий пример. | Требование, чтобы самостоятельный QA report и обновлённые Board/registry/handoff породили дополнительные stage/PR, не следует из GitHub. |
| Проверки CI | Workflow выполняет только указанные команды на определённом event/ref. Успех соседнего набора тестов не доказывает нужный набор; #270 наглядно. | Независимый отдельный физический чат QA для каждого PR и повторный полный exact-HEAD review после report-only commit — выбор директора. |
| Branch protection | На срезе main: API branch protected=false, rulesets пустой список. Нет подтверждения, что технически настроены mandatory status checks или запрет прямой записи; процедурная осторожность всё ещё полезна. | DIRECTOR_PROTOCOL самостоятельно запрещает MERGE без независимой exact-HEAD QA, успешных нужных CI и отдельного разрешения пользователя, даже без enforceable branch protection. |
| Ссылка на HEAD | Git SHA доказывает конкретный объект кода/истории; SHA меняется от любого коммита. Повторить обязательные CI для актуальной ref бывает разумно/нужно при реальной смене inputs. | Требовать полный новый человеческий review неизменённых implementation files после добавления отчёта не является требованием Git. |
| Immutable evidence | Для Git-owned state корректные single-add/first-parent/bindings и запрет overwrite защищают от реальной подмены/гонок в системе. | Отдельная новая независимая человеческая/Actions аттестация исторического freeze без доступного способа получить proof — введённая нами политика, не свойство Git. |
| Task metadata | GitHub может хранить issue/PR/label и реальные CI; задача не обязана получать новую ветку с тремя синхронизируемыми Markdown/JSON state. | Обязательный named task + registry + Board + handoff, отдельные report-only PR и последующая синхронизация статусов — договорённость проекта. |
| Реальный запуск | Merge и тесты не означают разрешение Research/Assembly или успешную production-публикацию. Это принципиальное различие. | Необязательно превращать каждый промежуточный технический приёмочный факт в новое обязательное ручное согласование. |

Оговорка: некоторые Markdown файлы являются **исполняемыми инструкциями для ChatGPT**. Изменение DIRECTOR_PROTOCOL.md или worker prompt не считается «безопасным только потому, что это Markdown». Безопасный report-only отличается от operational instructions.

## 4. Правило оценки ценности проверки

Проверка оправдана, если она отвечает на **новый и материалный** вопрос, который иначе остаётся неопределённым. Разделить четыре вида результата: (а) проверены тесты на конкретный implementation/content; (б) review рисков для опасного сценария; (в) PR технически может объединиться и нужные checks зелёные; (г) пользователь отдельно разрешил live action. Эти виды не заменяют друг друга, но не должны повторять друг друга.

Предлагаемая матрица как вариант для обсуждения, НЕ действующий контракт:

- **L0 — только фактический отчёт/описание статуса, не consumer-правило и не вход CI/worker:** сравнить список файлов, отсутствие иных изменений, проверить актуальную ссылку; никакого отдельного QA-chat, никакой recertification старого кода.
- **L1 — ограниченная безопасная governance/UI/документационная правка:** целевой смысловой review один раз и имеющиеся релевантные проверки. Если перенесена byte-equivalent дельта в чистую ветку — short delta check вместо холодного аудита всей задачи.
- **L2 — код, транспорт, алгоритм, тестовый workflow без live authority:** целевые регрессионные тесты в **реально исполняемом окружении**, проверка изменённых путей и failure mode; независимый QA только при неочевидном риске, сложном diff или обнаруженном дефекте.
- **L3 — production state writer, authorization, secrets, scheduler, material immutable input, live publish, денежные/персональные последствия:** независимая риск-ориентированная QA, актуальная CI, отдельный осознанный запуск, explicit scope, bounded end-to-end evidence; никакого автоматического ослабления fail-closed инвариантов.

На каждую QA задавать «какая новая гипотеза проверяется?», «какой ранний результат уже можно переиспользовать?», «что объективно изменилось?» и «кто может выполнить тест?». Если ответ «только новый SHA отчёта», полная QA не назначается. При отсутствии инструмента для запуска требуемого теста меняется **место запуска**, а не число QA-чатов.

## 5. Семь альтернатив operating model

Варианты альтернативны по масштабу и механике; их можно комбинировать только после явной сверки конфликтующих обязанностей.

### Вариант 1. Две точечные правки существующих правил (минимальный)

**Механизм:** в DIRECTOR_PROTOCOL.md заменить всеобщую инвалидизацию QA «после любого HEAD» на «после **материальной** дельты в проверяемых implementation/operational inputs». Существующие checks актуального PR HEAD остаются условием слияния, если их требует workflow/правило; отдельная human QA ранее проверенного материала переиспользуется с коротким перечнем diff. Второе изменение — после двух одинаковых недоступностей окружения не назначать новый QA до предъявления реально нового исполняемого пути. Director сам принимает простые низкорисковые административные обновления после существующей CI.

**#266:** оставить структурную QA полезного bug-fix; снять не обеспеченный данными новый gate только по отдельному решению пользователя. **#270:** после первой 0/14 сразу workflow runner; после report commit не полный re-QA. **#299:** одна review строки/существующий check, не новый review из-за чистого переноса того же diff. **#300:** GitHub merge conflict чинить адресно, проверять изменённую дельту, не переоткрывать #299.

**Устраняет:** самые очевидные возвратные петли. **Остаётся:** Board/registry/handoff всё ещё нужно поддерживать, могут появляться новые конфликты, директор всё ещё много решает вручную. **Цена:** малая, 1 узкий protocol PR с доказательством сохранения stop для опасного merge; без новых Actions. **Скорость:** высокая немедленная выгода, контекст расходуется только на delta. **Ограничение:** критерий «материальности» не должен позволять маскировать executable/prompt changes под «документы».

### Вариант 2. Один пользовательский результат — одна сквозная приёмка

**Механизм:** Director определяет законченный deliverable: «неактивный V2 Research receipt реально проходит 14 tests», «новый Dossier разрешается и выпускается корректно», «короткий launch действует». Implementer может иметь несколько внутренних коммитов, но промежуточные отчёты и исправления не создают обязательную самостоятельную QA на каждую фазу. Один финальный интегрированный PR/ветка, одна целевая независимая приёмка на конечной кодовой версии, один merge; внутренние локальные тесты запускаются сразу по ходу.

**#266:** structural fix и решение о минимальном provenance проверяются в одном целевом end-to-end сценарии выдачи (до реального запуска — безопасно симулированном), без принятия промежуточных QA-исправлений как самостоятельных релизов. **#270:** разработка+включение тестовой команды в той же ветке, 14/14 до финального review, не три внешних аудита. **#299:** один diff без побочной регистрации. **#300:** merge resolution выполняется до конечной финальной приёмки единой интеграционной версии.

**Устраняет:** цепочки «проверка реализации → проверка исправления → проверка отчёта». **Остаётся:** большая финальная область риска, задержка независимых частей до общей готовности, batch сложнее review. **Цена:** средняя — перепроектировать задания по пользовательскому deliverable, а не по микрошагам. **Скорость:** быстрее для одной тесно связанной задачи, может быть медленнее при большом независимом потоке. **Контекст:** меньше новых чатов, но длиннее контекст конечного implementer/QA; ограничить scope продукта, не объединять несвязанные изменения.

### Вариант 3. Risk-based acceptance, без обязательного QA для всего

**Механизм:** каждому PR присваивается L0–L3 по последствиям **конкретного изменённого пути**, не по имени файла. Автор несёт ответственность за тесты; независимый reviewer нужен только для L3 и выбранных L2 с нетривиальным correctness/authority risk; Director проверяет решение, не воспроизводит все тесты. GitHub CI проверяет executable code, PR diff определяет material delta, а право на live semantic/production запуск остаётся отдельным шагом.

**#266:** L3 из-за выдачи полномочий/freeze; настоящий риск подмены покрывается структурными guards и конкретной QA, но не вводится невозможная историческая аттестация без обоснованного threat model. **#270:** L2, Existing Actions 14/14 + адресный inspect remote-auth gap; это не L3 реальный запуск. **#299:** L1, одна локальная проверка изменения поведения. **#300:** L0/L1 для статусов; serializer/интегратор разбирает конфликт, существующая task-registry CI, не полная независимая QA.

**Устраняет:** механическую равную дороговизну разных классов изменений. **Остаётся:** ошибка классификации может ослабить защиту; нужен короткий набор критичных файлов/эффектов и escalation-on-doubt. **Цена:** малая/средняя; договориться о критериях, заменить (не добавить рядом) прежний универсальный QA gate. **Скорость:** большая выгода на административных и небольших PR. **Контекст:** меньше QA-дубликатов, больше внимания к действительно опасным случаям.

### Вариант 4. Один интегратор / релиз-менеджер для общего state

**Механизм:** Director принимает цели, независимые developer-чаты меняют только свою ветку и fileset, QA проверяет опасную техническую дельту, **один назначенный интегратор** единолично переносит исправления, устраняет merge conflicts и обновляет Board/registry/handoff, проверяя текущий main непосредственно перед merge. Нельзя двум параллельным PR объявлять владение общими director metadata. Интегратор отвечает за итоговую комбинацию, не за корректность семантики кода и не за approval реальных запусков.

**#266:** разработчик отдельно исправляет issuer, QA смотрит L3; интегратор сливает только разрешённую версию. **#270:** developer добавляет одну команду в текущий PR; интегратор получает CI 14/14, не отправляет ещё один чат повторять невоспроизводимую проверку. **#299:** узкая чистая дельта вливается без сопутствующей регистрации. **#300:** интегратор последовательно переносит обновления #301, затем #300 в один актуальный status snapshot; GitHub conflict решается единожды.

**Устраняет:** большую часть конфликтов общего Board/registry/handoff и путаницы «кто сливает». **Остаётся:** интегратор может стать узким местом и ошибиться; ему нельзя разрешать обход проверки L3. **Цена:** средняя организационная (новая роль или переназначение части директора), **без отдельного технического сервиса**. **Скорость:** высокая при параллельных PR, ниже при одном исполнителе и одной простой задаче. **Контекст:** у директора меньше Git details, но интегратору нужен компактный статус входящих PR. Интегратор лучше постоянного «ещё одного QA чата», если главная потеря — конфликты.

### Вариант 5. Один источник фактов, остальные представления генерируются

**Механизм:** убрать дублирование «всё в ручном JSON+Board+handoff». Задания и статусы либо в едином узком registry, либо в GitHub Issues/PR labels/milestones; Board/сайт/директорский handoff становятся read-only **проекциями**, а не обязательными ручными записываемыми authority files. Live merged/current/CI берётся из GitHub, а immutable report хранит историческое «что доказано на какой версии», не копирует в себе вечный статус задачи. Удобный конкретный выбор для данного проекта: сохранить существующий config/director_task_plan.json как единый план и постепенно прекратить требовать одновременной ручной правки Board/handoff; current/live status подгружать по exact PR. Полная миграция на GitHub Issues — отдельный вариант внутри этой модели и дороже.

**#266:** registry указывает task и authority phase, кодовая готовность отдельно от разрешения на live issuer; исчезает коллизия «исправлено»/«можно запускать». **#270:** CI pass и merged status из GitHub; невозможно продолжать выдавать старый Board «unmerged» как истину. **#299:** меняется только правило запуска, без трёх файлов сопутствующего назначения. **#300:** пропадает главная область пересечения нескольких правок; статусные commit churn сокращаются.

**Устраняет:** дрейф статусов и значительную часть merge conflicts. **Остаётся:** интеграция с сайтом задач, необходимость schema migration, offline bootstrap и надежного чтения GitHub для директора. **Цена:** средняя/высокая, реальные изменения route/CI/static task page; **не начинать** как немедленную мелкую правку. **Скорость:** лучшая долгосрочно, после миграции; в переходе временно медленнее. **Контекст:** существенно меньше повторного чтения и реконструкций.

### Вариант 6. GitHub-first release pipeline, минимум отдельных ChatGPT-чатов

**Механизм:** задачи ведутся через Issues/PR, существующий GitHub Actions становится источником target test receipt; CI выводит какие тесты реально исполнены на каком SHA, простой релиз происходит при зелёных проверках и разрешении пользователя. Humans/ChatGPT review делают смысловую оценку только обозначенных dangerous changes. Release-manager наблюдает статус, не требует специального draft PR для каждого отчёта. Для production authorization отдельная ручная кнопка/approval остаётся, без новых фоновых ChatGPT-автоматизаций.

**#266:** L3 review плюс проверка Git-identity и authority inputs в уже существующих runners, но не постулировать несуществующую исходную внешнюю аттестацию. **#270:** единственная уже имеющаяся Notes V2 Action выполняет 14 cases; CI receipt достаточен для offline suite. **#299:** markdown one-line diff проходит на одном PR с адресным review. **#300:** integration branch/PR после serial rebase, conflict проверяется при merge.

**Устраняет:** значительную часть человеческой работы по сбору технических логов и отчётов. **Остаётся:** CI green может не доказать нужный сценарий, runner может быть не связан с требуемым файлом (как раньше #270), правила branch protection сейчас не enforced. **Цена:** высокая для полной версии — нормализация checks, потенциальная настройка branch protection и изменённые CI политики, что раньше пользователь специально запрещал добавлять без разрешения. **Скорость:** высокая после внедрения, но не разумный первый шаг в личном проекте; **контекст:** минимальный при зрелом pipeline.

### Вариант 7. Убрать постоянного директора для простых PR / один управляющий с внутренними ролями

**Механизм:** пользователь непосредственно формулирует небольшой запрос исполнителю, тот в одном диалоге планирует, реализует, использует GitHub CI и выдаёт конечное состояние; отдельный директор/QA/registration не обязателен. Для опасных L3 — отдельный reviewer или интегратор и explicit user permission. Альтернатива внутри модели — один постоянный управляющий ChatGPT с автономными ролями, но только если доступные инструменты реально обеспечивают их независимость и разграничение доступа; нельзя считать несколько «воображаемых ролей» в одном контексте независимой QA.

**#266:** опасный выпуск обязан уйти на независимый технический review, даже при одном управляющем. **#270:** один исполнитель сразу обнаружит невключённый в workflow target и запустит 14 тестов там; не тратит три физических QA-чата на недоступный checkout. **#299:** один короткий PR/проверка/решение пользователя без новой регистрации. **#300:** единый владелец штатно синхронизирует статус, поэтому нет двух одновременно пишущих Board/registry.

**Устраняет:** большую часть переводов контекста между director и worker. **Остаётся:** потеря независимого взгляда, риск слишком длинного одного диалога, слабее разделение функций; нужен cold-start из GitHub при ротации. **Цена:** низкая для узких низкорисковых задач, высокая при полном отказе от текущего governance; **скорость:** максимальна на малых задачах, плохо масштабируется на параллельные сложные. Это осмысленный режим для личного проекта, а не единственно верный глобальный стандарт.

## 6. Сравнение моделей и условия выбора

| Модель | Скорость после перехода | Цена перехода | Новые узкие места / риск | Context budget |
| --- | --- | --- | --- | --- |
| 1. Две точечные правки | Сразу быстрее на review loops | Низкая | Остаются конфликтующие status writers | Лучше |
| 2. Одно конечное принятие | Быстрее для связанного deliverable | Средняя | Слишком большой PR, длинный worker | Иногда лучше, иногда хуже |
| 3. По уровню риска | Быстрее для большинства небольших задач | Низкая/средняя | Неверная классификация L3 | Лучше |
| 4. Интегратор | Быстрее на параллельных ветках | Средняя | Single-person bottleneck | Лучше у директора, умеренно у интегратора |
| 5. Единый источник фактов | Быстрее стабильно после миграции | Средняя/высокая | Смена формата сайта/плана | Существенно лучше |
| 6. GitHub-first release | Быстрее после существенной настройки | Высокая | Слепота CI к неназванным сценариям | Очень хорошо |
| 7. Без директора для small changes | Быстрее при малом масштабе | Низкая/высокая | Нет автоматически независимого reviewer | Хорошо в коротких сессиях |

**Если цель — быстро прекратить лишние циклы:** выбрать 1 + 3 и одно простое правило из 4: только один интегратор/директор пишет общие административные файлы; во время параллельного программирования изменения этих файлов откладывать до одного финального update. Не внедрять интеграционный сервис, новые Actions, новый CI или новый реестр.

**Если цель — устойчивая долгосрочная параллельная работа:** 3 + 4 + 5. Director — решения и приоритеты; developer — реализация; QA — риск L3/сложный L2, интегратор — только готовность общей ветки и статус; GitHub — единая техническая и статусная authority. Удалить дублирующие ручные write requirements, а не создавать поверх них шестой status-file.

**Когда вариант 2 лучше 4:** один непрерывный user-visible feature с тесно связанными кодовыми файлами; важно сохранить один end-to-end outcome. Когда 4 лучше 2: несколько действительно независимых функций, но единые статусные файлы. **Когда 7 приемлем:** один короткий низкорисковый PR, а пользователь хочет личную быструю итерацию; опасные действия всё равно требуют независимой защиты.

## 7. Эксперимент на следующем PR: без новой петли проверок

Один следующий **неproduction** L0/L1 или хорошо изолированный L2 PR используется как пилот после решения пользователя. Не переоткрывать уже принятые #270/#299/#300. До начала на одной странице зафиксировать:
1. Что конкретно меняется, fileset и риск L0–L3; owner PR, owner integration, одна acceptance-гипотеза, существующая тестовая команда.
2. Что считается **материальным изменением**, требующим новой проверки: изменение логики/workflow/исполняемой инструкции/bindings/permissions; не ordinary report-only текст. При неизвестной классификации повышать риск.
3. Условия остановки: нужный тест реально запущен в доступной среде, прошёл; конфликтов merge нет; при L3 есть независимая содержательная QA и отдельное разрешение на live действие. Без неназванных дополнительных этапов.
4. Прочие отчёты — ссылка/комментарий к тому же PR или один final report, не новый status PR на каждый event. Board/registry обновляет один actor **однократно** после изменения фактического состояния.

Замерить не выдуманные проценты, а фактические: количество отчётов без новой проверки, число попыток запусков, число конфликтов общих файлов, количество PR от запроса до работающего результата, сколько раз тест реально запускался и сколько разных worker-чатов пришлось создавать. Сравнить с подтверждёнными #270 (три 0/14 и один 14/14), #299/#300 конфликтом — без притворной универсальной статистики. Если пилот потерял реальную дефектную проверку или не может доказать materiality, откатить упрощение для соответствующего класса, не для всего проекта.

## 8. Архитектурный preflight и границы выбора

1. **Владельцы:** config/execution_ownership_contract.json сохраняет GitHub control plane производства (scope/queue/retry/validation/persistence); interactive chat остаётся developer/operator, не scheduled production engine. Governance задача директора находится в DIRECTOR_PROTOCOL.md, а технический status — в GitHub.
2. **Разрешение:** сейчас ни одно правило не авторизует автоматическую отмену существующих QA/merge gates. Нужна отдельная пользовательская воля и **замена**, а не наложение нового правила в том же canonical file. Нынешний report не изменяет никаких правил.
3. **Не переносить:** предлагаемые упрощения не переносят queue/ingest/semantic validation из GitHub в Director, автономного worker-а или браузер. Вариант 6 технически потребует отдельного решения о CI/config/permissions, вариант 5 — изменения site task source/projections.
4. **Нет нового scheduler:** предложения сами по себе не добавляют recurring stage, backlog manager, retry или production dispatch. Любой будущий настоящий V2 запуск и изменение production gates остаются отдельным явным решением.

**Что должно оставаться защищённым независимо от operating model:** фактическая консистентность перед merge, выполнение именно релевантных тестов, сохранение V1, проверка immutable original scope/bindings/отсутствия перезаписи, разграничение synthetic tests и live authenticated receipt, отдельное разрешение реальных семантических/production действий. Не подменять «личный проект» предположением, будто bugs/races больше не существуют; корректировать строго избыточные недостижимые proof requirements, а не устранять полезные invariants.

## 9. Решения для пользователя (не новая обязательная проверка)

**Решение A — быстрое:** разрешить один узкий operating-rule PR, который (i) ограничивает повторный QA материальной дельтой и невалидирует лишь обычный report-only commit, (ii) классифицирует L0–L3 и отменяет отдельного QA-работника для L0/простого L1, (iii) закрепляет одного ответственного за Board/registry/handoff; **не меняет** CI, код/production или отдельные live authorizations. Это мой практический выбор сейчас.

**Решение B — без перестройки правил:** на следующей малой задаче испытать вариант 7 в ручном режиме с существующими обязательными merge rules, зафиксировать разницу и только затем выбрать protocol delta. Польза меньше, но риск перехода почти нулевой.

**Решение C — структурное:** отдельно одобрить проект с одним статусным источником, интегратором и risk-based QA (варианты 3+4+5), миграционным периодом для страницы задач и отменой дублирующих ручных writes. Не совмещать с текущим исправлением #266, чтобы опять не получить конфликт.

**Решение D — радикальное:** GitHub-first release pipeline или частичный отказ от директора для ordinary work (6/7); выбирать только если цена ручной координации продолжает превышать стоимость миграции. Не вводить из инерции «ещё одну роль QA» при той же процедуре и тех же дублированных файлах.

- **Validation:** сравнение live PR metadata #266/#269/#270/#274/#282/#289/#290/#294/#295/#299/#300/#301/#302; подтверждение конкретных GitHub Actions 40287779143 из worker-report; просмотр DIRECTOR_PROTOCOL/CHAT_PROTOCOL/CHAT_CONTEXT, ownership, routes, Board/current registry, соответствующих PR-file scopes и QA-reports. Локальные Python тесты **не запускались**, потому что аудит не меняет executable code.
- **Не доказано:** реальные интервалы времени между действиями пользователя (не вести фиктивную метрику часов); неизвестный будущий production ущерб от упрощения governance; отсутствие branch protection сейчас не доказывает, что будущие PR можно сливать без human approval; отсутствие auth write-run у #266 не доказывает, что его вообще нельзя реализовать в будущем.

- **Recommended next step:** пользователь выбирает A (предпочтительно), B, C или D, после чего директор выдаёт **одно** ограниченное соответствующее поручение/пилот без новой цепочки предварительных аудитов.
