Do not assume GitHub Actions automatically bypasses PR review or that a narrowly scoped bypass is available.

**Gate B — reliable all-path required check (separate future authorized implementation PR):**
1. Introduce a **uniquely named** read-only PR job/context, e.g. main-pr-integrity, which runs on every pull_request path (without path filters, including docs-only and code-only), has bounded synthetic validations, and does not deploy or write production. Also cover merge_group if a merge queue is separately enabled. Existing job **validate** is ambiguous; backlog-disposition, synthetic-v2, core-and-optional-isolation, deploy and skipped guarded jobs are NOT valid universal requirements as-is.
2. First observe exact-head success across at least a report-only PR, a web/code PR and a workflow/config PR, and verify new SHA reruns; resolve duplicate names/required source App selection. Only then select the verified single stable job (and other proven always-triggered independent gates) as required. Leave specialized filtered jobs as automatic CI evidence, not blanket required checks.

**Gate C — human review and branch integrity (admin-only after bot compatibility confirmed):**
1. Require PRs for human changes; require **at least one independent approval** only after confirming a second real eligible reviewer exists. GitHub PR author self-approval does not satisfy independent review. Check collaborator permission and plan availability; otherwise enabling this can deadlock a single-owner repository.
2. Enable dismissal of stale approvals on new reviewable commits and, if actually available, require review of the most recent reviewable push; require conversation resolution if validated on this repo. Require required checks to pass on current changes, rather than historical success.
3. Block ordinary direct pushes and force pushes, disable branch deletion; verify effects on administrators and bypass actors. Consider linear history only after checking the merge strategy (repository currently permits merge, squash and rebase). Do not enable an untested include-admins/do-not-bypass mode before bot and rescue routes are proven.
4. Model recovery explicitly: a trusted administrator must retain the ability to correct mistaken rules through GitHub Settings or documented approved rollback; test access using a test rule/branch first. Keep emergency action logged, narrow and time-limited; review afterwards. Emergency bypass is a risk exception, not the everyday bot mechanism.

**Gate D — bot/production compatibility selection (director + administrator, separately authorized):**
- **Option 1:** move automated data updates through dedicated PRs with compatible validation/merge policy; has architectural and nightly latency implications; independent approval may prevent unattended completion.
- **Option 2:** use a purpose-specific GitHub App/bypass if the repo account/plan/ruleset UI actually supports that actor and permissions; verify end-to-end, limit credentials and actor capability, and accept residual risks of bypass. Current integration/metadata DO NOT prove feasibility.
- **Option 3:** separate immutable production-data writes from protected application source (e.g. a verified artifact/data branch or storage contract), then tighten main; larger redesign requiring its own canonical contract and rollout.

**No option is authorized by this audit.** Prefer a documented proof-of-compatibility before require-PR/reviews are enforced. A safer partial first step could be to restrict force pushes and deletion *if the administrator proves these settings do not block existing canonical writers*, but do not equate partial protection with a full protected main.
