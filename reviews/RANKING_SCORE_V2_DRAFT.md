# Draft: прозрачный рейтинг 0–100

Статус: **draft_for_user_approval**  
Дата: 2026-08-30

Это не production-policy. Документ фиксирует конкретный вариант новой модели для согласования до изменения `config/final_ranking_policy.json`.

## 1. Что должно остаться вне баллов

### Eligibility gates
До рейтинга по-прежнему применяются жёсткие правила:
- taste fit ниже moderate → не включать;
- скидка 5% и меньше → не включать;
- абсолютный бюджетный потолок 750 ₽ → не включать;
- действующие fit-specific budget gates сохраняются;
- уже закончившаяся акция не становится кандидатом.

Баллы не имеют права «спасать» кандидата, который не прошёл эти gates.

### Срочность окончания скидки
Предлагаемый порядок:
1. скидка заканчивается сегодня;
2. затем завтра;
3. затем остальные/срок неизвестен;
4. **внутри одного уровня срочности — `total_score` по убыванию**.

Причина: срочность — это не качество игры и не качество сделки, а риск не успеть увидеть предложение. Если добавлять её в 0–100, итоговый балл перестанет означать качество покупки.

UI должен показывать её первой как отдельную строку: `Срочность: сегодня / завтра / обычная`, с пояснением `вне баллов, влияет на порядок показа`.

### Явное действие пользователя
`manual_end_at` («В конец очереди») остаётся абсолютным локальным override поверх production-порядка и не меняет score.

## 2. Итоговая модель

`total_score = personal_score + purchase_score`

- `personal_score`: 0–60 — насколько игра подходит конкретному пользователю;
- `purchase_score`: 0–40 — насколько выгодно покупать её сейчас;
- `total_score`: 0–100 — единственный обычный числовой критерий final ranking внутри одного уровня срочности.

`priority_bucket` после перехода на V2 перестаёт быть ranking-фактором. Метка `БРАТЬ СЕЙЧАС / МОЖНО БРАТЬ / ЛУЧШЕ ЖДАТЬ` может остаться объясняющей, но не должна учитываться второй раз поверх тех же ценовых факторов.

## 3. Personal score: до 60

### 3.1. Насколько сама игра подходит по вкусу: 0–50

Это price-blind semantic score. Нельзя использовать:
- цену;
- скидку;
- wishlist;
- Steam reviews;
- SteamDB/history;
- sale end.

Для **точно оценённой пользователем этой же игры** прямой рейтинг является сильнейшим якорем:
- 5.0/5 → 50/50;
- 4.5/5 → 45/50;
- 4.0/5 → 40/50;
- 3.5/5 → 35/50;
- 3.0/5 → 30/50;
- и т. д. (`rating × 10`).

Текстовые объяснения пользователя имеют приоритет при разборе причин и конфликтов; числовой direct rating не должен потом получать ещё один отдельный бонус.

Для неоценённых игр semantic worker должен вернуть структурированный положительный score, а не только `strong/moderate`:

| Подкритерий | Максимум | Смысл |
|---|---:|---|
| Основной геймплей, управление и мастерство | 18 | Насколько сам процесс игры попадает в устойчивые предпочтения |
| Развитие, разнообразие и meaningful change | 12 | Меняются ли ситуации/возможности, есть ли ощущение развития вместо статичного повтора |
| Структура, темп и понятный вектор | 8 | Есть ли регулярная причина продолжать и достаточно ли понятно, что/зачем делать |
| Яркие персональные крючки и идентичность | 8 | Атмосфера, арт, история, персонажи, тактика, совместный опыт, сильная уникальная идея — только если они реально релевантны этой игре |
| Дополнительная ширина подтверждённого совпадения | 4 | Несколько независимых устойчивых профильных совпадений, не дублирующих пункты выше |
| **Итого положительное соответствие** | **50** | |

Важно: это **положительный fit**, а не уже уменьшенный score за риски. Негативные evidence остаются отдельно, чтобы пользователь видел точный штраф и чтобы один сигнал не учитывался скрыто дважды.

`strong/moderate/below_moderate` сохраняются как eligibility classification, но больше не являются основной градацией порядка внутри финального списка.

### 3.2. Wishlist: 0 или +4

- в wishlist: `+4`;
- не в wishlist: `0`.

Wishlist не является доказательством taste fit и применяется только после eligibility. Он не меняет semantic taste score 0–50.

### 3.3. Достижения: 0–3

Предлагаемая шкала:
- quality 5/5 → `+3`;
- 4/5 → `+2.5`;
- 3/5 → `+2`;
- 2/5 → `+1`;
- 1/5 → `+0.5`;
- Steam Achievements есть, но quality не оценён → `+1.5`;
- подтверждённо нет → `0`;
- статус неизвестен → `+1.5` (нейтрально, чтобы отсутствие данных не штрафовало автоматически).

### 3.4. Продолжительность: 0–3

Слабый фактор:
- preferred 10–40 ч → `+3`;
- слегка короче/длиннее → `+2`;
- очень короткая/длинная → `+1`;
- extreme → `0`;
- неизвестно → `+2` (нейтрально).

### 3.5. Персональный/практический риск: штраф 0…−12

Чтобы риск был видим, но не работал как абсолютный lexicographic барьер:
- подтверждённых рисков нет → `0`;
- слабый описательный риск → `−1`;
- средний подтверждённый риск → `−3`;
- высокий персональный конфликт → `−10`;
- подтверждённая серьёзная Windows-проблема → `−12`.

Используется **самый сильный применимый штраф**, а не сумма всех мелких рисков. Это предотвращает ситуацию, когда пять мелких эвристик случайно дают больший штраф, чем один реально серьёзный конфликт.

Отсутствие Steam Achievements не входит в этот risk penalty, потому что уже учтено отдельным achievement-score.

### 3.6. Формула personal score

`personal_score = clamp(taste_positive_score + wishlist_points + achievement_points + duration_points - risk_penalty_abs, 0, 60)`

Максимум без риска: `50 + 4 + 3 + 3 = 60`.

## 4. Purchase score: до 40

### 4.1. Размер скидки: 0–20

Скидка 5% и меньше уже исключена до score.

Предлагаемая шкала:
- 6–14% → `1`;
- 15–24% → `3`;
- 25–34% → `5`;
- 35–44% → `7`;
- 45–54% → `10`;
- 55–64% → `13`;
- 65–74% → `16`;
- 75–84% → `18`;
- 85–94% → `19`;
- 95–100% → `20`.

Это самый сильный purchase-фактор. Он намеренно весит больше history, чтобы первая −20% скидка новой игры не выигрывала только из-за формального `record`.

### 4.2. Текущая цена / комфорт бюджета: 0–12

Низкая цена — плюс, но разница внутри нормального бюджета намеренно небольшая:
- ≤100 ₽ → `12`;
- 101–250 ₽ → `11`;
- 251–400 ₽ → `10`;
- 401–500 ₽ → `9`;
- 501–550 ₽ → `7`;
- 551–650 ₽ → `4`;
- 651–750 ₽ → `1`.

Таким образом, игра за 39 ₽ получает всего на 3 балла больше игры за 460 ₽, а не огромный бонус просто за дешевизну.

### 4.3. Цена относительно истории: 0–8

Предлагаемая шкала:
- `record` → `8`;
- `near_record` → `7`;
- `good_vs_history` → `5`;
- `unverified` → `3`;
- `previously_free` → `2`;
- `well_above_history` → `0`.

`unverified` получает нейтрально-низкий балл, а не ноль: отсутствие SteamDB evidence не должно автоматически превращаться в доказательство плохой сделки.

`previously_free` ниже unverified: это уже известный факт, что раньше игру можно было получить выгоднее текущей платной цены.

### 4.4. Что НЕ получает отдельные баллы

- `БРАТЬ СЕЙЧАС / МОЖНО БРАТЬ / ЛУЧШЕ ЖДАТЬ` — это производная объясняющая метка, иначе произойдёт double count history/budget;
- `priority_bucket` — устаревающий смешанный слой V1;
- direct user evidence — уже входит в taste score;
- низкая цена/новизна/короткая история не получают отдельного штрафа;
- title используется только как deterministic final tie-break при полном равенстве score.

## 5. Вид на карточке

Пример структуры:

```
Итог: 82/100

Насколько подходит тебе: 53/60
  Игра сама по себе            +44/50
  Вишлист Steam                 +4/4
  Достижения                    +3/3
  Продолжительность             +2/3
  Риск                           0

Выгодность покупки: 29/40
  Скидка                       +16/20
  Текущая цена                 +10/12
  История цены                  +3/8

Срочность: обычная
  Вне баллов; влияет на порядок показа.
```

Каждая строка должна приходить готовой из producer (`score_breakdown`), UI ничего не пересчитывает.

## 6. Production contract

После одобрения дизайна:
1. создать новую canonical версию final ranking contract (V2), а V1 пометить superseded rationale в `PROJECT_DECISIONS.md`;
2. расширить semantic taste result/cache schema: score + structured breakdown;
3. bump `taste_model_version` / taste semantics, чтобы старые categorical cache entries не выдавались за числовые;
4. существующий scheduled semantic worker получает score в **том же taste evaluation**, без создания новой recurring стадии;
5. GitHub валидирует score bounds/sum и сохраняет его в canonical taste cache;
6. final producer детерминированно считает wishlist/achievements/duration/risk/deal points и `total_score`;
7. сортирует `urgency → total_score DESC → title`;
8. записывает полный `score_breakdown` в `current.json` и bounded ranking lookup;
9. UI только отображает готовые значения;
10. regression tests проверяют не отдельные названия игр, а классы конфликтов и несколько контрольных реальных примеров.

## 7. Миграционная цена

Текущий taste cache V2 не содержит числового score. Честный переход потребует одноразового обновления price-blind taste verdicts через **существующую** taste queue после bump модели/семантики. Не следует придумывать числовые значения задним числом из `strong/moderate`: это даст красивую, но ложную точность.

После миграции новый score кэшируется так же, как текущий taste verdict, и повторно не считается каждый день без изменения fingerprint/profile/semantics.

## 8. Основные продуктовые решения, требующие подтверждения пользователя

1. Оставляем ли срочность абсолютным отдельным слоем вне 0–100 (рекомендованный вариант)?
2. Принимаем ли структуру `60 personal / 40 purchase` в указанном виде?
3. Достаточен ли высокий персональный риск `−10`, Windows `−12`, или нужен другой масштаб?
4. Принимаем ли purchase-веса `скидка 20 / цена 12 / история 8`?

До подтверждения этих четырёх пунктов production на V2 не переключать.
