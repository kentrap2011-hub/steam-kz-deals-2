# CHAT_CONTEXT

Короткая точка входа для любого нового чата, работающего с рассылкой.

Главный принцип: **GitHub хранит состояние и правила проекта; чат — временная рабочая сессия.** Не переносить в новый чат старые логи, большие JSON и длинную историю обсуждений, если это не требуется текущей задачей.

Этот файл заменяет старую практику, при которой `PROJECT_RULES.md` считался обязательной полной точкой входа для каждого нового чата. Если в начале `PROJECT_RULES.md` встречается старая формулировка об обязательном чтении всего файла, для организации рабочего контекста приоритет имеет `CHAT_CONTEXT.md`.

## 1. Источники истины

### Репозиторий рассылки
`kentrap2011-hub/steam-kz-deals-2`

- `config/mailing_policy.json` — каноническая машинная политика рассылки.
- `config/mailing_policy.md` — короткое человекочитаемое описание политики.
- `PROJECT_RULES.md` — архив подтверждённых пользователем целей и договорённостей. Не читать целиком для каждой задачи.
- `data/cache/taste_fit.json` — постоянный кэш taste verdict.
- `data/production/pre_ai/chatgpt_payload.json` — основной вход ChatGPT для обычного production-run.
- `data/production/pre_ai/chatgpt_taste_queue.jsonl` — только кандидаты, которым требуется новый semantic taste verdict.
- `data/production/pre_ai/chatgpt_purchase_context.jsonl` — purchase/deal context; читать только нужные строки и только после фиксации taste verdict для соответствующего кандидата.

### Репозиторий вкуса и оценок
`kentrap2011-hub/stopgame-ratings-data`

- `gaming_taste_live.json` — единственный канонический живой профиль вкуса.
- `ratings.json` — фактические оценки StopGame.
- `steam_wishlist.json` — контекст интереса; wishlist не является доказательством taste fit.
- `gaming_taste_database_2026-08-12.json` — исторический архив. Не использовать в текущей логике.
- `.github/taste_update_request.json` — вход для небольших обновлений профиля через существующий update workflow.

Копии этих данных в ChatGPT/File Library не считать каноническими, если они расходятся с GitHub.

## 2. Что читать в начале задачи

Всегда сначала прочитать только этот файл, затем открыть минимальный набор файлов для конкретной задачи.

### Обычный выпуск / обработка production
1. `CHAT_CONTEXT.md`
2. `data/production/pre_ai/chatgpt_payload.json`
3. `data/production/pre_ai/chatgpt_taste_queue.jsonl`
4. Зафиксировать taste verdict для очереди без цены, скидки, reviews, wishlist и deal-quality.
5. После этого читать только соответствующие строки `chatgpt_purchase_context.jsonl` и использовать уже рассчитанные deal-сценарии.

Не читать весь каталог, все cache-файлы, весь pre-AI snapshot или полный профиль вкуса без необходимости.

### Новая пользовательская оценка / уточнение вкуса
1. Прочитать только релевантный участок `gaming_taste_live.json`, если он нужен для корректного обновления.
2. Подготовить небольшой delta-запрос через `.github/taste_update_request.json` и существующий workflow.
3. Не переписывать полный профиль через чат и не использовать исторический snapshot.

### Баг / ошибка workflow
1. `CHAT_CONTEXT.md`
2. Конкретный падающий workflow/script.
3. Только релевантная часть лога ошибки.
4. Не читать `PROJECT_RULES.md`, если ошибка не связана с изменением бизнес-логики.

### Изменение правил отбора / архитектуры
1. `CHAT_CONTEXT.md`
2. Релевантный раздел `PROJECT_RULES.md`.
3. `config/mailing_policy.md` и при необходимости `config/mailing_policy.json`.
4. Только затронутые contract/script/workflow файлы.

## 3. Контекстная гигиена

- Не вставлять в чат целиком многомегабайтные JSON, каталоги, кэши и логи.
- Предпочитать точечное чтение, поиск по ключу, диапазоны строк и diff.
- Не читать одновременно `PROJECT_RULES.md` и полный `mailing_policy.json`, если задача не требует сверки/изменения политики.
- Не читать полный `gaming_taste_live.json`, если достаточно конкретного раздела или уже подготовленного price-blind candidate context.
- Не переносить старую историю дебага в новый чат. Сохранять долговечный результат в GitHub, а не в памяти разговора.
- После завершения задачи новый чат может начинаться заново с этого файла и актуального GitHub-состояния.

## 4. Работа нескольких чатов

Разные чаты могут работать с одним GitHub-репозиторием, но их разговорная память не синхронизируется автоматически.

Перед любым изменением файла:
- заново прочитать его актуальную версию из GitHub;
- использовать текущий blob SHA;
- не допускать одновременного редактирования одного и того же файла двумя чатами.

Изменения, уже записанные в GitHub другим чатом, считать актуальным состоянием проекта после повторного чтения.

## 5. Когда нужен полный `PROJECT_RULES.md`

Только если задача меняет или проверяет:
- цели рассылки;
- taste/deal приоритеты;
- ценовые ограничения;
- правила wishlist/history/reviews;
- семейство изданий/DLC;
- финальную сортировку и пользовательский формат;
- архитектурные договорённости проекта.

Для обычного запуска, локального бага, GitHub Action, чтения очереди или обновления профиля полный `PROJECT_RULES.md` не является обязательным входом.
