# CHAT_CONTEXT

Короткая точка входа для любого нового чата, работающего с рассылкой/витриной Steam KZ.

Главный принцип: **GitHub хранит состояние и правила проекта; чат — временная рабочая сессия.** Не переносить в новый чат старые логи, большие JSON и длинную историю обсуждений, если это не требуется текущей задачей.

### Почему это критично
Проект уже столкнулся с практической проблемой: рабочие чаты по рассылке быстро достигали лимита контекста из-за повторного чтения больших файлов, логов, JSON, истории предыдущих обсуждений и лишних промежуточных данных. Поэтому экономия контекста — **обязательное архитектурное ограничение проекта**, а не рекомендация по стилю.

Каждый новый чат должен с самого начала работать с явным **context budget**:
- сначала читать `CHAT_CONTEXT.md`;
- затем открывать только минимально необходимые файлы/строки для текущего шага;
- не загружать данные «на всякий случай»;
- не держать в разговоре то, что уже надёжно сохранено в GitHub;
- после завершения подзадачи фиксировать долговечный результат в репозитории, чтобы следующий чат мог продолжить без переноса всей истории;
- если задачу можно решить точечным поиском, диапазоном строк, diff или одним validation-файлом, не читать полный исходный файл;
- при выборе между удобством текущего чата и сохранением контекстного бюджета предпочитать решение, которое уменьшает объём контекста без потери корректности.

Этот файл заменяет старую практику, при которой `PROJECT_RULES.md` считался обязательной полной точкой входа для каждого нового чата. Если в начале `PROJECT_RULES.md` встречается старая формулировка об обязательном чтении всего файла, для организации рабочего контекста приоритет имеет `CHAT_CONTEXT.md`.

## 1. Источники истины

### Репозиторий рассылки
`kentrap2011-hub/steam-kz-deals-2`

- `config/mailing_policy.json` — каноническая машинная политика отбора и production.
- `config/mailing_policy.md` — короткое человекочитаемое описание политики.
- `config/daily_execution_contract.json` — канонический контракт суточного выполнения: ночной production в 01:00, без отдельной доставки в 08:00, витрина работает pull-based.
- `config/execution_ownership_contract.json` — каноническая граница ответственности: GitHub = control plane, scheduled ChatGPT = ограниченный external/semantic worker, интерактивный чат = developer/operator session, но не production executor.
- `PROJECT_RULES.md` — архив подтверждённых пользователем целей и договорённостей. Не читать целиком для каждой задачи.
- `data/cache/taste_fit.json` — постоянный кэш taste verdict.
- `data/production/pre_ai/chatgpt_payload.json` — основной вход ChatGPT для обычного production-run.
- `data/production/pre_ai/chatgpt_taste_queue.jsonl` — только кандидаты, которым требуется новый semantic taste verdict.
- `data/production/pre_ai/chatgpt_purchase_context.jsonl` — purchase/deal context; читать только нужные строки и только после фиксации taste verdict для соответствующего кандидата.
- `data/production/visual/current.json` — канонический готовый суточный payload для мобильной витрины. UI должен только читать его, а не заново вычислять содержимое.

### Репозиторий вкуса и оценок
`kentrap2011-hub/stopgame-ratings-data`

- `gaming_taste_live.json` — единственный канонический живой профиль вкуса.
- `ratings.json` — фактические оценки StopGame.
- `steam_wishlist.json` — контекст интереса; wishlist не является доказательством taste fit.
- `gaming_taste_database_2026-08-12.json` — исторический архив. Не использовать в текущей логике.
- `.github/taste_update_request.json` — вход для небольших обновлений профиля через существующий update workflow.

Копии этих данных в ChatGPT/File Library не считать каноническими, если они расходятся с GitHub.

### Иерархия канонического состояния и временного handoff

- `CURRENT_TASK.md` — **только временный operational handoff**: что начато, последний подтверждённый прогресс и следующий шаг. Он не является источником истины для архитектуры, расписаний, лимитов, бизнес-правил или количества обрабатываемых объектов.
- При возобновлении работы новый чат сначала читает `CURRENT_TASK.md`, но перед выполнением содержащегося там архитектурного утверждения обязан сверить его с каноническими policy/contract-файлами. При конфликте канонический контракт имеет приоритет, а `CURRENT_TASK.md` нужно исправить до продолжения работы.
- Для любых изменений ночного production обязательна сверка с `config/daily_execution_contract.json` **и** `config/execution_ownership_contract.json`. Для SteamDB/runtime дополнительно обязательна сверка с `config/steamdb_lookup_contract.json`.
- Старый workflow, прежняя automation, исторический лог, временный progress-файл или удобный размер batch не могут самостоятельно изменить текущую архитектуру.
- Размер batch/checkpoint нельзя трактовать как суточную квоту. Суточная квота существует только если она прямо записана в актуальном каноническом контракте.
- Нельзя создавать отдельную повторяющуюся automation вокруг стадии единого nightly pipeline только на основании временного handoff, старой задачи или технического batch-size. Для отдельной recurring-стадии должно быть прямое основание в каноническом контракте.

### Обязательный architecture preflight перед изменениями

Перед **любой** правкой workflow, automation, runtime-процесса, расписания, очереди, retry/checkpoint-логики или переносом работы между GitHub и ChatGPT необходимо до первой записи ответить на четыре вопроса:
1. Какой компонент сейчас является владельцем этой ответственности по `config/execution_ownership_contract.json`?
2. Какой канонический contract/policy прямо разрешает предлагаемое изменение?
3. Не переносит ли изменение control-plane логику из GitHub в scheduled ChatGPT или в текущий пользовательский чат?
4. Не создаёт ли оно новую recurring-стадию, квоту, очередь, retry-loop или backlog-manager без прямого канонического основания?

Если хотя бы на один вопрос нет однозначного ответа — **не начинать реализацию**. Сначала исправить/уточнить канонический контракт, затем продолжать.

Особенно важно: **поправка пользователя не отменяет preflight**. Она является сигналом, что текущая модель могла быть неверной. Нельзя автоматически согласиться и немедленно реализовать буквальную формулировку. Сначала нужно сверить её с каноническими контрактами; если именно контракт оказался неполным или неправильным — сначала исправить контракт.

Интерактивный пользовательский чат нельзя превращать в production worker для большого backlog. Ручная проверка нескольких объектов допустима только как bounded verification реализации. Если для закрытия production-задачи чат начинает вручную перебирать десятки/сотни игр, это считается архитектурным дефектом: остановить ручной перебор и чинить автоматический owning component.

## 2. Что читать в начале задачи

Всегда сначала прочитать только этот файл, затем открыть минимальный набор файлов для конкретной задачи.

### Обычный выпуск / обработка production
1. `CHAT_CONTEXT.md`
2. `config/execution_ownership_contract.json`
3. `data/production/pre_ai/chatgpt_payload.json`
4. `data/production/pre_ai/chatgpt_taste_queue.jsonl`
5. Зафиксировать taste verdict для очереди без цены, скидки, reviews, wishlist и deal-quality.
6. После этого читать только соответствующие строки `chatgpt_purchase_context.jsonl` и использовать уже рассчитанные deal-сценарии.

Не читать весь каталог, все cache-файлы, весь pre-AI snapshot или полный профиль вкуса без необходимости.

### Работа только над дизайном / мобильной витриной
1. `CHAT_CONTEXT.md`
2. Конкретные файлы `web/**`, которые меняются.
3. При необходимости — небольшой фрагмент `data/production/visual/current.json` только для проверки готовых полей.

**Не запускать и не переносить расчёты в UI.** Дизайн, CSS, кнопки, навигация и отображение должны работать поверх уже готового суточного payload.

### Новая пользовательская оценка / уточнение вкуса
1. Прочитать только релевантный участок `gaming_taste_live.json`, если он нужен для корректного обновления.
2. Подготовить небольшой delta-запрос через `.github/taste_update_request.json` и существующий workflow.
3. Не переписывать полный профиль через чат и не использовать исторический snapshot.

### Баг / ошибка workflow
1. `CHAT_CONTEXT.md`
2. Если баг затрагивает границу GitHub/ChatGPT, очередь, retry, automation или ownership — `config/execution_ownership_contract.json`.
3. Конкретный падающий workflow/script.
4. Только релевантная часть лога ошибки.
5. Не читать `PROJECT_RULES.md`, если ошибка не связана с изменением бизнес-логики.

### Изменение правил отбора / архитектуры
1. `CHAT_CONTEXT.md`
2. `config/execution_ownership_contract.json`.
3. Релевантный раздел `PROJECT_RULES.md`.
4. `config/mailing_policy.md` и при необходимости `config/mailing_policy.json`.
5. Только затронутые contract/script/workflow файлы.

## 3. Контекстная гигиена

- Главная цель раздела — не допускать повторения ситуации, когда рабочий чат преждевременно упирается в лимит контекста.
- Не вставлять в чат целиком многомегабайтные JSON, каталоги, кэши и логи.
- Предпочитать точечное чтение, поиск по ключу, диапазоны строк и diff.
- Не читать одновременно `PROJECT_RULES.md` и полный `mailing_policy.json`, если задача не требует сверки/изменения политики.
- Не читать полный `gaming_taste_live.json`, если достаточно конкретного раздела или уже подготовленного price-blind candidate context.
- Не переносить старую историю дебага в новый чат. Сохранять долговечный результат в GitHub, а не в памяти разговора.
- Не пересказывать заново уже зафиксированные в GitHub договорённости, если достаточно сослаться на соответствующий файл и продолжить работу.
- Для больших файлов сначала использовать поиск/индекс/validation/manifest; полный файл открывать только если точечного чтения недостаточно.
- После завершения задачи новый чат может начинаться заново с этого файла и актуального GitHub-состояния.

## 4. Работа нескольких чатов

Разные чаты могут работать с одним GitHub-репозиторием, но их разговорная память не синхронизируется автоматически.

Перед любым изменением файла:
- заново прочитать его актуальную версию из GitHub;
- использовать текущий blob SHA;
- не допускать одновременного редактирования одного и того же файла двумя чатами.

Изменения, уже записанные в GitHub другим чатом, считать актуальным состоянием проекта после повторного чтения.

## 5. Когда нужен полный `PROJECT_RULES.md`

Только если задача меняет или проверяет:
- цели рассылки;
- taste/deal приоритеты;
- ценовые ограничения;
- правила wishlist/history/reviews;
- семейство изданий/DLC;
- финальную сортировку и пользовательский формат;
- архитектурные договорённости проекта.

Для обычного запуска, локального бага, GitHub Action, чтения очереди или обновления профиля полный `PROJECT_RULES.md` не является обязательным входом.

## 6. Критический архитектурный контракт: 01:00 production и pull-based визуализация

Это обязательное правило проекта, которое нельзя обходить ради быстрого исправления интерфейса.

- **Отдельной рассылки/доставки в 08:00 больше нет и её нельзя создавать заново.** Пользовательский способ получения результата теперь — только визуализация.
- Суточный production выполняется по ночному регламенту в **01:00 Europe/Samara**. Он использует только актуальный завершённый production-contract: complete pre-AI payload, полную family partition и закрытую AI taste queue. Старый `final_self_check.validation.json` не является readiness-барьером для текущего production.
- Суточный production — **один общий production cycle**, а не очередь, которую намеренно растягивают на несколько дней. GitHub выполняет control-plane и детерминированную часть, доступную ему в ночном контуре; scheduled ChatGPT выполняет только явно подготовленную external/semantic data-plane работу, которую GitHub не может выполнить напрямую.
- **GitHub владеет scope, manifest/queue, ordering, retry-state, checkpoint merge, completeness и downstream orchestration.** ChatGPT не должен сам изобретать эти механизмы или заменять их разговорным циклом.
- **Никакой суточной квоты по числу игр нет.** Если обработка технически разбивается на batch по 10/20/50 или любому другому размеру, это только checkpoint внутри текущего production cycle. Завершение одного batch не означает завершение суточной работы, пока остаётся требуемый текущим контрактом scope.
- Все тяжёлые и смысловые вычисления выполняются в production-слое **один раз для суточного снимка**. К ним относятся внешние Steam/Store/SteamDB lookup, taste/deal-логика, eligibility/family, цены и история, практические признаки, тексты рисков, причины соответствия и итоговый `priority_rank`.
- После завершения текущего production формируется и сохраняется готовый `data/production/visual/current.json`; read-only Pages deploy публикует именно этот подготовленный payload.
- Витрина работает **pull-based**: пользователь в течение дня открывает её в любое удобное время и видит уже подготовленный замороженный суточный результат. Никакого отдельного утреннего push/mailing нет.
- Открытие или обновление витрины **не должно** инициировать Steam/API/web-запросы, пересчёт taste/deal, eligibility/family, цены, истории, рисков, причин или `priority_rank`.
- Веб-интерфейс и Pages-deploy являются **read-only consumer** готового payload. Изменение CSS, HTML, кнопок, расположения блоков или другого оформления не должно запускать смысловой production.
- Если в готовом payload отсутствует риск, неправильный порядок, неверный текст или другое смысловое поле, исправлять producer/суточный расчёт и следующий готовый payload. **Не добавлять бизнес-логику или эвристический fallback во frontend.**
- Допустимая клиентская логика — только состояние интерфейса: текущая карточка, ручное «в конец очереди», вкладки, галерея, локальное сохранение прогресса. Она не должна решать, какая игра лучше или какой у неё риск.
- `priority_rank` считается заранее. UI обязан сохранять этот порядок как исходный и может менять его только по явному действию пользователя.
- Для намеренной разработки самой расчётной логики допускается принудительный тестовый rebuild, но это отдельное осознанное действие и не должно происходить от обычной правки дизайна.

## 7. Правила совместной работы с пользователем

Эти правила обязательны для всех будущих чатов проекта.

- Не соглашаться автоматически с предложением пользователя только потому, что оно предложено пользователем.
- **После любого пользовательского исправления архитектурной модели сначала повторно пройти architecture preflight; не переходить прямо к реализации.**
- Сначала оценить вариант по существу: плюсы, минусы, риски и наличие более сильного решения.
- Если есть существенное возражение или более удачный вариант, сказать об этом прямо и объяснить почему, прежде чем вносить изменение.
- После того как пользователь услышал возражения/альтернативу и всё равно выбрал свой вариант, окончательное решение остаётся за пользователем и фиксируется как правило проекта.
- Не принимать за пользователя спорные продуктовые решения, если выбор действительно неоднозначен. При этом не задавать лишних уточнений там, где безопасно сделать очевидный технический шаг.
- Учитывать, что пользователь часто использует голосовой ввод: не цепляться за опечатки и искажённые слова, если смысл понятен из контекста; уточнять только реальную неоднозначность.
- Если новая договорённость меняет архитектуру, поведение рассылки или стиль взаимодействия, сохранять её в GitHub, а не рассчитывать на память конкретного чата.
- Перед началом любой нетривиальной подзадачи явно сообщать пользователю, что именно начинается. Одновременно создавать или обновлять корневой файл `CURRENT_TASK.md` со статусом `in_progress`, временем старта, кратким описанием текущей подзадачи, последним подтверждённым прогрессом и следующим шагом. Новый чат при фразе вроде «продолжи работу прежнего чата, информация есть в GitHub» сначала проверяет `CURRENT_TASK.md`, затем сверяет архитектурные утверждения из него с соответствующими каноническими contract/policy-файлами и только после этого продолжает.
- `CURRENT_TASK.md` не может авторизовать перенос ответственности между GitHub/ChatGPT/UI или создание новой automation. Для этого всегда нужен канонический contract.
- После успешного завершения подзадачи `CURRENT_TASK.md` удалять. Если работа прервалась, файл сохраняется как durable handoff для следующего чата.
- Во время длительной подзадачи давать короткие сообщения о реальном прогрессе, если работа продолжается заметно дольше одного обычного шага. Не придумывать и не обещать точное время будущего завершения; вместо ETA сообщать время старта, последний подтверждённый прогресс, текущий шаг и при необходимости новый статус. Это позволяет отличить продолжающуюся работу от зависания без ложных обещаний по времени.
