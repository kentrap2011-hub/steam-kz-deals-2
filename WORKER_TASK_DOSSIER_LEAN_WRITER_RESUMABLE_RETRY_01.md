## IMPLEMENT — убрать fail-forever претензию без открытия произвольных writes
A. Явно раздели immutable **trial authorization**, отдельные **execution attempts**, **exclusive lease/lock**, и **terminal accepted outcome**; не превращай failed attempt в окончательную потерю права записи. Спроектируй короткую читаемую state machine: READY → RUNNING/LEASED → RETRYABLE_FAILED or BLOCKED_INVALID_INPUT → ACCEPTED. Attempt history append-only; прошлые claims/Action IDs не удаляются и не подменяются. После ACCEPTED всех членов любой повтор — verified NOOP. Для уже записанной части — либо детерминированный resume only missing, либо fail closed без дублирования, согласно реальной atomicity writer. Нельзя повторно принять тот же файл/receipt с другим содержимым.
B. Гарантируй single-writer concurrency, owner actor/repo/main SHA, eligible original grant, exact unchanged six, immutable source/SHA/TTL/year, refusal on changed payload, safe sandbox namespace, commit compare-and-swap, exact N+N readback, fail-closed on invalid schema/evidence/auth. Различай transient infrastructure / prewrite / postwrite uncertain failures; при uncertain write сначала readback reconcile. Никогда не обходи строгий V2 validator, не меняй Research/Assembly, канонический main/Deep/production.
C. Возврат работоспособности без бюрократии: GitHub сам может осуществить **ограниченный автоматический retry транзитной ошибки** или автоматически возобновить READY после принятого исправления кода, и должна существовать простая owner-approved recovery для того же trial без нового досье, нового worker-чата/отдельного grants/ручных JSON и без rerun старого Actions ID. Не создавать бесконечный loop/retry storm. Зафиксируй объяснимые пределы попыток/backoff/final block, GitHub-owned triggers, возможность явного STOP/pause. Если безопасная политика без дополнительного owner signal невозможна, покажи самый короткий событийный вариант, не скрывай ограничений.
D. **Специально для исторической шестерки:** старый spent claim и исходный старый failed run НЕ переписывай и НЕ удаляй. Подготовь миграцию/provenance для прежней неизменной авторизованной партии под новым execution lifecycle, с явным policy decision boundary. Дизайн/тесты могут доказать её безопасность; НЕ запускай live retry и НЕ считай предыдущую exhausted authority автоматически восстановленной в source PR. Для live попытки требуется отдельный точный scope-matched owner grant после source review, если действующий канонический контракт его требует.
