## Что конкретно закончить

1. Выясни один точный недостающий переход: каким способом существующий **общий механизм записи GitHub**, под текущей общей блокировкой писателя, может получить подтверждённые входы V2 (run/marker, trial, неизменные Research/Assembly commits, исходную игру) и вызвать **уже реализованный** режим `notes_v2` в `scripts/taste_steam_review_dossier_buffered.py`. Не создавай второй писатель или новую систему приёмки.
2. **Реализуй необходимое подключение сейчас**: только отдельно разрешаемый, по умолчанию выключенный путь V2 через существующее владение GitHub и общую блокировку записи. Если нужен минимальный V2-only вход в уже существующем workflow/script/contract, измени его без изменения обычного V1-пути. Не требуй успешности всей тройки. Не запускай настоящий workflow/семантическую работу.
3. Убери выявленное противоречие между V2-only индивидуальной приёмкой и старым условием приёма тройками **каноническим способом**, сохранив V1 неизменным. При этом файл `config/dossier_research_notes_v2_contract.json` также изменяется незавершённым PR #266: НЕ перезаписывай чужую ветку и не теряй её изменения. Используй согласованное переиспользование V2-only правила/приоритета, либо явно укажи точную зависимость, если без одновременного принятия #266 нельзя безопасно довести подключение до конца.
4. Проверь существующую схему общей блокировки записи, конфликты с ранее принятыми V1 Dossier, запись результата и подтверждения **в одной транзакции** и границу будущего использования Deep. Не менять поведение V1 и не объявлять готовую V2-игру Deep-ready без разрешённой канонической записи.
5. **Проведи полный ограниченный проверочный сценарий на тестовых данных** существующими инструментами, без настоящего Research или Assembly: игры A и C пригодны, B содержит ошибку. A и C отдельно принимаются и сохраняются, B отклоняется; обработка следующих игр продолжается. Проверь, что повторная запись не создаёт другой результат, а ошибка общей записи не выдаётся за успех. Если существующая инфраструктура позволяет безопасную проверку через GitHub в специально изолированной тестовой ветке без реальных данных, проверь именно её и фактическое подтверждение GitHub; иначе выполни имеющиеся подходящие тесты, назови ограничение и **не называй локальный результат реальной публикацией**. Не придумывай дополнительную инфраструктуру ради проверки.
6. Уже написанный код из PR #274, существующие тесты и общая система записи — основа решения. Все необходимые локальные тесты и применимые существующие проверки GitHub должны быть запущены и указаны точно. Новые тесты добавляй только при обнаружении конкретной непроверенной ошибки.
